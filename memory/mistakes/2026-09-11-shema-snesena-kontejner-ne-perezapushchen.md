# 2026-09-11 — схема снесена вручную, контейнер приложения не перезапущен, health не увидел пустую базу

**Вес:** стенд выглядел живым, будучи мёртвым; поймано только руками
**Где:** `src/app/health/route.ts`, `src/app/header.tsx`, процедура ручных операций с базой стенда

## Что произошло

Последовательность как есть:

1. Оператор снёс схему базы стенда вручную через `psql`: `DROP SCHEMA public; CREATE SCHEMA public`.
2. Нажал **Deploy** в Dokploy. Код не менялся, поэтому Dokploy контейнер `app` **не пересоздал** — а миграции и сид выполняет только `docker-entrypoint.sh`, при старте контейнера.
3. Миграции не отработали. База отвечает, соединение живое, таблиц нет.
4. `/health` делал `select 1` — и был **зелёным**. Соединение есть, о таблицах он не спрашивал.
5. Шапка на каждой странице глотала ошибку базы через `.catch(() => [])` — страницы отдавали **200** с пустыми состояниями, переключатель пользователя пустой.
6. Все API-роуты падали с `relation "plants" does not exist` (42P01), `/assistant` и `/questions/[id]` — server error: там `currentUser()` был без `.catch`.

Восстановлено вручную из контейнера: `node dist/migrate.cjs && node dist/seed.cjs`.

## Почему казалось правильным

Три решения, каждое разумное по отдельности, вместе спрятали инцидент:

- **`select 1` в health** — классика: «база отвечает — значит жива». Но здоровье продукта — это не соединение, а схема с данными.
- **Мягкая деградация в шапке** — правильно: шапка не должна ронять страницу из-за заглушки входа. Но `.catch(() => [])` превращает ошибку в *пустое значение*, и это уже нарушение правила «ошибки — значения»: ошибка перестаёт быть ошибкой и никому не видна.
- **Deploy после ручной правки базы** — интуитивно «переразвернуть». Но Deploy без изменений кода — это no-op для контейнера: entrypoint не выполняется, схема остаётся такой, какой её оставили.

Отдельно: в логе предыдущего старта entrypoint отработал (`▸ миграции` → `сид пропущен: база не пустая`). То есть это **не** обход entrypoint панелью, а ошибка процедуры — ручная операция без пересоздания контейнера.

## Как обнаружили

Руками, при проверке стенда 11.09: открыли страницы — пустые состояния везде, переключатель пользователя пуст, API 500. Ни healthcheck, ни мониторинг, ни `/health` этого не показали.

## Триггер на будущее

**Любая ручная операция с базой стенда завершается пересозданием контейнера приложения и проверкой глазами сквозного пути. Зелёный `/health` без проверки схемы не считается доказательством.**

Три следствия:

1. Health обязан спрашивать про **ключевую таблицу**, а не про соединение. `select 1 from plants limit 1`; 42P01 → 503 `{"db":"no-schema"}`.
2. Мягкая деградация не имеет права быть молчаливой: отказ базы пишется в лог уровнем **error** и показывается полосой в шапке. Страница не падает, но и не притворяется живой.
3. После ручных операций с базой — **Rebuild**, не Deploy. Записано в `DEPLOY.md`, раздел «Кто гарантирует схему», и в чек-лист «После деплоя, руками».

## Что изменили

- `/health` проверяет `plants`, различает `no-schema` и `down`, оба — 503. Пять тестов, три диверсии: откат к `select 1`, неразличение 42P01, 200 при пустой схеме — каждая роняет свой тест.
- Шапка: `Promise.allSettled` вместо `.catch(() => [])`; отказ логируется уровнем error и показывается полосой `role="alert"` под шапкой.
- `assistant/page.tsx`, `questions/[id]/page.tsx`: `currentUser().catch(() => null)` по образцу остальных страниц — экран ошибки вместо 500.
- `DEPLOY.md`: таблица ответов `/health`, раздел «Кто гарантирует схему» с правилом Rebuild, чек-лист «После деплоя, руками» из четырёх шагов.
