# 2026-09-10 — серверный импорт в файле, из которого клиент берёт константу

**Вес:** мелочь, поймана сборкой до коммита
**Где:** `src/lib/demo-user.ts`, шапка с переключателем пользователя

## Что произошло

Заглушка входа собрана одним файлом: там и `next/headers` для чтения cookie на сервере, и имя самой cookie, и словарь подписей ролей, и тип пользователя. Клиентский `user-switcher.tsx` импортировал оттуда имя cookie и словарь. Сборка отклонила: «You're importing a module that depends on `next/headers`. This API is only available in Server Components».

## Почему казалось правильным

Всё это — про одно и то же: демо-пользователя. Держать в одном файле выглядело как порядок, а не как ошибка. Но граница сервер/клиент проходит не по смыслу, а по тому, что физически попадёт в браузерный бандл: импорт одной строковой константы тянет за собой **весь модуль** со всеми его импортами.

## Как обнаружили

Первый же заход на страницу в dev-сервере: Build Error с трассой импортов — `demo-user.ts` → `header.tsx` → `layout.tsx`, и отдельно «Client Component Browser». Тайпчек и линтер это пропустили: для них импорт корректен.

## Триггер на будущее

Файл, из которого что-то импортирует клиентский компонент, не имеет права содержать `next/headers`, `next/cache`, драйвер базы или `fs` — даже если клиент берёт оттуда одну константу. Правило проще формулируется наоборот: **константы и типы, общие для сервера и клиента, кладём в отдельный файл без единого серверного импорта.**

Отдельный маркер: `"use client"` в компоненте и `import { ЧТО-ТО } from "@/lib/…"` в нём же — повод открыть этот `lib`-файл и посмотреть на его первую строку.

## Что изменили

`src/lib/demo-user.ts` разделён на два: `demo-user.ts` — имя cookie, тип и словарь ролей, без единого импорта из Next или базы; `demo-user.server.ts` — чтение cookie и запросы к базе. Клиент импортирует только первый. Отдельной проверки не завели: `next build` в `./check.sh` ловит это сам и падает.
