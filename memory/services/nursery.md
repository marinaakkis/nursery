# nursery

## Зачем

Онлайн-питомник растений: покупатель подбирает саженцы под свой участок, оформляет заказ и дальше ведёт «Мой сад» с календарём ухода и вопросами агроному. Внутри продукта работают два агента — подбора и консультанта, — действующие через инструменты продукта.

## Как устроен

- Репо: `nursery`
- Стек: Next.js (App Router) · TypeScript · Postgres · Drizzle · Vercel AI SDK. Один процесс приложения плюс Postgres. Решение и альтернативы — [decisions/0001-stack](../decisions/0001-stack.md)
- Данные: `plants`, `care_rules`, `batches`, `write_offs`, `demand_facts`, `cart_items`, `orders`, `order_items`, `order_reservations`, `order_status_history`, `delivery_slots`, `garden_plants`, `care_events`, `questions`, `messages`, `answer_drafts`, `users`, `notifications`. Хранилище — Postgres, миграции применяются при старте, демо-данные наливаются в пустую базу
- Модульный монолит: `catalog`, `orders`, `garden`, `consult`, `warehouse`. Модуль — папка с четырьмя экспортами: схема, сервисы, роуты, инструменты агента
- Внешние зависимости: провайдер языковой модели по HTTP — необязательный, за интерфейсом; вторая реализация детерминированная, работает без сети. Корпоративный SSO не подключён: роль выбирается переключателем пользователя, это заглушка и точка расширения

## Что отдаёт наружу

Все роуты обслуживает один диспетчер `src/app/api/[module]/[[...path]]/route.ts`; соглашение по путям — `/api/<module>/<action>`. Единый формат ответа `{ ok, data }` / `{ ok, error: { code, message } }`, коды 200 / 400 / 403 / 404 / 409 / 500.

Полный список эндпоинтов по модулям и формат ошибок — [`docs/architecture.md`](../../docs/architecture.md), раздел «Контракт API». Отдельного OpenAPI нет.

## Что из него можно взять в другой продукт

Три вещи, которые не про растения и переносятся целиком:

1. **Реестр инструментов агента.** Модуль объявляет `tools.ts`, реестр собирает инструменты в плоскую карту по имени и отдаёт агентскому циклу срез по роли пользователя. Инструмент вызывает ту же сервисную функцию, что и интерфейс, — своей логики поверх данных у агента нет. Добавление модуля не требует правок вне его папки; совпадение имён инструментов — ошибка на старте, а не тихая перезапись. Это готовый ответ на требование «агент действует через инструменты продукта».

2. **Провайдер языковой модели с детерминированной реализацией.** Один интерфейс, две реализации, переключение переменной окружения. Детерминированная разбирает запрос правилами и вызывает те же инструменты, поэтому продукт демонстрируется и тестируется без сети и без внешней модели. Отдельно полезен приём с намерением: если у модели нет tool-calling, она возвращает `{ tool, args }`, а вызывает инструмент наш код — остальная система об этом не знает.

3. **Паттерн human review.** Необратимое действие агента существует в данных как черновик и становится фактом только через отдельный эндпоинт одобрения: `answer_drafts.approved_at is null` — черновик, `POST /api/consult/approve` — единственный путь к сообщению покупателю. Тот же приём на заказе: агент доводит до корзины, заказ создаёт человек. Схема переносится на любой сценарий, где ИИ готовит, а человек отвечает.

Дополнительно переносимы карточка «что сделал и почему» (трасса вызовов инструментов, отрисованная как объяснение) и таблица токенов с набором из четырёх состояний экрана.

## Прежде чем лезть в код

- Настоящей авторизации нет: роль берётся из переключателя пользователя. Разграничение работает в интерфейсе и сервисном слое, но не защищает от намеренного обхода — см. «Вне скоупа» в `docs/spec.md` §10.
- Фоновых процессов и планировщиков в продукте нет: события ухода материализуются в момент действия, «просрочено» вычисляется при чтении.
- Резерв и списание берут партии `order by received_at, id ... for update`. Порядок блокировки обязан быть одинаковым во всех операциях с партиями, иначе взаимная блокировка.
- Факт неудовлетворённого спроса пишется отдельной транзакцией после отката основной — не переносить его внутрь транзакции заказа.
- Граф переходов статуса живёт в `orders/service.ts`, а не в схеме: прямой `update` статуса в обход сервиса поставит недопустимое значение.
- Оплата, уведомления, доставка и обработка фото — заглушки; каждая помечена на экране, где ею пользуются.
