# 0001 — Стек сервиса

## Что определяет выбор

_Свойства задачи: транзакционность / реалтайм / срок / деплой на стенд._

| Свойство задачи | Что нужно от стека | Что не подходит |
|---|---|---|
| Тяжёлый UI: 13 экранов, на каждом четыре состояния, адаптив до 375 px, работа с клавиатуры | Типизированный компонентный фронт, единая система токенов, серверный рендер для быстрого первого экрана | Шаблонизатор с ручной вёрсткой состояний; чистый SPA без SSR — первый экран каталога тяжелее нужного |
| Агент с tool-calling и потоковым выводом в UI: сообщения, вызовы инструментов и карточка «что сделал и почему» появляются по мере работы | Готовый агентный цикл со стримингом в интерфейс; описание инструмента лежит рядом с его реализацией | Стеки, где цикл «модель → инструмент → результат → модель» и его стриминг пишутся руками |
| Инварианты в БД: атомарный резерв остатка при гонке за последний экземпляр, вместимость слота, статусный граф заказа | Реляционная БД с транзакциями, уникальными индексами и CHECK; типобезопасный доступ с миграциями | Документные хранилища и in-memory без блокировок; ORM, прячущая транзакцию и блокировку строки |
| Деплой одним контейнером на стенд | Один процесс, multi-stage сборка, слушает 0.0.0.0, отдаёт `/health` | Раздельные фронт и бэк: два образа, CORS, вторая точка отказа |
| 1,5 дня, один человек | Один репозиторий, один язык на обе стороны, минимум связующего кода | Раскладки, где UI и API живут раздельно, а типы синхронизируются вручную |
| Точка расширения «модуль = папка»: модуль отдаёт схему, сервис-функции, роуты и те же функции как инструменты агента | Файловая маршрутизация и границы по папкам, чтобы структура читалась без онбординга | Фреймворки, где маршруты и регистрация собираются в конфигурациях вдали от кода модуля |
| Работа без языковой модели | Провайдер за интерфейсом; вторая реализация — детерминированные правила на тех же инструментах | Библиотеки, жёстко завязанные на одного поставщика модели без слоя абстракции |

## Что рассматривали

Кандидаты по слоям:

| Слой | Кандидаты | Решающее свойство |
|---|---|---|
| Приложение | Next.js App Router · FastAPI + React · NestJS + React · SvelteKit / Remix | Агентный цикл со стримингом + один процесс |
| БД | Postgres · SQLite | Конкурентная запись при гонке за остаток |
| Доступ к данным | Drizzle · Prisma · сырой SQL | Явные транзакции и миграции, типы из схемы |
| Деплой | Один контейнер + Postgres · два контейнера + Postgres | Число точек отказа на стенде |

1. **FastAPI + React** — привычный нам вариант.
   Не проходит по двум свойствам: два процесса вместо одного (лишний образ, CORS, вторая точка отказа) и агентный цикл с tool-calling и стримингом в UI, который здесь пишется вручную.
   По нашей оценке это около половины дня, а бюджет — полтора. Реляционная часть закрывается отлично, остальное — руками.

2. **NestJS + React** — тот же разрыв на два процесса.
   Дополнительно модульная церемония (модули, провайдеры, декораторы, DI-контейнер) окупается на длинной дистанции команды, а не на соло-задаче за полтора дня.
   Требование задания — чтобы новый разработчик подключился без онбординга: «папка с четырьмя экспортами» читается быстрее, чем регистрация в контейнере.

3. **SvelteKit / Remix** — по свойствам «один процесс», «файловая маршрутизация», «SSR» подходят не хуже.
   Отстают по свойству «агент с tool-calling»: готовых агентных примитивов и корпуса примеров меньше.
   Меньше корпус примеров — чаще ошибается агент-разработчик; на нашем сроке это прямой риск.

4. **SQLite вместо Postgres** — проще в деплое, один файл, нет второго сервиса; запись сериализует, так что простую гонку за последний экземпляр выдержит.
   Не проходит по другому: резерв идёт сразу по нескольким партиям в одной транзакции с блокировкой строк, а у SQLite блокировка только на всю базу; плюс файл на томе не посмотреть со стенда.
   Postgres — ещё и ожидаемый дефолт для нового разработчика. Взят отдельным сервисом; цена — второй контейнер в compose.

## Что выбрали и почему 🔶

_Если выбор отличается от привычного стека команды — сказать явно._

🔶 **Next.js (App Router) + TypeScript + Postgres + Drizzle + Vercel AI SDK.** Один контейнер приложения плюс Postgres.

Выбор осознанно отличается от привычного нам Python + React. Основание — не вкус, а две строки таблицы свойств: агентный цикл со стримингом в интерфейс здесь есть из коробки, а не пишется руками, и весь продукт остаётся одним процессом с файловой маршрутизацией, где модуль — это папка.

Остальные свойства — реляционные инварианты, типизация, деплой контейнером — закрываются любым из кандидатов. Поэтому решают именно эти два, и только они.

Postgres + Drizzle: транзакции, уникальные индексы и CHECK держат резерв остатка, вместимость слота и статусный граф. Миграции и типы выводятся из схемы, поэтому агент-разработчик не расходится с базой.

TypeScript один на обе стороны: типы модулей переиспользуются интерфейсом и инструментами агента без ручной синхронизации контрактов.

🔶 **Языковая модель — за интерфейсом провайдера, две реализации.**

Первая — внешняя модель по HTTP; все параметры подключения приходят из переменных окружения и в репозиторий не попадают.

Вторая — детерминированная: разбирает запрос правилами и вызывает те же самые инструменты продукта. Нужна для тестов (проверяемый результат без сети) и как рабочий режим демо.

Если у внешней модели нет tool-calling, она возвращает структурированное намерение — какой инструмент и с какими параметрами, — а вызывает инструмент наш код. Для продукта это тот же путь, меняется только источник намерения.

## Чем платим и что проверить

+ Один процесс, один язык, один репозиторий: меньше связующего кода и одна точка деплоя.
+ Агентный цикл и стриминг в UI готовые — освобождают около половины дня на UX и склад.
+ Реляционные инварианты закреплены в схеме, а не в коде приложения.
+ Детерминированный режим агентов делает демо независимым от доступности внешней модели.

− App Router и серверные компоненты требуют дисциплины: граница «сервер / клиент» не видна глазами, при небрежности состояние и запросы уезжают на клиент.
  _Проверить:_ ни один модуль доступа к БД не импортируется в клиентский компонент.
− Drizzle моложе Prisma, экосистема и корпус примеров меньше; часть вопросов решается чтением исходников, а не ответом из поиска.
  _Проверить:_ миграции применяются на чистой БД с нуля.
− Vercel AI SDK навязывает свои абстракции провайдера: смена поставщика модели — это адаптер под его интерфейс, а не свободный выбор.
  _Проверить:_ обе реализации провайдера подставляются переменной окружения и проходят один набор тестов инструментов.
− Один процесс означает отсутствие горизонтального разделения UI и агента: долгий запрос к модели занимает ресурсы того же приложения.
  _Проверить:_ на стенде агентский запрос не блокирует открытие каталога в соседней вкладке.
− Главный риск выбора — незнакомый App Router на сроке 1,5 дня.
  Купируется тем, что каталог, заказ и склад — обычные серверные страницы с формами, а вся нестандартная часть сосредоточена на агентском экране.
