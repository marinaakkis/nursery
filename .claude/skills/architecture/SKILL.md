# Architecture: решения и карточка сервиса

Роль на ассессменте — архитектор, агент — исполнитель. Человек принимает решения о структуре, данных и границах; агент их реализует. Решения записаны до кода и показаны на защите.

## Шаги

1. **Модель данных.** Сущности, ключевые поля, связи, инварианты (что не может быть нарушено — «одно место в одном сеансе продаётся один раз»). Инварианты — на уровне БД (constraint/unique), не только в коде.
2. **Границы и слои.** Одна схема: клиент → API → домен → хранилище → внешние сервисы. Для 1,5 дней — один сервис, монолит с чистыми слоями. Микросервисы не предлагать без свойства задачи, которое их требует.
3. **API-контракт.** Список эндпоинтов/экранов с входом-выходом и кодами ошибок. Именование единообразное.
4. **Точки human review.** Явно: где агент делает сам, а где остановиться и показать (схема данных, контракт API, UX ключевого сценария, всё про безопасность).
5. **Записать** решение в `memory/decisions/NNNN-slug.md` и завести паспорт `memory/services/<name>.md`.

## Шаблон ADR (`memory/decisions/NNNN-slug.md`)

```
# NNNN — <тема>
Дата · Статус · Принял
## Что определяет выбор     — свойство задачи / ограничение
## Что рассматривали        — 1) … 2) … 3) …
## Что выбрали и почему 🔶
## Чем платим и что проверить
```
Решения не переписываются — новое решение ссылается на старое.

Обязательные ADR: стек; модель данных и инварианты; обработка конкурентности (если есть); авторизация (если есть); что мокаем (оплата, внешние API).

## Паспорт сервиса (`memory/services/<name>.md`)

То, что на целевой платформе агент читает перед работой. Поля:

- Название, назначение (2 предложения), owner
- Стек и версии
- API: базовый URL, список эндпоинтов, ссылка на контракт/OpenAPI
- Данные: сущности, хранилище, миграции
- Зависимости: от чего зависит, кто зависит от него
- Переиспользуемые capabilities: что из сервиса можно взять в другой продукт (auth, компонент, справочник)
- Состояние: deployed / URL / версия
- Известные ограничения и долги

## Принцип

Если решение можно нарушить, не заметив, — оно закрепляется в коде или БД (constraint, тип, тест), а не в документе. Документ — для объяснения, код — для гарантии.
