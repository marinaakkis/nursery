# Defense: 30 минут

Оценивают: понимание платформенной идеи, архитектурное мышление, гибкость стека, UX/UI, качество работы с агентом. Приложение — повод для разговора, не предмет оценки.

## Тайминг

| Мин | Блок | Что показать |
|---|---|---|
| 0–3 | Задача и как её понял(а) | `spec.md`: роли, главный сценарий, 2–3 самых интересных развилки 🔶 |
| 3–7 | Стек и архитектура | ADR-001 (почему этот стек, от чего отказались), схема слоёв, главный инвариант и где он закреплён |
| 7–15 | Демо | главный сценарий + один edge-кейс вживую (гонка/ошибка/пустое состояние) по внешнему URL |
| 15–19 | Работа с агентом | `CLAUDE.md`, `memory/` (карточка, решения, ошибки), точки human review, verify-gate |
| 19–22 | UX | карта экранов, состояния, токены; что измерено и почему |
| 22–30 | Вопросы | см. ниже |

## Демо-правила

- Прогнать за час до защиты по внешнему URL; локальный запуск — запасной.
- Данные подготовлены заранее — не создавать на глазах.
- Edge-кейс показывать намеренно: «два параллельных запроса — второй получает 409».
- Если что-то сломано — сказать первым и показать запись в «известные проблемы».

## Вопросы, которые зададут

| Вопрос | На что опираться |
|---|---|
| Почему такой стек, а не привычный? | ADR-001: свойства задачи → требования → выбор. Явно: «привычный стек отвергнут, потому что …» |
| Как агент узнал правила и контекст? | `CLAUDE.md` + `memory/`: читает перед задачей, обновляет после |
| Что из сделанного переиспользуемо на платформе? | Карточка сервиса, раздел capabilities: auth, компоненты, справочники |
| Где вмешивались руками и почему? | Точки human review из `architecture` |
| Как проверяли, что работает? | `verify.md`: четыре состояния кода, уровни 0–5, тест на инвариант |
| Что бы изменили в платформе с 30 сервисами? | Единая память + автоматические gates; BIOCAD ID как общий auth; UX не унифицировать, дизайн-систему — да |
| Где агент ошибся? | `memory/mistakes/` — разборы с триггером и выросшие из них правила |
| Что не успели? | «Вне скоупа» из spec + «известные проблемы» из verify |

## Как это соотносится с их методикой (оценщик — автор AI Developer Kit)

Формулировка для защиты: «Кит читали, брали идеи, не файлы. Собрали свой минимальный контур под соло-задачу на 1,5 дня».

| Их идея | Наш аналог | Наше отличие |
|---|---|---|
| Общая память людей и агентов в git | `memory/` — решения, паспорта сервисов, разборы ошибок | без vault-хуков; обновляется правилом в `AGENTS.md` и проверкой в verify-gate |
| Правило держится на автоматике, не на сознательности | колонка «проверка» у каждого правила, `check.sh` | вместо 17 хуков — один скрипт, который реально успевается за день |
| «Готово» = живой прогон | четыре состояния кода + уровни 0–5 | «на стенде» = внешний URL |
| Ошибки агента копятся и превращаются в правила | `memory/mistakes/` с полем «Триггер» | своя структура записи |
| Прототип UI до кода с ревью | `ux-ui`: правила визуала → мокап → независимое ревью → код | без оркестрации субагентов |
| Один человек ведёт фичу от идеи до релиза | ровно формат ассессмента | — |

**Чего нет и почему** (сказать до вопроса): хуки на событиях сессии, inbox/daily/чекпоинты трекера, trunk-based без MR — командные механики, в соло-задаче на 1,5 дня им нечего проверять. Своё, чего у них нет: `stack-choice` как отдельный шаг с таблицей «свойство задачи → стек».

## Одна фраза, к которой сводится всё

«Показываю не приложение, а воспроизводимый процесс: ТЗ → решения → правила → код → runtime-проверка → память. Приложение — побочный продукт; процесс — то, что масштабируется на платформу».
