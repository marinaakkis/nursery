# UX/UI: интерфейс как решение, а не обвязка

Типичный провал вайбкодинга — рабочий бэк и фронт «из дефолтов библиотеки»: без состояний, без обратной связи, с одинаковыми кнопками. Этот скилл закрывает ровно это.

## Шаги

1. **Карта экранов из сценариев.** Каждый сценарий из `spec.md` → цепочка экранов. Главный сценарий должен проходиться минимальным числом действий — посчитать клики и записать.
2. **Состояния каждого экрана** (все пять): пусто · загрузка · данные · ошибка · успех. Для форм — ещё валидация «до отправки» и «после».
3. **Правила визуала** — зафиксировать до генерации в `docs/ui-rules.md`; без этого файла генерация UI не начинается: палитра (фон, поверхность, текст, акцент, ошибка, успех), максимум 2 шрифта, шкала отступов (4/8/16/24/32), радиусы, тени, запрещённые приёмы (градиентные герои, эмодзи-иконки, три primary на экран).
4. **Компонентный минимум**: кнопка (primary/secondary/disabled/loading), поле ввода с ошибкой, карточка, модалка/шит, тост, пустое состояние. Остальное — из них.
5. **Мокап → ревью → код.** Сначала статический HTML-мокап главного сценария; затем отдельный проход по чек-листу ниже вторым агентом (или свежей сессией), у которого право вернуть на доработку; только после прохода — рабочий фронт. Итерации по одному экрану, не «сверстай всё за раз».
6. **Прогнать чек-лист** на живом сервисе перед демо.

## Чек-лист качества

### Поток
- [ ] Главный сценарий проходится без чтения инструкции
- [ ] На каждом шаге понятно, что произошло и что делать дальше
- [ ] Необратимые действия (оплата, отмена) требуют подтверждения
- [ ] Ошибка говорит, что делать, а не «что-то пошло не так»
- [ ] Возврат назад не теряет введённое

### Состояния
- [ ] Пустые списки объясняют, почему пусто и что сделать
- [ ] Загрузка видна (скелетон/спиннер), кнопки блокируются на время запроса
- [ ] Успех подтверждён явно (экран/тост), а не исчезновением формы

### Визуал
- [ ] Иерархия: один primary на экран; заголовок > текст > вторичное
- [ ] Отступы по шкале, ничего не прижато к краю
- [ ] Контраст читаемый, размер шрифта ≥ 14px
- [ ] Один стиль иконок, одна палитра на всех экранах
- [ ] Адаптив: главный сценарий работает на 375px и на 1280px

### Доступность-минимум
- [ ] Интерактивные элементы доступны с клавиатуры
- [ ] У полей есть label, у иконок-кнопок — aria-label
- [ ] Фокус видим

## Что сказать на защите

- Как измерен главный сценарий (клики/шаги) и почему так
- Какие состояния спроектированы и где они видны
- Правила визуала заданы до генерации → консистентность управляема, а не случайна
- Мокап прошёл независимое ревью до кода — UI не «получился», а принят
- 🔶 UX намеренно не унифицирован под «корпоративный шаблон»: аудитория задачи отличается — ровно тезис платформы (единая дизайн-система, разный UX)
