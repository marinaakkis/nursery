# Intake: задача → ТЗ

Цель — за 30–40 минут получить `docs/spec.md`, по которому агент сгенерирует сервис без вопросов в процессе.

## Шаги

1. **Переписать задачу своими словами** в 3–5 предложениях: кто пользователь, что делает, какой результат. Если формулировка задания расходится с пересказом — это первый вопрос к организаторам.
2. **Роли.** Перечислить всех акторов, включая неявных (админ, система/крон, гость). Для каждой — что видит и что может.
3. **Сценарии.** Главный сценарий (happy path) шагами. Затем 3–7 альтернативных: ошибка, отмена, повтор, конкурентный доступ, пустое состояние.
4. **Edge-кейсы.** Прогнать чек-лист ниже, отметить применимые.
5. **Развилки.** Всё, что ТЗ не определяет, — решить самостоятельно, пометить 🔶, кратко обосновать. В тело ТЗ не попадают «TBD», «уточнить», «на усмотрение».
6. **Критерии приёмки.** Проверяемые утверждения формата «при X происходит Y». Минимум по одному на сценарий из п. 3.
7. **Границы.** Что явно не делаем (out of scope), чтобы не расползлось за 1,5 дня.

## Чек-лист edge-кейсов

- Двое делают одно действие одновременно (гонка за ресурс)
- Действие над уже несуществующим / изменённым объектом
- Повторная отправка (двойной клик, повтор запроса)
- Истечение времени (бронь, сессия, токен)
- Пустые списки, первый запуск без данных
- Невалидный / граничный ввод (0, отрицательное, очень длинное, unicode)
- Прошедшие даты, часовые пояса
- Права: пользователь пытается сделать чужое действие
- Частичный сбой (оплата прошла, запись не создалась)

## Формат `docs/spec.md`

```
# <Название сервиса>
## Суть (3–5 предложений)
## Роли
## Сценарии
### S1. <главный>
### S2… <альтернативные>
## Edge-кейсы (применимые из чек-листа + решение по каждому)
## Решения 🔶
| # | Развилка | Решение | Почему |
## Критерии приёмки
- [ ] AC1 …
## Вне скоупа
```

## Критерий готовности ТЗ

Разработчик (или агент), прочитав `spec.md`, не должен задать ни одного вопроса «а что делать, если…» по перечисленным сценариям. Если вопрос возможен — вернуться к п. 5.
