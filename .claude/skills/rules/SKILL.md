# Rules: правила для агента

Правило без проверки — совет. Каждое правило ниже имеет способ проверки (линтер, тест, gate, ручной чек-лист). При переносе в проект колонку «проверка» не удалять.

## Шаги

1. Взять базовый набор, убрать неприменимое, добавить специфичное из `docs/spec.md` и ADR.
2. Записать в `AGENTS.md` в корне проекта (IDE-нейтральное имя); `CLAUDE.md` — одна строка `@AGENTS.md`; для Cursor — `.cursorrules`. Объём — до 80 строк: длинные правила агент игнорирует.
3. Настроить автоматизируемые проверки: линтер, типизация, тесты, скрипт `check.sh`.
4. Вести `memory/mistakes/`: каждая ошибка агента → файл по `_template.md`; обязательное поле — «Триггер на будущее».

## Базовый набор правил

### Контекст
| Правило | Проверка |
|---|---|
| Перед задачей прочитать `docs/spec.md`, `memory/decisions/`, `memory/services/` | Агент ссылается на ADR в плане |
| Не менять модель данных и API-контракт без остановки и вопроса | Ручной review диффа схемы |
| После изменений обновить карточку сервиса и ADR **в той же сессии** | Чек-лист в verify-gate |
| Значение, которое пришло не от человека (порт, имя сервиса, URL) — проверить фактом, не подставлять «по аналогии» | Агент показывает, откуда взял |

### Код
| Правило | Проверка |
|---|---|
| Типизация обязательна (TypeScript strict / type hints + mypy/pyright) | Тайпчек в `check.sh` |
| Линтер и форматтер настроены, проходят чисто | `check.sh` |
| Слои не смешиваются: HTTP-слой без SQL, домен без HTTP | Review структуры папок |
| Инварианты — в БД (unique, FK, check), не только в коде | Миграции содержат constraints |
| Миграции для любой смены схемы, без ручных правок БД | Папка migrations, применяется с нуля |
| Один способ обработки ошибок, единый формат ответа об ошибке | Тест на 400/404/409 |

### Безопасность (InfoSec gate)
| Правило | Проверка |
|---|---|
| Секреты только в env, в репо — `.env.example` | grep по паттернам ключей, `.gitignore` |
| Валидация всех входных данных на границе API | Тест невалидного ввода |
| Параметризованные запросы / ORM, никакого string-SQL | grep |
| Проверка прав на каждом действии, не только на UI | Тест «чужое действие → 403» |
| Логи без персональных данных и токенов | Review логов на демо |
| Зависимости только из официальных реестров | Review lock-файла |

### Тесты
| Правило | Проверка |
|---|---|
| Тест на каждый критерий приёмки из spec.md | Список AC ↔ список тестов |
| Обязательный тест на главный инвариант (гонка, дубль) | Есть в `check.sh` |
| Тесты зелёные до заявления «готово» | `check.sh` |

### Поведение агента
| Правило | Проверка |
|---|---|
| Сначала план на 5–10 строк, потом код | Видно в диалоге |
| «Готово» = сервис запущен и сценарий прогнан (см. verify-gate) | Лог/скриншот |
| При ошибке — разбор в `memory/mistakes/` с полем «Триггер», а не молчаливый ретрай | Папка растёт |
| Отчёт о готовности — только через четыре состояния из verify-gate | Нет слова «готово» без них |
| Не расширять скоуп: всё, что не в spec.md, — предложить, не делать | Diff соответствует задаче |

## Шаблон ошибки

`memory/mistakes/_template.md`: что произошло · почему казалось правильным · как обнаружили · **триггер на будущее** · что изменили.
