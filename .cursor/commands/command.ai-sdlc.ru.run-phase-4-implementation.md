# Команда: Фаза 4 — IMPLEMENTATION

Запуск фазы реализации по апрувленному плану с multi-agent командой и автоматическими гейтами качества.
Применяет `skill.ai-sdlc.ru.phase-4-implementation`.

**Аргументы:** `$ARGUMENTS` — `<task-name> [mode=manual|auto|review]`

Примеры:
- `feature-auth-refactor`
- `feature-auth-refactor mode=auto`
- `feature-auth-refactor mode=2` (алиас)
- Невалидно: `mode=auto feature-auth-refactor` (режим указывается только вторым аргументом)

---

## Предварительные условия

1. Убедиться, что файл `docs/dev-requests/dev-request.r-<nnn>.<system-request-name>/dev-process-plan.r-<nnn>.<system-process-plan-name>.md` существует и поля `Расположение требований` и `Расположение проекта` заполнены. Если файл отсутствует или поля пусты — остановиться и предложить пользователю: «Пожалуйста, запустите `command.ai-sdlc.ru.run-phase-1-research` для создания dev-process-plan, или заполните поля `Расположение требований` и `Расположение проекта` вручную.»
2. Определить целевой `dev-request`. Если в репозитории найдено несколько `docs/dev-requests/dev-request.r-*`, запросить у пользователя явный выбор целевого `dev-request` до продолжения.
3. Убедиться, что апрувлены:
   - `docs/dev-requests/dev-request.r-<nnn>.<system-request-name>/dev-planning/dev-plan.r-<nnn>.<system-dev-plan-name>/dev-plan.r-<nnn>.<system-dev-plan-name>.md`
   - Все `docs/dev-requests/dev-request.r-<nnn>.<system-request-name>/dev-planning/dev-plan.r-<nnn>.<system-dev-plan-name>/dev-task.r-<nnn>.t-<nnn>.<system-dev-task-name>.md`
   - В `docs/dev-requests/dev-request.r-<nnn>.<system-request-name>/dev-process-plan.r-<nnn>.<system-process-plan-name>.md` Фаза 3 имеет статус "Завершена"
4. **Стартовый контекст и изоляция (режим manual/review):** Предложить пользователю очистить контекст разговора перед запуском (`/clear` или новый чат). При согласии — перезапустить команду в чистом контексте. При отказе — продолжить.

   **Для всех режимов — обязательно:**
   - При старте читать ТОЛЬКО: dev-task файлы + `design/` (C4, Sequence, ADR) + dev-process-plan (включая раздел «Паттерны ошибок реализации»).
   - Не читать дополнительные файлы, пока dev-task не содержит явную ссылку на путь.
   - История предыдущих разговоров — не источник данных; использовать только файлы.
5. Прочитать dev-plan и все dev-task-файлы.
6. Определить режим исполнения: `manual` / `auto` / `review` (по умолчанию — `review`). Числовые алиасы: `1=manual`, `2=auto`, `3=review`. Если режим явно не указан в `$ARGUMENTS` — использовать `review`.
7. Определить стандарты стека (применить нужные):
   - Backend .NET/C#: `skill.dev.ru.dotnet-csharp-standards`
   - Frontend TS/React: `skill.dev.ru.frontend-ts-react-standards`
   - REST API: `skill.integration.ru.api-rest-standards`
8. Обновить `docs/dev-requests/dev-request.r-<nnn>.<system-request-name>/dev-process-plan.r-<nnn>.<system-process-plan-name>.md`: установить "Текущая фаза" = IMPLEMENTATION, установить `Режим = <режим>` в разделе «Фаза 4».

## Состав агентной команды

| Агент | Роль | Ограничение |
|---|---|---|
| **Lead** | Читает план, назначает задачи, запускает ревью, агрегирует результаты | Никогда не пишет код |
| **Implementer** | Пишет код строго по заданию Lead | Не проводит ревью |
| **Reviewer: Build+Test** | Запускает билд и тесты, репортит ошибки (файл+строка) | Не правит код |
| **Reviewer: Architecture** | Проверяет соответствие C4/Sequence, DDD, слоям, стандартам | Не правит код |
| **Reviewer: Security** | OWASP Top 10, hardcode, инъекции, открытые endpoints | Не правит код |
| **Reviewer: Plan Compliance** | Все шаги phase выполнены, решение не упрощено | Не правит код |

---

## Stop-conditions и эскалация

1. При конфликте между ревьюерами (один требует изменение, другой считает изменение вне scope) Lead обязан остановить выполнение и эскалировать решение пользователю. Продолжать реализацию до ответа пользователя нельзя.
2. Для каждого `dev-task` допустимо не более 3 итераций цикла Implementer ↔ Reviewer. После 3-й неуспешной итерации Lead формирует краткий отчёт о зацикливании (причины, блокеры, предложенный next step) и эскалирует пользователю.
3. При ANY FAIL переход к следующему `dev-task` запрещён до явного закрытия всех блокирующих замечаний.

## Цикл выполнения (для каждого dev-task)

### Шаг 1: Lead назначает задачу Implementer

Lead читает dev-task-файл и передаёт Implementer:
- Цель dev-task
- Конкретные шаги реализации
- Acceptance criteria
- Ссылки на дизайн-артефакты (C4, Sequence, ADR) из `docs/dev-requests/dev-request.r-<nnn>.<system-request-name>/design/`
- Применимые стандарты стека

### Шаг 2: Implementer пишет код

Реализует код строго по заданию. При наличии интеграций применяет `rule.integration.ru.integration-passport-and-reliability-gate` (timeout, retry, circuit breaker).

### Шаг 3: Lead запускает всех 4 ревьюеров ПАРАЛЛЕЛЬНО

Каждый ревьюер получает: изменённые файлы + своё задание.

**Reviewer: Build+Test** — запустить билд и все тесты. При FAIL: указать файл + строку + сообщение об ошибке.

**Reviewer: Architecture** — проверить:
- Соответствие C4/Sequence диаграммам
- Доменная модель корректна (нет прямых DB-запросов в доменных сущностях)
- Слои не нарушены
- DRY, SOLID, стандарты стека соблюдены
- Cyclomatic/cognitive complexity в норме

**Reviewer: Security** — проверить (применить `skill.security.en.security-review`):
- Нет конкатенации строк в SQL (только параметризованные запросы)
- Нет hardcoded credentials, API keys, паролей
- Все входные параметры валидируются
- Auth-check на защищённых endpoints
- Нет логирования sensitive-данных
- XSS, CSRF, IDOR, SQL injection — OWASP Top 10

**Reviewer: Plan Compliance** — проверить:
- Все шаги dev-task-файла выполнены
- Решение не упрощено (AI не выкинул функционал)
- Соответствие дизайн-артефактам
- Нет изменений за пределами scope текущего dev-task (нет незапланированных «попутных улучшений»)
- Весь выявленный техдолг вне scope — зафиксирован в разделе «Итоги фазы» dev-process-plan, не внесён в код

### Шаг 4: Lead агрегирует результаты

- **ALL PASS** → перейти к следующему dev-task (или к финальному ревью, если это последний dev-task)
- **ANY FAIL** → собрать все замечания, сгруппировать по ревьюеру, вернуть Implementer с конкретным списком (файл + строка + проблема). Повторить с шага 2, но не более 3 итераций для одного dev-task. При превышении лимита — эскалация пользователю.
- **FAIL на итерации 2+** → Lead дополнительно фиксирует паттерн ошибки в раздел **«Паттерны ошибок реализации»** dev-process-plan (dev-task, итерация, критерий, причина, исправление). При старте следующего dev-task Lead читает этот раздел.

### Шаг 5: Предложение коммита после dev-task

После PASS всех гейтов:
- **Режим manual/review:** **предложить** пользователю создать коммит (без автосоздания).
- **Режим auto/plan-review:** не предлагать коммит на уровне отдельного dev-task; предложение возможно только после прохождения всего процесса.

Не создавать коммит без явного подтверждения.

Формат предложения:
```
Dev-task r-<nnn>.t-<nnn> прошёл все гейты. Предлагаю создать коммит:
  Сообщение: "<функциональное описание изменения>"
  Файлы: <список изменённых файлов>
  (Файлы планирования и дизайна в коммит не включаются)
Создать коммит? [да / нет / изменить сообщение]
```

## Финальный Cross-Phase Review (после всех dev-task)

Запустить всех 4 ревьюеров по полному набору изменений:
- Проверить консистентность между реализованными dev-task
- Нет дублирования, нет противоречий
- Итоговый security-check всего изменённого кода

---

## Обновление dev-plan после реализации

После финального ревью обновить `docs/dev-requests/dev-request.r-<nnn>.<system-request-name>/dev-process-plan.r-<nnn>.<system-process-plan-name>.md`: отметить все шаги чеклиста фазы 4 (включая Cross-Phase Review), заполнить раздел "Итоги фазы" (результаты всех dev-task, отклонения от дизайна, технический долг), установить статус = "Завершена", дату завершения.

## Завершение

Вывести summary:
- Список реализованных dev-task и результаты гейтов
- Итоги Cross-Phase Review
- Отклонения от дизайна (если были)
- Технический долг (если есть)

**ГЕЙТ (режим manual/review — с согласованием инженера):**

Агент автоматически проставляет в разделе «Фаза 4» dev-process-plan: `Статус = Завершена`, `Дата завершения = <сегодня>`.

Если коммиты для отдельных dev-task ещё не созданы — предложить создать их сейчас (по одному, с подтверждением каждого).

Переход к Фазе 5 заблокирован до перехода фазы в статус **Согласовано**.

Согласование — два варианта:
- **А — самостоятельно:** инженер открывает dev-process-plan и вручную устанавливает в разделе «Фаза 4»: `Статус = Согласовано`, `Дата согласования = <YYYY-MM-DD>`.
- **Б — через агента:** инженер отправляет подтверждение (например: «согласовано», «апрув», «approve»); агент проставляет `Статус = Согласовано` и `Дата согласования = <сегодня>`.

**ГЕЙТ (режим auto/plan-review):** Агент автоматически устанавливает `Статус = Завершена` и переходит к Фазе 5 без ожидания.

После фиксации статуса **Согласовано** и создания коммитов запустите `command.ai-sdlc.ru.run-phase-5-release-gate`.
