# Генерация архитектурных артефактов из спецификации

Универсальная команда для AI-агентов: **создать или обновить** набор архитектурной документации на основе файла-источника (specification / technical description / architecture brief). Команда переносима между репозиториями.

## Профиль переносимости (обязательно)

- **Базовое переносимое ядро (всегда):** анализ спецификации, фиксация пробелов/рисков, выбор релевантных архитектурных артефактов, соблюдение консистентности между документами.
- **Репозиторный профиль (по правилам текущего проекта):** конкретные пути, шаблоны именования и обязательные наборы артефактов (например, `docs/requirements/*`, `docs/api-requirements/*`, `docs/adr-log/*`, `docs/dds-log/*`).
- Если репозиторный профиль отсутствует или конфликтует с входной задачей, использовать переносимое ядро и явно сообщить пользователю о принятых допущениях.

---

## Как вызывать

`$ARGUMENTS`:

- `<spec-path>` — обязательный путь к исходной спецификации (абсолютный или относительный от корня репозитория).
- Путь с пробелами передается в кавычках: `"<spec-path with spaces>"`.

Валидные примеры:

- `docs/specs/system-spec.md`
- `".input/source specs/architecture brief.md"`
- `C:\work\project\docs\spec.md`

Невалидные примеры:

- `docs/specs/ system-spec.md` (пробел внутри пути без кавычек)
- `spec.md extra.md` (несколько путей вместо одного аргумента)

Если путь не указан:

1. Найти наиболее вероятный source-of-truth файл спецификации.
2. Если найден ровно один кандидат — использовать его.
3. Если кандидатов несколько или ни одного — уточнить у пользователя и не продолжать генерацию до ответа.

**Каталог вывода по умолчанию:** `docs/` рядом со спецификацией (в том же модуле).  
Если пользователь явно просит другой каталог `docs/`, использовать его и отразить выбор в `docs/README.md`.

## Порядок работы (обязательно)

### 0. Применить профильные скиллы

Перед генерацией/обновлением артефактов открыть и применить:

- `.agents/skills/skill.arch.ru.c4-diagrams/SKILL.md`
- `.agents/skills/skill.arch.ru.sequence-diagrams/SKILL.md`
- `.agents/skills/skill.arch.ru.workflow-diagrams/SKILL.md`
- `.agents/skills/skill.arch.ru.bpmn-diagrams/SKILL.md`
- `.agents/skills/skill.arch.ru.dfd-diagrams/SKILL.md`
- `.agents/skills/skill.arch.en.architecture-md-artifact/SKILL.md`

При необходимости открыть соответствующие `reference.md`.

### 1. Прочитать спецификацию

Извлечь:

- цель системы и границы;
- основные функциональные возможности;
- стек и технологические ограничения;
- интеграции и интерфейсы;
- нефункциональные требования и ограничения эксплуатации.

### 2. Выполнить критический разбор

Проверить и зафиксировать:

- неоднозначности терминов и трактовок;
- пробелы (MVP-границы, объемы, форматы, безопасность, отказоустойчивость);
- риски (стоимость, лимиты API, PII, compliance, ops);
- противоречия между частями спецификации.
- подходящий тип process-диаграммы для текущей задачи (`sd.*`, `wf.*` или `bpmn.*`).

Фиксировать сжато и структурированно, без дословного дублирования исходника.

### 3. Создать/обновить структуру документации

Сформировать артефакты по матрице обязательности (не создавать фиктивные документы):

| Категория | Артефакт | Статус | Условие |
|---|---|---|---|
| Индекс документации | `docs/README.md` | обязателен | Всегда |
| Архитектурный агрегатор | `docs/architecture.md` | обязателен | Всегда |
| Требования | `docs/requirements/furps.<...>.md`, `docs/requirements/fr.<...>.md`, `docs/requirements/nfr.<...>.md` | обязателен | Если спецификация содержит требования уровня системы/модуля |
| API-требования | `docs/api-requirements/api.external.<system-name>.md`, `docs/api-requirements/api.<project-name>.<domain-or-service-or-controller-name>.md` | опционален | Только если есть API-контракты или интеграционные интерфейсы |
| ADR log | `docs/adr-log/adr.<nnn>.<kebab-case-title>.md` | опционален | Если выявлены архитектурные решения с альтернативами/компромиссами |
| DDS log | `docs/dds-log/dds.<nnn>.<kebab-case-title>.md` | опционален | Если есть значимые design-решения реализации |
| C4 диаграммы | `docs/c4-diagrams/` | обязателен | Если спецификация описывает архитектуру компонентов/контейнеров |
| Process диаграммы | `docs/process-diagrams/dfd.<diagram-title>.<ext>`, `docs/process-diagrams/sd.<diagram-title>.<ext>`, `docs/process-diagrams/wf.<title>.<ext>`, `docs/process-diagrams/bpmn.<title>.<ext>` | опционален | Если есть процессы/потоки данных/сценарии выполнения |

Для требований и API-контрактов применяй единый стиль именования в рамках модуля и строгие шаблоны из скиллов: `furps.*`, `fr.*`, `nfr.*`, `api.external.*`, `api.<project-name>.*`.  
Для остальных документов и диаграмм используй зафиксированные шаблоны репозитория (`architecture.md`, `README.md`, `c1/c2/c3/c4d.*`, `sd.*`, `wf.*`, `bpmn.*`).  
Сценарии и runtime-потоки фиксируются в `architecture.md` и в process-диаграммах (`sd.*`, `wf.*`, `bpmn.*`).

Если для категории не выполнено условие из таблицы, артефакт не создавать и явно зафиксировать причину в итоговом отчете.

### 4. Применить стандарты диаграмм

- C4 диаграммы (`C1`, `C2`, `C3`, optional dynamic) размещать в `docs/c4-diagrams/`.
- Process диаграммы (`DFD`, `sequence`, `workflow`, `BPMN`) размещать в `docs/process-diagrams/`.
- Именование:
  - C4: `<c4-level>.<diagram-title>.<ext>` (`c1`, `c2`, `c3`, `c4d`);
  - Data Flow Diagram: `dfd.<diagram-title>.<ext>`;
  - Sequence: `sd.<diagram-title>.<ext>`;
  - BPMN: `bpmn.<title>.<ext>`;
  - Workflow: `wf.<title>.<ext>`.
- Минимум для первичной генерации process-артефактов: **минимум 1 релевантная диаграмма** из `dfd.*` / `sd.*` / `wf.*` / `bpmn.*` (не обязательно все типы сразу).
- Выбор типа process-диаграммы:
  - для потоков данных между компонентами (хранение, трансформация, передача) — DFD (`dfd.*`);
  - для простой утилиты/технического потока чаще достаточно sequence (`sd.*`);
  - для бизнес-процесса с ролями, ветвлениями и регламентом предпочитай BPMN (`bpmn.*`);
  - для orchestration/saga и межшагового потока состояния используй workflow (`wf.*`), BPMN (`bpmn.*`) или sequence (`sd.*`) в зависимости от цели описания.
- Если по спецификации неясно, какой тип диаграммы нужен, **обязательно уточни у пользователя до генерации**.

### 5. Согласованность

- Термины, роли и названия сущностей согласованы между требованиями, C4 и процессными документами.
- `architecture.md` содержит актуальную карту ссылок и каталог компонентов.
- Трассировка решений (ADR/DDS) и компонентов не противоречит диаграммам.
- Если UI отсутствует, это явно отражено в архитектурной декомпозиции.

### 6. Ограничения и безопасность

- Не добавлять секреты/ключи/токены в документацию.
- В `docs/` не добавлять ссылки на `.input/` (если иное явно не разрешено правилами проекта).
- Писать только относительные ссылки внутри `docs/`.

### 7. Формат итогового ответа (обязательно)

После завершения команды выдай результат строго в формате:

```md
## Результат генерации архитектурных артефактов

### 1) Создано/обновлено
- <path> — <кратко что сделано>

### 2) Пропущено (с причиной)
- <артефакт/категория> — <почему не создавался>

### 3) Риски и пробелы
- <риск или пробел из шага 2>

### 4) Вопросы к пользователю
- <вопрос, если нужен ответ для продолжения>

### 5) Следующие шаги
- <что рекомендуется сделать после текущего прогона>
```

## Ориентир по содержанию

### `docs/requirements/*.md`

- функциональные и нефункциональные требования;
- ограничения дизайна/реализации/интерфейсов;
- раздел рисков, пробелов и открытых вопросов.

### `docs/api-requirements/*.md`

- внешние и внутренние API-контракты;
- таблицы операций, форматов, ошибок, лимитов;
- способы аутентификации и авторизации (authn/authz): схема, токены/claims/scopes/roles, ограничения доступа;
- строгие имена файлов:
  - `api.external.<system-name>.md`;
  - `api.<project-name>.<domain-or-service-or-controller-name>.md`.

### `docs/architecture.md`

- единый индекс архитектурных артефактов;
- агрегированный каталог C1/C2/C3;
- C4-описание (контекст/контейнеры/компоненты) и трассировка к элементам;
- правила консистентности между описанием и диаграммами;
- сценарии и runtime-поток (включая error branching) с ссылками на `sd.*`, `wf.*`, `bpmn.*`.

### `docs/README.md`

- краткая аннотация модуля;
- таблица ссылок на все ключевые документы и каталоги диаграмм.
- раздел `Output Artifacts Specification` с нормативом по выходным файлам (вместо отдельного файла `output-artifacts-specification.md`).

## После генерации (рекомендуется)

### Доработка первоначальных требований

По результатам формирования документации предложить пользователю причесать исходный файл-источник (specification / technical description / architecture brief):

- устранить обнаруженные неоднозначности и пробелы (зафиксированные в шаге 2);
- привести структуру и терминологию в соответствие с итоговыми артефактами;
- убрать дублирование и противоречия.

После доработки скопировать улучшенный файл в `docs/requirements/source/` — это сохраняет первоначальный источник требований внутри `docs/` и делает его доступным для трассировки.

### Закрытие пробелов требований

Для закрытия оставшихся пробелов использовать скилл интервьюера:

- `.agents/skills/skill.arch.ru.architecture-requirements-interviewer/SKILL.md`
- `.agents/skills/skill.arch.ru.architecture-requirements-interviewer/reference.md`

Черновики раундов вести в `.input/proposals/<theme>-proposal.md`; перенос в опрос/документацию выполнять после явного сигнала пользователя о завершении раунда.

## Версия команды

Команда должна оставаться переносимой: не фиксируй здесь продукт-специфичные пути, названия модулей или жесткие имена документов, если это не требуется правилами конкретного репозитория.
