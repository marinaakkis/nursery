# Команда: Актуализация основной документации `docs/` по итогам dev-request

Актуализирует **постоянную** документацию `docs/` глобально значимыми design-артефактами завершённого dev-request (C4 C2/C3, межсервисные контракты, ERD, ключевые ADR/DDR, глобальные process-диаграммы). Сначала формирует **план изменений** для согласования, затем — после подтверждения пользователя — выполняет обновление.

> Авторинг делегируется `skill.arch.en.architecture-md-artifact` (раздел «Actualization targets») и диаграммным скиллам `skill.arch.ru.*-diagrams`. Нормативная обязанность предлагать актуализацию — `rule.ai-sdlc.ru.docs-actualization-after-dev-request`.

**Аргументы:** `$ARGUMENTS`

| Опция | Назначение |
|---|---|
| `--request r-<nnn>` | Конкретный dev-request (по умолчанию — `currentDevRequestNumber` из `.project-metadata.local.json`; если несколько незавершённых — спросить) |
| `--dry-run` | Только сформировать план изменений, без обновления `docs/` |
| `--help` | Справка |

---

## Инварианты

- В `docs/` актуализируется **только глобально значимое**: системные C2/C3, межсервисные контракты, ERD, ключевые ADR/DDR, глобальные process-диаграммы. Локальные детали одной задачи (частный C3, SD сценария) — нет.
- Актуализация = **синтез/копия** в `docs/`, **без ссылок** в `docs/dev-requests/**` (`rule.governance.ru.docs-no-dev-requests-links`).
- Выполнять **до** `command.ai-sdlc.ru.publish-dev-requests-docs --with-clean` (иначе исходные design-артефакты будут удалены).
- Идемпотентно: повторный прогон обновляет те же целевые артефакты (между `<!-- AUTOGEN:start -->…<!-- AUTOGEN:end -->` или в чётко ограниченной секции), без слепой перезаписи.
- Команда **не выполняет** git-операций; коммит предлагается отдельно (после, в run-all / Фазе 5).

---

## Шаги исполнения

### Шаг 1. Определить dev-request
Определить целевой `r-<nnn>` (из `--request` или `currentDevRequestNumber`). Если незавершённых несколько и не задан `--request` — спросить пользователя.

### Шаг 2. Сформировать план изменений
Создать файл **`docs/dev-requests/dev-request.r-<nnn>.<name>/docs-actualization-plan.r-<nnn>.<name>.md`** по шаблону-скелету `.agents/skills/skill.arch.en.architecture-md-artifact/template.docs-actualization-plan.md`. Агент заполняет всё, включая **дефолтные** `Решение`: глобально значимые → `✅ Принять`, локальные кандидаты → `❌ Отклонить`; пользователь проверяет и правит.

**Шапка:** dev-request id, дата, профиль `docs` источника, якорь на `docs/architecture.md`, сводный риск, легенда «Решение».

**Таблица глобально значимых артефактов** (по умолчанию переносятся):

| # | Артефакт | Источник (путь от корня репо) | Целевой артефакт | Действие | Решение | Статус |
|---|---|---|---|---|---|---|

- `Действие` ∈ `Create` / `Update` / `Deprecate`:
  - **Create** — целевого глобального дока/раздела нет → новый файл/раздел;
  - **Update** — целевой есть → внести дельту (вкл. частичное удаление внутри дока);
  - **Deprecate** — целевой неактуален целиком (сервис/возможность удалены) → пометить «устарело»/удалить.
- `Решение`: `✅ Принять` / `❌ Отклонить` / `⏳ Запланировать` / `✎ Редактировать` (агент проставляет дефолт по группе — см. выше; пользователь правит).
- `Статус`: `Запланировано` / `Выполнено` / `Пропущено`.

**Таблица локальных кандидатов** (по умолчанию НЕ переносятся; перенос — по `Решение = ✅ Принять`):

| # | Локальный артефакт | Источник (путь от корня репо) | Возможный целевой артефакт | Уже в `docs/`? | Решение | Статус |
|---|---|---|---|---|---|---|

- «Уже в `docs/`?» = `да`/`нет`. Если `да` — строку перенести в таблицу глобально значимых (дефолт `✅ Принять`).
- Дефолт `Решение` локального кандидата — `❌ Отклонить`; пользователь меняет на `✅ Принять` для переноса.

**Блок «Переход» под каждой строкой** (кроме Deprecate-без-замены):
- **Сейчас (AS-IS):** текущее состояние целевого артефакта (`отсутствует` / кратко);
- **Станет (TO-BE):** целевое состояние;
- **Дельта:** конкретные правки (узлы/связи C4, строки ERD, поля контракта, новый ADR) — отдельно от TO-BE;
- **Почему:** какое изменение кода / межсервисной связи / решение это отражает;
- **Формат/профиль:** диаграмма/таблица в `docs/`; нужно ли развернуть `compact`-таблицу источника в диаграмму;
- **Зона обновления:** `целиком` / `между AUTOGEN-маркерами` / `ручной merge-review` + риск перезаписи.

### Шаг 3. Согласование
После создания плана **предупредить** пользователя: проверить план и при необходимости отредактировать колонку `Решение` **прямо в файле**; затем дождаться выбора:

```
План актуализации создан: <путь>.
Значения по-умолчанию проставлены: глобально значимые → ✅ Принять, локальные кандидаты → ❌ Отклонить.
Проверьте план и при необходимости отредактируйте колонку «Решение» в файле, затем:
  [Применить] — выполнить актуализацию по проставленным «Решение»
  [Отмена]    — пропустить актуализацию; процесс продолжается дальше
```

- **«Применить»** — перечитать (возможно отредактированный) план и перейти к Шагу 4 (исполнение по `Решение`).
- **«Отмена»** (или флаг `--dry-run`) — не применять: гейт пропускается, процесс идёт дальше; зафиксировать в dev-process-plan.
- Правки вносятся пользователем **непосредственно в файл плана** — интерактивный опрос по строкам не требуется.

### Шаг 4. Исполнение (по строкам с `✅ Принять`)
Для каждой принятой строки применить `Действие` к `docs/` через `skill.arch.en.architecture-md-artifact` (+ диаграммные скиллы при разворачивании таблиц в диаграммы):
- `❌ Отклонить` — пропустить (`Статус = Пропущено`);
- `⏳ Запланировать` — создать **самодостаточный** future-task в `docs/dev-requests/future-tasks/` (вне папки dev-request — переживает публикацию `--with-clean`) по `rule.governance.ru.future-tasks`. **Встроить полное описание изменения**: целевой артефакт + весь блок «Переход» (AS-IS / TO-BE / Дельта / Почему / Формат / Зона обновления). **Без ссылок на dev-request** (он может быть перенесён в хранилище и удалён) — future-task должен быть понятен сам по себе. `docs/` не трогать;
- `✎ Редактировать` — перепланировать строку (вернуться к Шагу 2 для неё).
Обновить `docs/architecture.md` (индекс) и колонку `Статус` в плане.

### Шаг 5. Итог
Сообщить: сколько артефактов создано/обновлено/устарело/запланировано; обновлён ли `architecture.md`. Напомнить, что коммит и публикация — отдельные шаги (коммит предлагается после; публикация — `command.ai-sdlc.ru.publish-dev-requests-docs`, после неё `--with-clean` безопасен).
