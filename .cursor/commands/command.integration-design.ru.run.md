# Команда: Проектирование и согласование интеграции — RUN

Сквозной запуск процесса проектирования и согласования межсервисной интеграции: Концепт → Проектирование → Согласование. Точка входа облегчённого семейства `integration-design` (по-фазных команд нет; процесс реализован тремя скиллами).

**Аргументы:** `$ARGUMENTS` — описание/цель интеграции, ID тикета или путь к файлу со сведениями. Опционально: `mode=auto|plan-review` (по умолчанию `plan-review`); `docs=compact|full` (по умолчанию `compact`).

Применяет последовательно:
- Фаза 1 — `skill.integration-design.ru.phase-1-concept`
- Фаза 2 — `skill.integration-design.ru.phase-2-architecture`
- Фаза 3 — `skill.integration-design.ru.phase-3-approval`

---

## Принципы исполнения

- **Накопитель состояния:** `integration-request-plan` создаётся в фазе 1 и обновляется на каждой фазе (рантайм-папка `docs/integration-requests/integration-request.i-<nnn>.<name>/`).
- **Table-first:** агент работает по таблицам; диаграммы (C2/Sequence/окружения) формируются по запросу пользователя (mermaid по умолчанию).
- **Изоляция контекста между фазами:** следующая фаза читает только артефакты предыдущей из файловой системы.
- **Ручное согласование (фаза 3):** заявки в Service Desk создаёт и ведёт пользователь; агент готовит лёгкие заявки и фиксирует статусы. Агент не создаёт тикеты и не меняет их статус в Service Desk.
- **Git/PR:** не выполняются автоматически — только по явному подтверждению пользователя.
- **DLP:** при заполнении документации не вписывай реальные секреты и ПДн (только факт наличия); конфиденциальные имена систем/организаций — только в рабочем экземпляре, в примерах — плейсхолдеры.

---

## Режимы

| Режим | Поведение |
|---|---|
| `plan-review` (по умолчанию) | Фаза 1 → подтверждение концепта пользователем → Фаза 2 → **пауза-подтверждение** проектирования → Фаза 3 (ручное согласование: Отдел архитектуры → Отдел информационной безопасности → Отдел инфраструктурного развития) |
| `auto` | Фазы 1–2 без пауз (с дефолтными допущениями); фаза 3 в любом случае ручная (зависит от пользователя) |

> Фаза 3 всегда требует участия пользователя (создание заявок в Service Desk), независимо от режима.

---

## Pre-flight

- [ ] Из `$ARGUMENTS` понятна цель интеграции и хотя бы две системы-участника (иначе — задать уточняющие вопросы).
- [ ] Определён `i-<nnn>` (следующий свободный номер в `docs/integration-requests/`).
- [ ] Область определена (какие системы, контур).

При нехватке сведений — собрать недостающее чеклистом фазы 1, не блокируя старт.

---

## Шаги выполнения

### Фаза 1 — Концепт
1. Применить `skill.integration-design.ru.phase-1-concept`.
2. Создать рантайм-папку и `integration-request-plan`; присвоить `i-<nnn>`.
3. Заполнить «Описание», компоненты/акторы/связи (минимум для C1), FURPS+, `user-input-checklist`.
4. При нехватке сведений — предложить C1-схему и перечень уточняющих вопросов для владельцев систем и профильных отделов; зафиксировать открытые вопросы.
5. `plan-review`: получить подтверждение пользователя на переход к проектированию.

### Фаза 2 — Проектирование
6. Применить `skill.integration-design.ru.phase-2-architecture` (читать на старте `integration-request-plan` + артефакты фазы 1).
7. Заполнить карточку проекта, тех-таблицу связей + надёжность, окружения, эндпоинты, модель данных (ПДн/КТ), маппинг (если у шлюза есть трансформация контрактов), аутентификацию/авторизацию, журнал связанных заявок.
8. По запросу — сформировать C2 / sequence / диаграмму окружений (mermaid).
9. Обновить накопитель (итоги, открытые вопросы).
10. **PAUSE (plan-review):** показать сводку артефактов фазы 2 и открытые вопросы; получить подтверждение на переход к согласованию.

### Фаза 3 — Согласование
11. Применить `skill.integration-design.ru.phase-3-approval`.
12. Подготовить лёгкую заявку для Отдела архитектуры (обзор/цель/процесс/ссылки на документацию).
13. Передать пользователю для создания тикета в Service Desk; зафиксировать в журнале связанных заявок и накопителе.
14. Подготовить заявку для Отдела информационной безопасности (обязательна, параллельно с Отделом архитектуры) и, при необходимости, для Отдела инфраструктурного развития.
15. Отражать статусы по мере подтверждения пользователем.
16. Когда все необходимые заявки согласованы — зафиксировать завершение процесса (Текущая фаза = DONE) и отметить готовность к разработке.
