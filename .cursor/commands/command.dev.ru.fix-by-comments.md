# Команда: исправление по комментариям разработчика

Прочитай указанный файл (или файлы из `$ARGUMENTS`), найди все комментарии-указания на исправления,
подготовь и опиши предлагаемые изменения, затем **жди подтверждения** — ничего не меняй без команды пользователя.

## Аргументы

`$ARGUMENTS` — путь к файлу или список путей через пробел.  
Если путь не передан — спроси, для какого файла выполнять команду.

---

## Шаг 1: Прочитать файл

Прочитай каждый указанный файл целиком. Не пропускай фрагменты.

---

## Шаг 2: Найти комментарии-указания

Собери **все** комментарии, которые выражают намерение изменить код.  
Критерий: комментарий описывает **проблему** или **желаемое поведение**, а не поясняет уже существующую логику.

Маркеры (независимо от языка файла):

| Маркер | Примеры |
|--------|---------|
| `TODO` | `// TODO:`, `# TODO:`, `<!-- TODO: -->` |
| `FIXME` | `// FIXME:`, `# FIXME:` |
| `HACK` | `// HACK:` — обходное решение, требующее замены |
| `REVIEW` | `// REVIEW:` — требует анализа или переработки |
| Произвольные | `// Надо переименовать`, `// здесь должен быть`, `// заменить на`, `// убрать`, `// вынести в ...` |

Пропускай: docstring-объяснения логики, license-заголовки, закомментированный код без явного указания действия.

Если комментарии не найдены — сообщи: `Комментариев-указаний не найдено. Уточни намерение.` и останови выполнение.

---

## Шаг 3: Подготовить исправления

Для каждого найденного комментария:

1. Определи **намерение** — что именно нужно сделать.
2. Если намерение неоднозначно — зафиксируй вопрос (не угадывай).
3. Подготовь **конкретное изменение кода** в формате `diff`.
4. Оцени **риск**:
   - `low` — переименование, форматирование, извлечение константы
   - `medium` — изменение логики, сигнатуры, перемещение кода
   - `high` — изменение контракта, удаление, структурный рефакторинг
5. Укажи, требует ли изменение **тестов** или **обновления документации**.

---

## Шаг 4: Вывести отчёт

Выведи отчёт строго в формате ниже. Не вноси никаких изменений в файл на этом шаге.

```
## Найдено исправлений: N  [файл: path/to/file.cs]

---

### [1] Строка XX — <краткое описание намерения>

**Комментарий:** `// TODO: ...`

**Предлагаемое изменение:**
<описание прозой — что именно будет изменено и почему>

**Diff:**
```diff
- старый код
+ новый код
```

**Риск:** low | medium | high  
**Требует тестов:** да / нет  
**Требует обновления документации:** да / нет

---

### [2] ...
```

Если для какого-либо пункта намерение **неоднозначно** — вместо `diff` укажи:
> ❓ **Уточни:** <вопрос, без которого нельзя подготовить корректное исправление>

---

## Шаг 5: Ожидать подтверждения

После вывода отчёта выведи ровно следующее:

```
Исправления подготовлены. Введи команду:
  apply all       — применить все
  apply 1, 3      — применить выбранные (по номеру)
  skip            — отменить, не вносить изменений
```

**Жди ввода пользователя. Ничего не меняй до получения явной команды.**

---

## Шаг 6: Применить подтверждённые исправления

После получения `apply ...`:

1. Применяй изменения **по одному**, строго по номерам из подтверждения.
2. После каждого изменения **удали** соответствующий комментарий-указание из кода — он выполнен.  
   Исключение: если комментарий несёт смысловую нагрузку за пределами задачи (например, поясняет обходное решение для бага библиотеки) — оставь с пометкой `// NOTE (архитектурное):`.
3. Не трогай код за пределами контекста каждого отдельного исправления.

## Ограничения

- Структурный рефакторинг (`high`-риск, затрагивающий несколько слоёв) — **только** при явном `CONFIRM: REWRITE` от пользователя.
- Не агрегируй несколько `medium/high`-изменений в один шаг — применяй последовательно.
- Соблюдай `rule.dev.ru.no-silent-rewrite-legacy-code.mdc`: хирургические изменения, без попутной «уборки».
