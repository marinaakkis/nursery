# Команда: Полный цикл — RUN ALL

Исполнение всех 5 фаз процесса разработки последовательно без ожидания апрувов между фазами.
Гейты между фазами выполняются самим агентом (автоматическая самопроверка через phase-команды).
При переходе между фазами агент **очищает рабочий контекст**: следующая фаза читает только артефакты предыдущей из файловой системы.
Git-операции (коммиты, PR) выполняются только по явному подтверждению пользователя — агент только предлагает, никогда не создаёт автоматически.

**Аргументы:** `$ARGUMENTS` — описание задачи / ID тикета / путь к тикет-файлу. Опционально: `mode=auto|plan-review` (по умолчанию — `plan-review`); `docs=compact|full` (по умолчанию — `compact`).

> **Параметр `docs` (объём документации, ортогонален `mode`):** определяет профиль артефактов каждой фазы.
> - **`compact`** — артефакты в плотной машинно-ориентированной форме для ИИ-агента: структурные таблицы и списки вместо диаграмм там, где они применяются (фаза 2); без нарративных пояснений, без обновления `docs/architecture.md`, без человеко-ориентированных секций отчётов. Незыблемо в обоих профилях: dev-process-plan, dev-task, тест-стратегия, API-контракты, smoke-отчёт.
> - **`full`** — человеко-читаемый профиль: дополнительно Mermaid-диаграммы (C4/DFD/Sequence/…), нарративные Design Report и отчёты, обновление `docs/architecture.md`.
>
> Точный состав по фазам — `reference.artifacts.{compact,full}.md в каталоге соответствующего phase-скилла (skill.ai-sdlc.ru.phase-{1,2,3,5}-*/)`. Невалидное значение — запросить корректный ввод и остановиться.

---

## Режимы работы run-all

| Режим | Поведение |
|---|---|
| `auto` (`2`) | Все 5 фаз выполняются полностью автоматически; гейты — самопроверка агента |
| `plan-review` _(по умолчанию)_ | Фазы 1–3 автоматически → PLAN-REVIEW PAUSE (обсуждение, правки, подтверждение) → Фазы 4–5 автоматически → Post-Release Feedback Loop |

В обоих режимах после Фазы 5 агент переходит в **Post-Release Feedback Loop** и остаётся в контексте разработки до явного завершения.

> Режимы `manual` и `review` в `run-all` не используются: они предполагают ручной апрув каждой фазы. Для итерационного запуска используйте phase-команды напрямую.

> **Статус «Согласовано» в этих режимах не используется.** Агент переходит к следующей фазе автоматически по статусу **Завершена**.

При FAIL автоматического гейта — агент выполняет `RETRY` (до 2 попыток), при повторном FAIL останавливается, сообщает о проблеме и ждёт инструкций.

---

## Управление контекстом

При переходе между фазами агент **обязан изолировать контекст**:

- Следующая фаза стартует, прочитав **только артефакты предыдущей фазы** из файловой системы
- Дополнительные файлы читаются только при наличии явной ссылки в артефактах
- История разговора предыдущих фаз **не является** источником данных — только файлы

| Фаза | Читает при старте |
|---|---|
| RESEARCH | `$ARGUMENTS` (описание задачи) |
| DESIGN | `research.r-<nnn>.<system-request-name>.md` + dev-process-plan (вкл. «Открытые вопросы») |
| PLANNING | `design/` (все артефакты) + `research.r-...md` + dev-process-plan |
| IMPLEMENTATION | dev-task файлы + `design/` (C4, Sequence, ADR) + dev-process-plan (вкл. «Паттерны ошибок») |
| RELEASE GATE | dev-process-plan + dev-task файлы + `design/testing/dev-testing.r-<nnn>.strategy.md` |

---

## Обязательная фиксация артефактов по завершению каждой фазы

Переход между фазами разрешён только после:

1. Все выходные артефакты текущей фазы созданы в файловой системе (не в черновом ответе).
2. Артефакты проверены: непустые, соответствуют требованиям.
3. В dev-process-plan обновлены: чеклист, ссылки на артефакты, `Статус фазы = Завершена`, `Дата завершения`, `Текущая фаза = <следующая>`.

**ЗАПРЕЩЕНО:** переносить создание артефактов фаз 1/2/3 на более поздний этап.

---

## Политика RETRY для автоматических гейтов

- Если phase-команда возвращает FAIL — агент выполняет корректировку и повторный запуск.
- Максимум: 2 попытки `RETRY` на одну фазу или один dev-task.
- После каждого `RETRY` — фиксировать, что исправлено и что остаётся FAIL.
- После 2 неуспешных попыток — остановить цикл, эскалировать пользователю.

**Шаблон FAIL-отчёта (обязательный):**
```
✗ FAIL GATE
  Фаза: <RESEARCH|DESIGN|PLANNING|IMPLEMENTATION|RELEASE GATE>
  Критерий: <текст критерия>
  Артефакт: <путь или "не создан">
  Попытка: <n>/<2>
  Что исправлено: <кратко>
  Что нужно от пользователя: <следующая команда или решение>
```

## Шаги выполнения

### Pre-flight: Проверка запроса

Выполняется до создания каких-либо файлов.

**Формальная проверка (блокирующая):**
- [ ] Тип задачи определяем из `$ARGUMENTS` (Фича / Баг / Рефакторинг)
- [ ] Путь к требованиям указан или проект идентифицируется из контекста
- [ ] Нет явных противоречий в формулировке

**Смысловая проверка (блокирующая):**
- [ ] Запрос достаточно детален для исследования (не «сделай лучше», «улучши код»)
- [ ] Понятна область изменений (фронт / бэк / инфра / конкретный модуль)
- [ ] Нет скрытых предположений, обнуляющих смысл исследования

При любом FAIL — сформулировать список уточняющих вопросов, ждать ответа пользователя, повторить валидацию, только после PASS переходить к Инициализации.

### Инициализация

1. Прочитать задачу из `$ARGUMENTS`; определить `mode` (по умолчанию `plan-review`) и `docs` (по умолчанию `compact`)
2. Определить `<task-name>` (kebab-case), `r-<nnn>` (следующий свободный номер в `docs/dev-requests/`)
3. Определить тип задачи: Фича / Баг / Рефакторинг
4. Если в `$ARGUMENTS` не переданы путь(и) к требованиям/проекту и не найден существующий `dev-process-plan` для текущего `r-<nnn>`:
   - "Где находятся требования к задаче? (папка, файл или ссылка)"
   - "Где расположен код проекта или как назвать новый проект?"
5. Создать папку `docs/dev-requests/dev-request.r-<nnn>.<system-request-name>/`
   Обновить `currentDevRequestNumber = "r-<nnn>"` в `.project-metadata.local.json`.
6. Создать `dev-process-plan.r-<nnn>.<system-process-plan-name>.md` по шаблону `.agents/skills/skill.ai-sdlc.ru.phase-1-research/template.process-plan.md`
7. Заполнить поля `Расположение требований` и `Расположение проекта`; установить `Режим = <mode>` в каждом разделе фаз (1–5); установить `Объём документации = <docs>` в разделе «Мета». Передавать `docs` в каждую phase-команду наравне с `mode`.
8. Сообщить: "Запуск полного цикла для задачи `<task-name>`. Режим: `<mode>`. Объём документации: `<docs>`. Dev-process-plan: `docs/dev-requests/dev-request.r-<nnn>.<system-request-name>/dev-process-plan.r-<nnn>.<system-process-plan-name>.md`. Git-коммиты и PR будут только предлагаться — создание только по явному подтверждению."

### PLAN-REVIEW PAUSE (только `mode=plan-review`)

После завершения фазы 3 и до запуска фазы 4:

#### 1. Саммари по фазам 1–3

```
══════════════════════════════════════════
PLAN-REVIEW PAUSE: план готов, ожидаю подтверждения
══════════════════════════════════════════
RESEARCH  ✓  Затронутых компонентов: <N>
DESIGN    ✓  Артефактов: <список>
PLANNING  ✓  Dev-task: <N>, Тест-кейсов: <N>

Ключевые архитектурные решения:
<1-3 пункта>

Риски реализации:
<список или "не выявлены">
```

#### 2. Открытые вопросы агента

Вывести все строки из раздела **«Открытые вопросы»** dev-process-plan со статусом «Открыт».
Если открытых вопросов нет — явно указать: "Открытых вопросов нет."

#### 3. Вопросы пользователя

Дать пользователю возможность задать свои вопросы и ответить на них.
Продолжать диалог до тех пор, пока пользователь не завершит обсуждение.

#### 4. Правки по итогам обсуждения

После завершения диалога — уточнить у пользователя уровень необходимых правок:

```
Требуются ли правки в артефактах?
  [A] Нет правок — всё в порядке
  [B] Правки в артефактах (без перезапуска фаз)
  [C] Перезапуск части фазы (уточнить: какой артефакт)
  [D] Перезапуск целой фазы (уточнить: какой: 1 / 2 / 3)
```

- При **A** — перейти к подтверждению (п. 5).
- При **B** — внести правки в указанные артефакты, обновить dev-process-plan, перейти к подтверждению.
- При **C** — уточнить конкретный артефакт/шаг, выполнить перезапуск части, вернуться к п. 2.
- При **D** — уточнить номер фазы (1, 2 или 3), выполнить полный перезапуск этой фазы и всех последующих до 3, вернуться к п. 2. ⚠ Предупредить: перезапуск фазы N аннулирует все артефакты фаз N…3.

#### 5. Подтверждение запуска реализации

После закрытия всех открытых вопросов:

```
══════════════════════════════════════════
Все открытые вопросы закрыты. Готов к запуску реализации.
Выберите действие:
  [Запустить реализацию]   — начать Фазы 4–5
  [Продолжить обсуждение]  — задать ещё вопросы
  [Перезапустить процесс]  — повторить с фазы (1 / 2 / 3)
══════════════════════════════════════════
```

При **"Запустить реализацию"** → продолжить с фазы 4.
При **"Продолжить обсуждение"** → вернуться к п. 3.
При **"Перезапустить процесс"** → уточнить с какой фазы (1/2/3), выполнить перезапуск, вернуться к п. 2.

### Фаза 4: IMPLEMENTATION

Запустить `command.ai-sdlc.ru.run-phase-4-implementation` с `mode=auto` для каждого dev-task.
Гейты (Build, Tests, Linters, Architecture, Security, Plan Compliance) выполняются phase-командой.

Коммиты не предлагать после каждого dev-task; предложение коммита/PR — только после завершения всего цикла и только по явному подтверждению пользователя.

Прогресс-отчёт после каждого dev-task:
```
✓ Dev-task p-<nnn>.t-<nnn>/<total>: <название>
  Гейты: Build ✓ | Tests ✓ | Linters ✓ | Architecture ✓ | Security ✓ | Plan ✓
```

После финального Cross-Phase Review: установить `Статус фазы 4 = Завершена`, `Текущая фаза = RELEASE GATE`.

```
✓ IMPLEMENTATION завершён
  Dev-task выполнено: <N>/<N>
  Cross-Phase Review: PASS
→ Переход к Release Gate...
```

### Фаза 5: Release Gate

Запустить `command.ai-sdlc.ru.run-phase-5-release-gate` с `mode=auto`.
Гейт выполняется phase-командой.

После прохождения smoke-теста создать PR-описание. **Предложение коммита/PR — после шага «Post-Release Gate: актуализация `docs/`»** (ниже), чтобы изменения `docs/` вошли в коммит. Ничего не создавать автоматически — только при явном подтверждении пользователя.

После успешного завершения релиз-гейта: установить `Статус фазы 5 = Завершена`, `Текущая фаза = DONE`.

---

### Post-Release Gate: актуализация `docs/`

Обязательный шаг (`rule.ai-sdlc.ru.docs-actualization-after-dev-request`). Выполняется после Фазы 5 и **до** предложения коммита/PR.

1. Предложить пользователю выбор:
   - **`[Актуализировать документацию]`** — запустить `command.ai-sdlc.ru.actualize-main-docs --request r-<nnn>`: сформировать план `docs-actualization-plan.r-<nnn>.<system-request-name>.md`, согласовать (план создаётся с дефолтами `Решение`: значимые → `Принять`, локальные → `Отклонить`; пользователь правит план при необходимости и выбирает «Применить», либо «Отмена» — пропустить), затем обновить `docs/` синтезом (без ссылок в `dev-requests/**`).
   - **`[Пропустить]`** — не актуализировать документацию сейчас (зафиксировать решение в dev-process-plan).
2. После шага (актуализация выполнена или пропущена) — **предложить коммит** (включая изменения `docs/`), затем при необходимости PR. Создание — только по явному подтверждению.
3. Актуализацию выполнять **до** `command.ai-sdlc.ru.publish-dev-requests-docs --with-clean` (иначе исходные design-артефакты будут удалены).

```
✓ Release Gate завершён
  Актуализация документации: <актуализировано N артефактов | пропущено>
  Коммит/PR: предложить (после актуализации docs/)
```

### Post-Release Feedback Loop

После завершения Фазы 5 агент **не закрывает контекст разработки**, а переходит в режим пост-релизных исправлений.

#### Уведомление об активации

```
══════════════════════════════════════════
✓ Полный цикл завершён. Перехожу в Post-Release Feedback.
  Сообщайте об ошибках, запросах на доработку или задавайте вопросы.
  Для завершения напишите: "готово" / "done" / "закрыть".
══════════════════════════════════════════
```

#### Обработка каждого сообщения пользователя

**Шаг 1: Классификация**

| Тип | Признаки |
|---|---|
| **Bug** | Что-то не работает, ошибка, неожиданное поведение |
| **Improvement** | Доработка существующей функциональности, улучшение UX |
| **Docs** | Документация неполная или неточная |
| **Architecture** | Изменение требует пересмотра дизайна |
| **Out-of-scope** | Новая функция, не связанная с текущей задачей |

**Шаг 2: Оценка объёма**

| Объём | Критерии | Путь |
|---|---|---|
| **Мелкое** | Изменение 1–3 файлов, нет изменения интерфейсов, < 30 мин | Hotfix-задача → реализация → гейты |
| **Среднее** | Затронуто несколько компонентов, интерфейсы меняются, 30 мин – 2 ч | Краткая design-нота → hotfix-задача → реализация → гейты |
| **Крупное** | Архитектурные изменения, новые компоненты, новые интеграции | Эскалация: "Это требует нового цикла. Запустить новый dev-request?" |
| **Out-of-scope** | Совершенно новая функция | Эскалация: предложить создать отдельный тикет |

**Шаг 3: Фиксация в dev-process-plan**

Добавить строку в раздел **«Дополнительные исправления»** dev-process-plan:
```
| <N> | <описание проблемы> | <Bug/Improvement/Docs> | <Мелкое/Среднее> | В работе | dev-task.r-<nnn>.hotfix-<nnn>.<name>.md | <дата> |
```

**Шаг 4: Создание hotfix-задачи** (для Мелкого и Среднего)

Создать файл `docs/dev-requests/dev-request.r-<nnn>.<system-request-name>/dev-planning/dev-plan.r-<nnn>.<system-dev-plan-name>/dev-task.r-<nnn>.hotfix-<nnn>.<system-hotfix-name>.md` по структуре:

```markdown
# Dev-task hotfix-<nnn>: <краткое описание>

## Проблема
<что именно не работает / что нужно улучшить>

## Причина (если известна)
<анализ корневой причины>

## Шаги исправления
1. <конкретный шаг>
2. ...

## Тест-кейс
| Сценарий | До исправления | После исправления |
|---|---|---|

## Acceptance Criteria
- [ ] Проблема воспроизводится до исправления
- [ ] После исправления не воспроизводится
- [ ] Билд: PASS
- [ ] Тесты: PASS
- [ ] Security: PASS

## Затронутые файлы
| Файл | Тип изменения |
|---|---|
```

Для **Среднего** объёма — перед hotfix-задачей создать краткую design-ноту:
`docs/dev-requests/dev-request.r-<nnn>.<system-request-name>/design/hotfix-design-note.hotfix-<nnn>.<name>.md`
с разделами: Проблема / Текущее поведение / Целевое поведение / Затронутые компоненты / Решение.

**Шаг 5: Реализация с гейтами**

Запустить упрощённый цикл (аналог Фазы 4 для одной задачи):
- Implementer реализует строго по hotfix-задаче
- Reviewer: Build+Test, Architecture, Security, Plan Compliance — параллельно
- При FAIL: до 2 итераций RETRY, затем эскалация
- Нет изменений за пределами scope hotfix-задачи (scope expansion запрещён)
- Техдолг вне scope — фиксировать в «Дополнительные исправления», не в код

**Шаг 6: Закрытие задачи**

- Обновить статус в таблице «Дополнительные исправления»: `Закрыта`, `Дата закрытия`
- Предложить коммит пользователю (не создавать автоматически)
- Вывести:
```
✓ Hotfix-<nnn> закрыт: <описание>
  Гейты: Build ✓ | Tests ✓ | Architecture ✓ | Security ✓ | Plan ✓
  Продолжайте сообщать о проблемах или напишите "готово" для завершения.
```

#### Завершение Post-Release Feedback Loop

При получении "готово" / "done" / "закрыть" / "завершить":

- Проверить: все строки таблицы «Дополнительные исправления» со статусом «Закрыта» или явно помечены как отложенные
- Обновить dev-process-plan: заполнить итоговую строку Post-Release
- Предложить финальный коммит со всеми hotfix-изменениями
