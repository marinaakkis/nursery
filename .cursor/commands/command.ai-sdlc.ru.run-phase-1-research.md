# Команда: Фаза 1 — RESEARCH

Запуск фазы исследования кодовой базы для задачи разработки.
Применяет `skill.ai-sdlc.ru.phase-1-research`.

**Аргументы:** `$ARGUMENTS` — `<task-input> [mode=manual|auto|review] [docs=compact|full]`

Где:
- `<task-input>` — описание задачи / ID тикета / путь к тикет-файлу
- `mode` — режим гейтов (`manual`, `auto`, `review`), опциональный; числовые алиасы `1=manual`, `2=auto`, `3=review`; если не указан, используется `review`
- `docs` — объём документации (`compact`/`full`), опциональный, ортогонален `mode`; если не указан — брать `Объём документации` из dev-process-plan, иначе `compact`. Профиль конечных артефактов фазы — `.agents/skills/skill.ai-sdlc.ru.phase-1-research/reference.artifacts.<docs>.md`

Валидные примеры:
- `PROJ-1427: добавить экспорт отчёта mode=auto`
- `.input/tickets/PROJ-1427.md`
- `bug: 500 на /api/orders mode=manual`
- `PROJ-1427 mode=2` (алиас)

Невалидные примеры:
- `mode=plan-review PROJ-1427` (режим `plan-review` допустим только в `run-all`, не в phase-командах)
- `PROJ-1427 mode=two` (режим должен быть `manual|auto|review` или числом `1|2|3`)

## Предварительные условия

1. Прочитать и распарсить `$ARGUMENTS` по формату `<task-input> [mode=1|2|3]`.
2. Определить режим исполнения: `manual` / `auto` / `review` (по умолчанию — `review`). Числовые алиасы: `1=manual`, `2=auto`, `3=review`. Если `mode` отсутствует, использовать `review`. Если указан невалидный `mode` — запросить корректный ввод у пользователя и остановиться.
3. Определить тип задачи: Фича / Баг / Рефакторинг.
4. Определить `<request-name>` — короткое kebab-case имя задачи запроса на разработку или изменение (например: `user-avatar-upload`).
5. `<system-request-name>` = `<request-name>` (kebab-case, совпадает с именем задачи).
6. `<system-process-plan-name>` = `<system-request-name>` (используется тот же slug для имени process-plan). Пример: `dev-process-plan.r-001.user-avatar-upload.md`.
7. Выбрать целевой `dev-request`:
   - если найден ровно один незавершённый `docs/dev-requests/dev-request.r-<nnn>.<system-request-name>/` — продолжить в нём;
   - если найдено несколько незавершённых кандидатов — обязательно спросить пользователя, какой `r-<nnn>` использовать;
   - если кандидатов нет — определить `r-<nnn>` как следующий свободный номер в `docs/dev-requests/` (например: `r-001`).
8. **Стартовый контекст и изоляция (режим manual/review):** Предложить пользователю очистить контекст разговора перед запуском (`/clear` или новый чат). При согласии — перезапустить команду в чистом контексте. При отказе — продолжить.

   **Для всех режимов — обязательно:**
   - При старте читать ТОЛЬКО: `$ARGUMENTS` (описание задачи).
   - Не читать дополнительные файлы, пока research не покажет конкретную ссылку на путь.
   - История предыдущих разговоров — не источник данных; использовать только файлы.
9. Создать папку `docs/dev-requests/dev-request.r-<nnn>.<system-request-name>/` (если не существует).
   При создании новой папки — обновить `currentDevRequestNumber = "r-<nnn>"` в `.project-metadata.local.json`.
   Если `docs/dev-requests/dev-request.r-<nnn>.<system-request-name>/dev-process-plan.r-<nnn>.<system-process-plan-name>.md` не существует — опросить пользователя:
   - "Где находятся требования к задаче? (папка, файл или ссылка)"
   - "Где расположен код проекта или как назвать новый проект?"
   Затем создать файл по шаблону `.agents/skills/skill.ai-sdlc.ru.phase-1-research/template.process-plan.md`, заполнить раздел Мета (включая `Расположение требований` и `Расположение проекта`), установить "Текущая фаза" = RESEARCH, установить `Режим = <режим>` в разделе «Фаза 1».
   Обязательный минимум полей при первичном создании:
   - `ID запроса` (`r-<nnn>`) и `<system-request-name>` в заголовке/мете;
   - `Расположение требований`;
   - `Расположение проекта`;
   - `Текущая фаза = RESEARCH`;
   - в разделе «Фаза 1»: `Режим = <режим>`, `Статус = В работе`.
   Если файл уже существует — прочитать его и проверить, что `Расположение требований` и `Расположение проекта` заполнены; если нет — запросить у пользователя.

## Шаги выполнения

### Шаг 1: Декомпозиция задачи (Lead-агент)

Определить направления исследования исходя из типа задачи:

| Тип | Фокус sub-агентов |
|---|---|
| Фича | Все компоненты, которых коснётся фича; текущие интерфейсы; доменные модели |
| Баг | Как воспроизвести; какой код исполняется на пути к ошибке; соседние зависимости |
| Рефакторинг | Текущие паттерны; кто зависит от изменяемого кода; тесты |

### Шаг 2: Параллельный запуск sub-агентов

Запустить одновременно три sub-агента. Каждый работает в своём контекстном окне и отвечает только на свой вопрос:

**Sub-агент: Архитектура**
- Что изучает: слои, структуру, компоненты, зависимости между модулями в затронутой области
- Выход: список файлов с ролью каждого, слои и их взаимодействие

**Sub-агент: Паттерны и доменные модели**
- Что изучает: сущности, их поля и инварианты, используемые паттерны (репозитории, сервисы, handlers, фабрики)
- Выход: описание доменных моделей и паттернов с ссылками на файлы и строки

**Sub-агент: Интеграции и внешние зависимости**
- Что изучает: вызовы внешних сервисов, API, БД, очереди — всё, что выходит за границы модуля
- Выход: список интеграций с файлами, интерфейсами и описанием

### Шаг 3: Агрегация (Lead-агент)

Собрать результаты sub-агентов. Сформировать единый research-документ.

**СТОП-ПРАВИЛО:** В research-документ включаются ТОЛЬКО факты AS-IS.
Запрещено: советы, предложения рефакторинга, оценки качества, слова "стоит", "лучше", "нужно исправить".

### Шаг 4: Создание артефактов

1. Создать `docs/dev-requests/dev-request.r-<nnn>.<system-request-name>/research.r-<nnn>.<system-request-name>.md` по шаблону из `skill.ai-sdlc.ru.phase-1-research/reference.md`.
   Если кодовая база отсутствует (новый проект) — раздел `## Архитектурный контекст` пропустить, в `## Затронутые компоненты` указать `N/A` для всех полей «Ссылка на файл» и «Строки».

2. Обновить `docs/dev-requests/dev-request.r-<nnn>.<system-request-name>/dev-process-plan.r-<nnn>.<system-process-plan-name>.md`: отметить выполненные шаги чеклиста фазы 1, добавить ссылки на артефакты, заполнить раздел "Итоги фазы", установить статус = "Завершена", дату завершения.

3. Если в ходе исследования выявлены неопределённости или противоречия — добавить каждый вопрос строкой в раздел **«Открытые вопросы»** dev-process-plan (Источник = RESEARCH, Статус = Открыт).

### Шаг 5: Самопроверка перед гейтом

- [ ] Research-документ содержит только факты — нет советов и мнений
- [ ] Найдены все компоненты с конкретными ссылками (файл + строки)
- [ ] Граничные условия задокументированы
- [ ] Явно перечислено, что НЕ затрагивается
- [ ] Раздел "Итоги фазы" в dev-process-plan заполнен

**ГЕЙТ (режим manual/review — с согласованием инженера):**

Агент автоматически проставляет в разделе «Фаза 1» dev-process-plan: `Статус = Завершена`, `Дата завершения = <сегодня>`.

Переход к Фазе 2 заблокирован до перехода фазы в статус **Согласовано**.

Согласование — два варианта:
- **А — самостоятельно:** инженер открывает dev-process-plan и вручную устанавливает в разделе «Фаза 1»: `Статус = Согласовано`, `Дата согласования = <YYYY-MM-DD>`.
- **Б — через агента:** инженер отправляет подтверждение (например: «согласовано», «апрув», «approve»); агент проставляет `Статус = Согласовано` и `Дата согласования = <сегодня>`.

**ГЕЙТ (режим auto/plan-review):** Агент автоматически устанавливает `Статус = Завершена` и переходит к Фазе 2 без ожидания.

После фиксации статуса **Согласовано** запустите `command.ai-sdlc.ru.run-phase-2-design`.
