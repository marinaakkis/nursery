# Reference: C1-концепт межсервисной интеграции

Как сформировать верхнеуровневую схему контекста (C1) на фазе «Концепт». Назначение C1 — дать пользователю артефакт для согласования и сбора недостающих технических сведений с владельцами систем и профильными отделами.

## Минимальный набор сведений для C1

1. **Системы** — участники интеграции (1–N программных систем).
2. **Акторы** — люди/роли, инициирующие или потребляющие процесс (если есть). На уровне C2 акторы, как правило, опускаются — там значимы только системы и контейнеры.
3. **Связи** — кто кого вызывает. **Направление стрелки = «использует/вызывает», а не «передаёт данные»** (для потоков данных используется DFD, не C1/C2).
4. **Расположение относительно контура компании** — каждая система помечается как «в контуре компании» или «вне контура компании».

C1 НЕ требует: протоколов, форматов данных, моделей аутентификации, окружений — это уровень C2 и таблиц фазы 2.

## Тип системы и расположение относительно контура

Каждая система описывается двумя независимыми характеристиками — используй их так:

- **Тип** (`Система` / `Актор`) — колонка «Тип» в таблице-источнике.
- **Контур компании** (`в контуре` / `вне контура`) — колонка «Контур компании»; заполняется для каждой системы. Интеграция может быть между двумя системами в контуре или между системой в контуре и системой вне контура; инициатором может быть и система вне контура.

Роль в интеграции (`инициатор` / `получатель`) отдельной колонкой не выносится — она задаётся направлением связи (кто кого вызывает).

**Употребление термина «внешняя»:**
- Допустимо только с явным указанием оси: «внешняя относительно контура компании» или «внешняя относительно системы-инициатора».
- Без такого уточнения слово «внешняя» не используется — вместо него пиши «в контуре / вне контура» (это однозначно).

## Принцип table-first

Источник истины для агентов — таблица компонентов и связей. Диаграмма C1 — производная для людей. По умолчанию формат — **mermaid** (по запросу — Structurizr DSL или PlantUML).

### Таблица-источник C1

| N | Элемент | Тип | Контур компании | Использует / вызывает | Назначение |
|---|---|---|---|---|---|
| 1 | [Система A] | Система | в контуре | [Система B] | Инициатор: запрашивает данные X |
| 2 | [Система B] | Система | вне контура | — | Получатель: поставщик данных X |
| 3 | [Пользователь] | Актор | в контуре | [Система A] | Инициирует процесс (на C1; на C2 опускается) |

> «Тип» ∈ `Система` / `Актор`. «Контур компании» ∈ `в контуре` / `вне контура`. Первый столбец всегда `N`.

### Mermaid-пример C1 (по таблице)

```mermaid
flowchart LR
    user([Пользователь]):::actor
    a["[Система A]<br/><i>Система, в контуре компании</i>"]:::sys
    b["[Система B]<br/><i>Система, вне контура компании</i>"]:::ext

    user -->|инициирует процесс| a
    a -->|использует / вызывает| b

    classDef actor fill:#08427b,color:#fff;
    classDef sys fill:#1168bd,color:#fff;
    classDef ext fill:#999999,color:#fff;
```

> Заметка: стрелка отражает направление вызова (А вызывает B), не направление данных. Актор показан для C1; при построении C2 акторов опускают.

## Уточняющие вопросы для сбора недостающих сведений

Сформируй список под конкретную интеграцию, опираясь на `user-input-checklist`. Адресаты — владельцы систем и профильные отделы (Отдел архитектуры, Отдел информационной безопасности, Отдел инфраструктурного развития). Типовые вопросы:

1. Какой API у целевой системы? Есть ли OpenAPI/Swagger/Postman, ссылка на контракт?
2. Какие форматы данных (JSON/XML) и тип взаимодействия (REST/gRPC/OData)?
3. Какая модель аутентификации: OAuth2.0 Access Token Provider (или иной Identity Provider), Basic Auth, mTLS, API key?
4. Нужен ли Service Account / ClientId? Существует ли он или его необходимо создать (через Отдел архитектуры / Отдел инфраструктурного развития)?
5. Какие окружения есть у каждой системы (test/stage/prod, инстансы) и какое к какому подключается?
6. Используется ли промежуточный шлюз? Какие функции он выполняет (трансформация контрактов, кэширование, смена модели аутентификации, маршрутизация)?
7. Содержат ли данные ПДн/КТ? Есть ли требования к маскированию (вопрос к Отделу информационной безопасности)?

> Зафиксируй ответы в `user-input-checklist` и `integration-request-plan` (раздел «Открытые вопросы»). Когда собран минимум для C1 и получено подтверждение пользователя — переходи к фазе 2 (`skill.integration-design.ru.phase-2-architecture`).
