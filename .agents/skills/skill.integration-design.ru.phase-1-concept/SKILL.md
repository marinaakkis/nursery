# SKILL: integration-design phase-1-concept — Фаза 1: Концепт

> **Скоуп:** Первая фаза процесса проектирования и согласования межсервисной интеграции. Формирует верхнеуровневый концепт (достаточный для схемы C1), стартует накопитель `integration-request-plan`, собирает с пользователя недостающие сведения. Также служит точкой входа и оркестрационным обзором всего процесса.
> **Семейство (family):** `integration-design` — процесс из трёх фаз (Концепт → Проектирование → Согласование) без отдельного процессного правила.
> **Приоритет:** явные инструкции пользователя → security/DLP → этот скилл → общая эвристика.
> **Companion-файлы:** [`template.integration-request-plan.md`](template.integration-request-plan.md), [`template.user-input-checklist.md`](template.user-input-checklist.md), [`template.furps-plus.md`](template.furps-plus.md), [`reference.c1-concept.md`](reference.c1-concept.md).

## Обзор процесса (оркестрация 1 → 2 → 3)

| Фаза | Скилл | Назначение | Гейт перехода |
|---|---|---|---|
| 1. Концепт | `skill.integration-design.ru.phase-1-concept` (этот) | Минимум для C1 + наполнение «Описание» + старт накопителя | Сведений достаточно для C1 и для перехода к детальному проектированию |
| 2. Проектирование | `skill.integration-design.ru.phase-2-architecture` | Карточка проекта + вся техдокументация (тех-таблица, C2, окружения, API, модель данных, маппинг, аутентификация, журнал связанных заявок) | Подтверждение пользователя |
| 3. Согласование | `skill.integration-design.ru.phase-3-approval` | Заявки в Отдел архитектуры → Отдел информационной безопасности → (Отдел инфраструктурного развития) в Service Desk, вручную пользователем | Все необходимые заявки согласованы |

Сквозная точка входа — команда `command.integration-design.ru.run` (оркеструет фазы 1→2→3). По завершении фазы 3 процесс проектирования и согласования закрыт; после этого пользователь может инициировать разработку интеграции как отдельный этап.

## Когда применять

- Старт проектирования новой межсервисной интеграции.
- Пользователь приходит с запросом уровня «нужно подключить систему А к системе Б, чтобы получать X».
- Консультация по процессу проектирования и согласования интеграции.

## Адаптивность к уровню пользователя

Пользователь может иметь разный технический бэкграунд. Действуй по факту входных данных:

| Ситуация | Действие агента |
|---|---|
| Пользователь дал только цель/бизнес-описание | Сформируй концепт и `user-input-checklist`: перечисли, что ещё нужно (API, аутентификация, окружения, доступы), и кто это может предоставить |
| Пользователь знает компоненты, но не API/аутентификацию | Заполни известное; недостающее вынеси в чеклист со статусом «нет» и источником (владелец системы / профильный отдел) |
| Пользователь может заполнить всё | Зафиксируй сведения, сразу переходи к фазе 2 |

Предложи пользователю сформировать схему **C1** (по [`reference.c1-concept.md`](reference.c1-concept.md)), чтобы использовать её для согласования и сбора недостающих технических сведений с владельцами систем и профильными отделами.

## Входы / Выходы

| Входы | Выходы |
|---|---|
| Запрос/цель интеграции; известные компоненты, акторы, связи; (опц.) сведения об API и аутентификации | `integration-request-plan` (создан, Фаза 1 заполнена); раздел «Описание» концепта; `user-input-checklist`; FURPS+; (опц.) C1-схема |

## Алгоритм фазы «Концепт»

1. Создай рантайм-папку `docs/integration-requests/integration-request.i-<nnn>.<name>/` и `integration-request-plan` по шаблону; присвой `i-<nnn>` (следующий свободный номер).
2. Зафиксируй цель/бизнес-описание интеграции в разделе «Описание» (наполнение карточки проекта фазы 2).
3. Определи верхнеуровневые компоненты: системы, акторы, связи (направление = кто кого вызывает). Этого достаточно для C1.
4. Сопоставь с FURPS+: вытащи функциональные и нефункциональные требования из запроса.
5. Заполни `user-input-checklist`: что есть, чего не хватает (API-документация, модель аутентификации, окружения, доступы), кто источник недостающего.
6. При нехватке сведений — предложи C1-схему и перечень уточняющих вопросов для владельцев систем и профильных отделов; зафиксируй открытые вопросы в накопителе.
7. Когда минимум для C1 собран и пользователь подтвердил — переходи к фазе 2 (`skill.integration-design.ru.phase-2-architecture`).

## Принципы

- **Table-first:** источник истины для агентов — таблицы накопителя и чеклистов. C1-схема — производная, для людей (mermaid по умолчанию).
- **Минимализм фазы:** на концепте не углубляйся в детали API/маппинга — это фаза 2.
- **Безопасность данных (DLP) — секреты и ПДн:** при заполнении документации никогда не вписывай реальные секреты (`client_secret`, пароли, токены, ключи, сертификаты) и персональные данные — фиксируй только факт их наличия.
- **Безопасность данных (DLP) — конфиденциальные имена:** реальные имена систем и организаций приводи только в рабочем экземпляре документации; в примерах и совместно используемых/публикуемых артефактах используй плейсхолдеры (`[Система A]`, `client-example`).

## Чеклист (перед переходом к фазе 2)

- [ ] `integration-request-plan` создан, Фаза 1 заполнена, текущая фаза зафиксирована
- [ ] Раздел «Описание» (цель + бизнес-контекст) заполнен
- [ ] Верхнеуровневые компоненты/акторы/связи определены — достаточно для C1
- [ ] FURPS+ заполнен по доступным требованиям
- [ ] `user-input-checklist` отражает, что есть и чего не хватает (с источником)
- [ ] Открытые вопросы зафиксированы в накопителе
- [ ] (Опц.) C1-схема предложена/сформирована
- [ ] Подтверждение пользователя на переход к проектированию получено
