# Чеклист сведений от пользователя: <название интеграции>

Заполняется агентом совместно с пользователем на фазе «Концепт». Колонка «Статус» = `есть` / `нет` / `частично`.
Незаполненные обязательные строки блокируют переход к детальному проектированию (фаза 2) в части соответствующего раздела.

| N | Что предоставить | Зачем | Обязательность | Статус | Источник (кто даст) |
|---|---|---|---|---|---|
| 1 | Цель и бизнес-процесс интеграции | Раздел «Описание», C1 | Обязательно | <!-- есть/нет --> | Пользователь |
| 2 | Перечень систем-участников и их роли (инициатор/получатель) | Компоненты, C1/C2 | Обязательно | | Пользователь |
| 3 | Связи между системами (кто кого вызывает, частота) | Тех-таблица связей | Обязательно | | Пользователь / владельцы систем |
| 4 | Документация на API целевого сервиса (OpenAPI/Swagger/Postman/описание) | Описание эндпоинтов, модель данных | Обязательно | | Владелец целевой системы |
| 5 | Форматы данных (JSON/XML/иное) и тип взаимодействия (REST/gRPC/OData) | Тех-таблица, контракты | Обязательно | | Владелец API |
| 6 | Модель аутентификации/авторизации (OAuth2.0 через Access Token Provider; Basic Auth; mTLS; API key) | Шаблон auth | Обязательно | | Владелец системы / Отдел архитектуры |
| 7 | Сведения о Service Account / ClientId и требуемых ролях/доступах | Таблица доступов | Обязательно (может заполняться позже) | | Отдел архитектуры / Отдел инфраструктурного развития |
| 8 | Перечень окружений (test/stage/prod, инстансы) каждой системы | Таблица окружений | Обязательно | | Команды систем |
| 9 | Какое окружение к какому подключается | Таблица связей окружений | Обязательно | | Команды систем / Отдел архитектуры |
| 10 | Наличие промежуточного шлюза и его функции (трансформация контрактов, кэширование, смена модели аутентификации/авторизации к целевому сервису, маршрутизация) | Тех-таблица, auth, шаблон маппинга | Условно (если есть шлюз) | | Владелец интеграционного слоя / Отдел архитектуры |
| 11 | Маппинг полей — преобразование контрактов (частный случай функции шлюза, строка 10) | Шаблон маппинга | Условно (если есть трансформация) | | Владельцы контрактов |
| 12 | Особенности данных: наличие ПДн / КТ, требования к маскированию | Модель данных, Отдел информационной безопасности | Обязательно | | Пользователь / Отдел информационной безопасности |
| 13 | Список уже созданных заявок (согласование/инфра/УЗ/доступ) | Журнал связанных заявок (related-requests-log) | По мере появления | | Пользователь |

> При статусе `нет` для обязательной строки — предложи пользователю сформировать C1-схему (`reference.c1-concept.md`) и использовать её при обращении к указанному источнику. Зафиксируй пробел как «Открытый вопрос» в `integration-request-plan`.
>
> Добавляй/убирай строки под конкретную интеграцию. Колонки фиксированы: первый столбец — `N`.
