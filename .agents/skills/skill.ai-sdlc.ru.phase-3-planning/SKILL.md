# SKILL: phase-3-planning — Фаза 3: PLANNING

> **Скоуп:** Третья обязательная фаза любой задачи разработки. Преобразует апрувленный дизайн в исполнимый план реализации.
> **Главенствующий процессный контекст:** `rule.ai-sdlc.ru.process` — порядок фаз, гейт-правила, ролевая модель.
> **Исполнительный артефакт:** `command.ai-sdlc.ru.run-phase-3-planning` содержит пошаговый алгоритм выполнения фазы. Этот SKILL.md — нормативная спецификация; команда — исполнительная реализация.

## Когда применять

- После апрува фазы DESIGN
- До фазы IMPLEMENTATION
- При изменении дизайна — план пересматривается

## Структура dev-task (шаг реализации)

Формируй каждый шаг как отдельный `dev-task` по `skill.dev.ru.dev-planning` — полный шаблон для фазы 3 см. в [`reference.md`](reference.md).

Каждый dev-task ОБЯЗАН содержать разделы: **Цель**, **Входные условия**, **Зависимости**, **Шаги реализации**, **Тест-кейсы**, **Acceptance Criteria**, **Выходные артефакты**.

## Правила планирования

- Планировщик ОБЯЗАН вести **один dev-request -> один активный dev-plan**
- Планировщик ОБЯЗАН формировать несколько `dev-task`-файлов, по одному на логический срез, а не один монолитный dev-task
- Каждый dev-task ОБЯЗАН быть самодостаточным: ревьюируемым, коммитируемым и тестируемым независимо
- Каждый шаг ОБЯЗАН быть однозначным: без формулировок вида "сделай хорошо", только конкретные действия и ожидаемые результаты
- Acceptance Criteria ОБЯЗАНЫ включать автоматические гейты (build, tests, linters) и соответствие дизайну
- Планировщик ОБЯЗАН читать только approved research + approved дизайн и НЕ ПЕРЕЧИТЫВАТЬ весь проект заново
- Если в кодовой базе уже есть частичная реализация, планировщик ОБЯЗАН фиксировать это как риск/проверку для фазы 4, а не менять контекст фазы 3
- Каждый dev-task ОБЯЗАН явно фиксировать зависимости в секции `Зависимости` в формате `Depends on: t-<nnn> | —`
- Dev-task с необратимой операцией данных (DROP TABLE/COLUMN, TRUNCATE, CASCADE DELETE, удаление/переименование колонки в production) ОБЯЗАН быть помечен **💥** в заголовке и ОБЯЗАН содержать раздел **«План отката»** со ссылкой на подтверждение из итогов фазы 2: `(подтверждено: YYYY-MM-DD)`

### Критерии размера dev-task

| Размер | Характеристики | Действие |
|---|---|---|
| **Small** | ≤ 1 файл, ≤ 50 строк изменений, одна сущность или один endpoint | Один dev-task |
| **Medium** | 2–5 файлов, 50–200 строк, одна связная область (слой, модуль) | Один dev-task |
| **Large** | > 5 файлов, > 200 строк или несколько независимых слоёв | Разбить на несколько dev-task |

## Агентная структура

```
AI-агент (планировщик)
  Вход: research-doc + design-artifacts + test-strategy + стандарты
  Выход: dev-plan.r-<nnn>.<name>.md + dev-task.r-<nnn>.t-001.<name>.md, dev-task.r-<nnn>.t-002.<name>.md, ...
```

Планировщик ОБЯЗАН работать только с подготовленными артефактами (research/design/test strategy) и не перечитывать весь проект.

Связь с режимами проверки:

- **Режим 1 (Инженер):** план формирует агент; инженер выполняет гейт-проверку вручную
- **Режим 2 (Агент-ревьюер):** план формирует агент; отдельный агент-ревьюер выполняет гейт-проверку автоматически
- **Режим 3 (Агент + Инженер):** план формирует агент; агент-ревьюер проверяет первым, инженер завершает финальную верификацию

## Гейт качества

Режим проверки задаётся в начале задачи (по умолчанию — **Режим 3**):

| Режим | Описание |
|---|---|
| **1 — Инженер** | Инженер проверяет вручную по чеклисту |
| **2 — Агент-ревьюер** | Отдельный агент автоматически проверяет по чеклисту |
| **3 — Агент + Инженер** | Агент проверяет первым, затем инженер финально верифицирует |

Чеклист агента:

- [ ] `Режим` исполнения зафиксирован в разделе «Фаза 3» dev-process-plan
- [ ] Каждый dev-task охватывает конкретный срез функционала
- [ ] Acceptance criteria конкретны и проверяемы (не "работает нормально")
- [ ] Тест-кейсы прописаны для каждого dev-task
- [ ] Шаги не содержат неоднозначностей
- [ ] Для каждого dev-task заполнена секция `Зависимости`
- [ ] Стандарты проекта (стек, архитектурные ограничения) включены в контекст
- [ ] Выходные артефакты каждого dev-task определены явно
- [ ] Dev-task с деструктивными операциями помечен **💥** и содержит раздел «План отката»

Чеклист инженера:

- [ ] Порядок dev-task логичен и реализуем с учётом `Зависимости`
- [ ] Один dev-request содержит один активный dev-plan
- [ ] Риски частично реализованного функционала отражены в соответствующих dev-task

## Future-tasks

Если в ходе фазы PLANNING выявлен техдолг или задача вне scope текущего dev-request — создать future-task файл.

**Когда создавать:**
- При обнаружении техдолга вне scope текущего dev-task (техдолг не пишется в код)
- При выявлении улучшений, требующих отдельного дизайна или внешней зависимости
- По явному запросу пользователя или по рекомендации агента с явным подтверждением пользователя

**Нормативный baseline:** `rule.governance.ru.future-tasks` — папка, маска имени, обязательные разделы.

После создания future-task — добавить ссылку в раздел «Итоги фазы» dev-process-plan.

## Профиль артефактов (`docs`)

Состав конечных артефактов зависит от параметра `docs=compact|full` (дефолт `compact`; берётся из «Объём документации» dev-process-plan):

- **`compact`** (по умолчанию) — dev-task создаются всегда в полном объёме; сводный dev-plan — компактный индекс-таблица (без нарратива). Профиль: `.agents/skills/skill.ai-sdlc.ru.phase-3-planning/reference.artifacts.compact.md`.
- **`full`** — dev-task + развёрнутый сводный dev-plan с нарративом. Профиль: `.agents/skills/skill.ai-sdlc.ru.phase-3-planning/reference.artifacts.full.md`.

В обоих профилях: dev-task самодостаточны (acceptance criteria конкретны, тест-кейсы прописаны, шаги однозначны); future-tasks создаются при техдолге вне scope.
