# Reference — phase-3-planning

## Шаблон dev-task (phase 3)

```md
# dev-task.r-<nnn>.t-<nnn>.<system-dev-task-name>

## Цель
- <конкретный результат шага>

## Входные условия
- [ ] <что должно быть готово до старта шага>

## Зависимости
- Depends on: t-<nnn> | —

## Шаги реализации
1. <действие 1>
2. <действие 2>
3. <действие 3>

## Тест-кейсы
- [ ] <unit/integration/e2e кейс #1>
- [ ] <критичный негативный кейс>

## Acceptance Criteria
- [ ] `build` проходит
- [ ] `tests` проходят
- [ ] `linters` проходят
- [ ] Соответствие design-артефактам подтверждено

## Выходные артефакты
- `path/to/file-1`
- `path/to/file-2`

## Риски и примечания
- <фиксируем частично реализованный функционал, если найден>
```

## Дополнение для dev-task с деструктивной операцией

Если шаг содержит необратимую операцию, используй заголовок с `💥` и добавь раздел ниже:

```md
## План отката
- <шаг восстановления 1>
- <шаг восстановления 2>
- Подтверждение: (подтверждено: YYYY-MM-DD)
```

## Пример декомпозиции Large-задачи

Исходно: задача затрагивает 8 файлов и два слоя (API + use-cases).

Корректная декомпозиция:

- `t-001` — обновление контрактов и DTO
- `t-002` — реализация use-cases
- `t-003` — контроллеры и интеграционные тесты

Некорректная декомпозиция:

- Один `t-001`, который одновременно меняет DTO, бизнес-логику, API и тесты без зависимостей

## Примеры «правильно / неправильно»

- **Правильно:** `Small` задача (1 файл, 30 строк, 1 endpoint) -> один dev-task.
- **Неправильно:** `Large` задача (>5 файлов, >200 строк) -> один dev-task без разбиения.
- **Правильно:** у `t-003` указано `Depends on: t-002`.
- **Неправильно:** в чеклисте есть «зависимости соблюдены», но секция `Зависимости` пустая.
