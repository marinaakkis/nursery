# Таблица описания модели данных

Стандарт описания структурированных моделей данных в документации: сущности, DTO, JSON-контракты, схемы БД, межсервисные модели.

**Приоритет:** явные инструкции пользователя → этот скилл → общая эвристика.

**Смежные скиллы:**
- `skill.dev.ru.enum-doc` — правила документирования enum и discriminated union.
- `skill.integration.ru.api-endpoint-doc` — описание endpoint и его моделей запроса/ответа.
- `reference.md` в этом же каталоге — расширенные примеры и краевые случаи.

## Когда применять

- Описание Entity, DTO, ViewModel, record-типов.
- Описание тела запроса / ответа в API-контракте (OpenAPI, интеграционный паспорт).
- Описание JSON-структур в межсервисном взаимодействии.
- Описание схемы таблицы БД или проекции запроса.
- Любой контекст, где нужно формально задокументировать набор свойств модели.

## Структура таблицы

| N | Свойство модели | Наименование | Тип данных | Формат | Комментарий |
|---|---|---|---|---|---|
| ... | ... | ... | ... | ... | ... |

### Описание колонок

| Колонка | Описание |
|---|---|
| **N** | Номер свойства. Используется для навигации и (при Стратегии A) для обозначения вложенности. |
| **Свойство модели** | Системное название свойства. Формат зависит от выбранной стратегии вложенности. |
| **Наименование** | Человекочитаемое описание. Например: «Идентификатор пользователя». |
| **Тип данных** | Тип свойства с `?`-нотацией обязательности/nullable (см. ниже). |
| **Формат** | Ограничения и форматы значений (см. нотацию форматов ниже). |
| **Комментарий** | Дополнительные сведения: бизнес-правила, ограничения, особенности поведения. Заполняй обязательно, если есть значимые ограничения; иначе можно оставить пустым. |

> Первый столбец всегда `N`, последний всегда `Комментарий`.

---

## Как составить таблицу

1. Выбери одну стратегию вложенности: `A` по умолчанию или `Б` только для JSON/межсервисного контракта с вложенностью не глубже 3 уровней.
2. Создай таблицу со строгим порядком колонок: `N | Свойство модели | Наименование | Тип данных | Формат | Комментарий`.
3. Заполни свойства по выбранной стратегии: используй иерархическую нумерацию `N` для Стратегии A или полный путь свойства для Стратегии Б.
4. Укажи типы, обязательность и nullable через `?`, затем проставь формат/ограничения; для объектов и массивов ставь `—` в `Формат`, если формат не применим.
5. Проверь результат по чеклисту перед сдачей и убедись, что именование совпадает с кодом/контрактом.

## Нотация обязательности и nullable через `?`

Используй суффикс `?` на типе для nullable/optional — отдельных колонок для этого нет.

| Запись | Значение |
|---|---|
| `string` | Обязательное, не может быть `null` |
| `string?` | Необязательное или может быть `null` |
| `int` | Обязательное числовое (value-тип) |
| `int?` | Nullable числовое |

> Если свойство обязательно, но значение допускает `null` — пиши `Type?` и добавь «Обязателен» в Комментарий.

## Стратегии вложенности

Выбери одну стратегию вложенности и не смешивай их в одном документе.

**Стратегия A — базовая, применяется по умолчанию** для Entity, DTO, схем БД, а также для JSON с вложенностью > 3 уровней.

**Стратегия Б — dot-path** применяй только для JSON и межсервисных контрактов с вложенностью **≤ 3 уровней**.

Если нет явных оснований для Стратегии Б (JSON/межсервис + вложенность ≤ 3) — применяй Стратегию A.

### Стратегия A — N-нумерация (базовая)

Выражай вложенность иерархической нумерацией в колонке `N`. В колонке `Свойство модели` указывай только имя текущего свойства (без пути).

Пример:

| N | Свойство модели | Наименование | Тип данных | Формат | Комментарий |
|---|---|---|---|---|---|
| 1 | `Id` | Идентификатор | `Guid` | GUID | Генерируется на сервере |
| 2 | `Contact` | Контактные данные | `ContactDto` | — | Вложенный объект |
| 2.1 | `Email` | Email | `string` | email | |
| 2.2 | `Phones` | Телефоны | `[]PhoneDto?` | — | Массив, необязателен |
| 2.2.1 | `Type` | Тип телефона | `PhoneType` | enum | |
| 2.2.2 | `Number` | Номер | `string` | `+7XXXXXXXXXX` | |
| 3 | `CreatedAt` | Дата создания | `DateTimeOffset` | ISO 8601 | UTC |

### Стратегия Б — Dot-path (JSON / межсервис, вложенность ≤ 3)

Выражай вложенность полным путём в колонке `Свойство модели`. Колонка `N` — порядковый номер строки.

Если вложенность превышает 3 уровня — переведи всю таблицу на Стратегию A (не смешивай стратегии в одном документе).

Пример:

| N | Свойство модели | Наименование | Тип данных | Формат | Комментарий |
|---|---|---|---|---|---|
| 1 | `id` | Идентификатор | `string` | GUID | |
| 2 | `contact` | Контактные данные | `{}` | — | |
| 3 | `contact.email` | Email | `string` | email | |
| 4 | `contact.phones` | Телефоны | `[]?` | — | Необязателен |
| 5 | `contact.phones[].type` | Тип телефона | `string` | enum | |
| 6 | `contact.phones[].number` | Номер | `string` | `+7XXXXXXXXXX` | |
| 7 | `createdAt` | Дата создания | `string` | ISO 8601 | UTC |

## Нотация типов данных

| Запись | Значение |
|---|---|
| `string` | Строка |
| `int` / `number` | Целое число |
| `decimal` / `float` | Число с плавающей точкой |
| `bool` | Булево |
| `Guid` | GUID (.NET-контекст) |
| `DateTimeOffset` / `DateTime` | Дата и время (.NET-контекст) |
| `{}` | Объект (анонимный, структура раскрывается ниже) |
| `[]` | Массив (тип элементов раскрывается ниже) |
| `[]string` | Массив строк |
| `UserDto` | Конкретный именованный тип |
| `TypeA \| TypeB` / `oneOf(TypeA, TypeB)` | Union/oneOf. Для discriminated union дополнительно синхронизируй описание с `skill.dev.ru.enum-doc`. |

## Нотация форматов / ограничений

| Запись | Значение |
|---|---|
| `GUID` | UUID v4 |
| `ISO 8601` | Дата/время по стандарту ISO |
| `YYYYMMDD` | Дата без разделителей |
| `email` | Электронная почта RFC 5322 |
| `enum` | Значение из перечисления (укажи имя enum в `Формат`; допустимые значения приведи в `Комментарий`, если enum не вынесен отдельно) |
| `Regex: <pattern>` | Произвольный regex |
| `[min..max]` | Диапазон числовых значений |
| `maxLength: N` | Максимальная длина строки |
| `—` | Формат не применим (объект, массив, составной тип) |

> Список является базовым. На уровне проекта допускается введение дополнительных обозначений при наличии явного соглашения команды.

## Соглашения именования

| Контекст | Именование |
|---|---|
| Entity, DTO, record, ViewModel | Зависит от стека: `.NET` — `PascalCase`, `Python` — `snake_case`. Определяется соглашением проекта. |
| JSON, межсервисный контракт, REST API | `camelCase` |
| База данных (столбцы) | `snake_case` (если не диктует иное) |

Именование в документации должно совпадать с реальными именами в коде / схеме, чтобы таблица оставалась актуальной без ручной синхронизации.

## Наследование и базовые типы

Если модель наследует базовый тип (`extends`, `BaseEntity` и т.п.), используй один из двух вариантов:
- Явно раскрой унаследованные поля в общей таблице и добавь пометку `(Inherited from <BaseType>)` в `Комментарий`.
- Или вынеси базовый тип в отдельную таблицу и укажи явную ссылку на неё в `Комментарий`.

Выбери один вариант и применяй его последовательно в рамках документа.

## Перед сдачей (чеклист)

- [ ] Выбрана одна стратегия вложенности (A или Б) и не смешивается.
- [ ] Стратегия Б применена только для JSON/межсервис с вложенностью ≤ 3; иначе — Стратегия A.
- [ ] Первый столбец — `N`, последний — `Комментарий`.
- [ ] Необязательные и nullable свойства помечены `?` на типе; отдельных колонок `Обязателен`/`Nullable` нет.
- [ ] Именование свойств соответствует стеку/контексту.
- [ ] Массивы: `[]TypeName` (Стратегия A) или `[].property` (Стратегия Б).
- [ ] Для перечислений в `Формат` указано имя enum.
- [ ] Для перечислений допустимые значения указаны в `Комментарий`, если enum не вынесен в отдельный артефакт.
- [ ] Вложенные объекты раскрыты строками ниже.
- [ ] Если документируется API-контракт — таблица согласована с OpenAPI-спецификацией (`docs/api-requirements/`).
