# SKILL: phase-4-implementation — Фаза 4: IMPLEMENTATION

> **Скоуп:** реализация апрувленных `dev-task` из Phase 3 с обязательными quality gates.
>
> **Главенствующий процессный контекст:** `rule.ai-sdlc.ru.process.mdc` (последовательность фаз и режимы).
>
> **Исполнительный артефакт:** `command.ai-sdlc.ru.run-phase-4-implementation`.
>
> **Reference:** `reference.md` (шаблоны отчётов ревьюеров и Lead).

## Когда применять

- После апрува фазы PLANNING
- Единственная фаза, где AI пишет production-код
- Каждая фаза плана реализуется последовательно — следующая только после прохождения всех гейтов

## Стоп-условия

| # | Условие | Действие |
|---|---|---|
| 1 | ANY ревьюер вернул FAIL | Переход к следующему dev-task заблокирован; все замечания объединяются и передаются Implementer |
| 2 | Конфликт между ревьюерами | Lead останавливается и эскалирует пользователю; реализация не продолжается до принятия решения |
| 3 | Предыдущий dev-task не прошёл все гейты | Следующий dev-task не начинается |
| 4 | Фаза PLANNING не апрувлена | Фаза 4 не запускается |
| 5 | Достигнут лимит итераций Implementer ↔ Reviewer (3) | Lead эскалирует пользователю с кратким отчётом причин зацикливания и блокирует продолжение до решения |

**Запрещено в любом режиме:**
- Lead пишет код
- Implementer проводит ревью или правит тесты без явной задачи от Lead
- Любой Reviewer правит код
- AI создаёт коммит без явного подтверждения пользователя

## Команда агентов (multi-agent)

```
Lead
  ├── читает текущий dev-task из плана
  ├── декомпозирует на задачи для Implementer
  ├── НИКОГДА не пишет код
  ├── запускает всех 4 ревьюеров параллельно после завершения dev-task
  └── агрегирует: ALL PASS → следующий dev-task | ANY FAIL → возврат к Implementer

Implementer
  ├── пишет код строго по заданию от Lead
  ├── записывает файлы в рабочую директорию через Write/Edit инструменты
  ├── НЕ проводит ревью
  └── НЕ правит тесты без явной задачи

Reviewer: Build + Test
  ├── запускает билд
  ├── запускает все тесты
  └── репортит конкретную ошибку (файл + строка + сообщение)

Reviewer: Architecture + Standards
  ├── проверяет соответствие C4 / Sequence (диаграммы в `full` или таблицы-эквиваленты в `compact`)
  ├── проверяет доменную модель только если это релевантно типу задачи (для CRUD допускается облегчённый профиль проверки)
  ├── проверяет распределение по слоям
  ├── проверяет DRY, SOLID, стандарты стека
  └── НЕ правит код

Reviewer: Security
  ├── проверяет OWASP Top 10
  ├── ищет hardcoded secrets, открытые endpoints
  ├── проверяет валидацию входных данных
  └── НЕ правит код

Reviewer: Plan Compliance
  ├── проверяет: все шаги dev-task выполнены
  ├── проверяет: решение не упрощено (AI не выкинул функционал)
  ├── сверяет с design-артефактами
  └── НЕ правит код

Tester
  ├── запускает приложение / тесты
  ├── репортит что сломано (файл + строка + стектрейс)
  └── НЕ правит код
```

## Протокол ревью

1. Implementer сообщает Lead: dev-task завершён
2. Lead отправляет задачи **всем 4 ревьюерам одновременно** (параллельно)
3. Ревьюеры возвращают результаты с конкретными проблемами
4. Lead агрегирует:
   - ALL PASS → переход к следующему dev-task
   - ANY FAIL → объединяет все замечания, группирует по ревьюеру, возвращает Implementer
5. После завершения **всех** dev-task → Final Cross-Phase Review (те же 4 ревьюера)

## Гейты качества (на каждый dev-task)

Режим проверки задаётся в начале задачи (по умолчанию — **Режим 3**):

| Режим | Описание |
|---|---|
| **1 — Инженер** | Инженер проверяет вручную по чеклисту |
| **2 — Агент-ревьюер** | Все 4 ревьюера проверяют автоматически; при ALL PASS — переход к следующему dev-task происходит без ожидания инженера |
| **3 — Агент + Инженер** | Агент проверяет первым, затем инженер финально верифицирует |

| Гейт | Что проверяется | Кто |
|---|---|---|
| Режим | `Режим` зафиксирован в разделе «Фаза 4» dev-process-plan | Lead |
| Build | Компилируется без ошибок | Reviewer: Build+Test |
| Tests | Все тесты зелёные; при падении существующего теста Lead эскалирует пользователю выбор «править тест/править код» с объяснением причины падения и рекомендацией действия | Reviewer: Build+Test + Lead |
| Linters | Cyclomatic/cognitive complexity, стандарты команды | Reviewer: Architecture |
| Architecture | Доменная модель, слои, соответствие C4/Sequence | Reviewer: Architecture |
| Security | Инъекции, утечки, hardcode, открытые endpoints | Reviewer: Security |
| Plan compliance | Все шаги dev-task выполнены, ничего не упрощено | Reviewer: Plan Compliance |

**Нельзя переходить к следующему dev-task, не пройдя ВСЕ гейты.**

## Исключительные ситуации

### 1) Частичное выполнение dev-task (PARTIAL)

- Если Implementer заблокирован на середине задачи, Lead фиксирует статус `PARTIAL`
- Формируется артефакт эскалации с блокерами, сделанными шагами и несделанными шагами
- Пользователь принимает формальное решение: `подтверждено` или `отклонено`
- До решения пользователя переход к следующему dev-task запрещён

### 2) Отклонение от плана/дизайна в ходе реализации

При выявлении необходимости изменить план или дизайн Lead обязан эскалировать пользователю три варианта:

1. Вернуться к Фазе 2/3 для доработки требований (завершить текущий контекст и создать артефакт причины возврата)
2. Продолжить в текущем контексте
3. Остановить обработку и создать артефакт «на чём остановились»

Если пользователь подтверждает возврат к предыдущей фазе:

- текущий контекст Фазы 4 считается завершённым;
- создаётся артефакт возврата с описанием причины, статуса и точки остановки;
- запускается повторно соответствующая фаза (2 или 3) с чистым контекстом.

### 3) Несвязанные регрессии в legacy-коде

- Если упал тест, не связанный с текущим dev-task, Lead эскалирует пользователю варианты действий:
  - исправить в рамках текущей фазы;
  - вынести в отдельный dev-task/отдельную задачу;
  - остановить текущий dev-task до отдельного решения.
- В отчёте обязательно фиксируются: влияние на текущий scope, риск и рекомендованное действие.

## Что проверяет Reviewer: Security

Список ниже — обязательный минимум. Конкретный проект может расширять его дополнительными проверками.

- Нет конкатенации строк в SQL (только параметризованные запросы)
- Нет hardcoded credentials, API keys, паролей, токенов
- Все входные параметры валидируются
- Auth-check на всех защищённых endpoints
- Нет логирования sensitive-данных (пароли, токены, PII)
- Rate limiting на auth-эндпоинтах
- XSS, CSRF, IDOR, SQL injection — по OWASP Top 10

## Правила агентов

- Ревьюеры передают **конкретную строку** и **конкретную проблему** — не "сделай лучше"
- Tester не говорит "тесты упали" — он указывает какой тест, какая строка, какой output
- Lead не интерпретирует и не улучшает замечания ревьюеров — передаёт дословно
- AI non-deterministic: может упростить решение, "посчитав, что это MVP" — Reviewer: Plan Compliance существует именно для этого
- При конфликте между ревьюерами (один требует изменений, другой считает их вне скоупа) — Lead останавливается и эскалирует пользователю; реализация не продолжается до принятия решения

> **Граница с Фазой 5:** Reviewer: Security проверяет **код текущего dev-task** (OWASP inline, hardcoded secrets, auth-checks в написанном коде). Полный SAST/DAST на весь набор изменений — задача Фазы 5.

## Завершение фазы и коммит

После прохождения всех dev-task и финального Cross-Phase Review возможны два сценария:

| Режим | Сценарий завершения |
|---|---|
| **Режим 2** | Фаза завершается автоматически — AI переходит к следующей фазе (phase-5) без предложения коммита и без ожидания инженера; предложение коммита допустимо только после прохождения всего процесса |
| **Режим 1 / 3** | AI предлагает инженеру сделать коммит; реализация до подтверждения не завершена |

Самостоятельное создание коммита не допускается ни в одном режиме.

Рекомендации для инженера (режим 1/3):
- Один финальный коммит на задачу (или по одному на dev-task — по договорённости команды)
- Сообщение коммита: только функциональное изменение
- Файлы планирования и дизайна **не входят** в коммит с кодом

## Техдолг и future-tasks

Техдолг, выявленный вне scope текущего dev-task, **не пишется в код** — фиксируется как future-task.

- Создать `docs/dev-requests/future-tasks/future-task.<domain>.<name>.md` по `rule.governance.ru.future-tasks`
- Добавить ссылку в раздел «Паттерны ошибок реализации» или «Итоги фазы» dev-process-plan
- Reviewer: Plan Compliance проверяет: нет изменений вне scope текущего dev-task; весь выявленный техдолг зафиксирован в dev-process-plan, не внесён в код

## Чеклист

- [ ] Фаза 3 апрувлена, входные `dev-task.r-<nnn>.t-<nnn>` доступны
- [ ] Для каждого dev-task пройдены все гейты (Build, Tests, Linters, Architecture, Security, Plan compliance)
- [ ] При падении существующего теста выполнена эскалация пользователю с объяснением причины и рекомендацией
- [ ] При блокере оформлен `PARTIAL` + артефакт эскалации
- [ ] При отклонении от плана/дизайна выполнена эскалация с выбором из 3 вариантов
- [ ] Несвязанные legacy-регрессии обработаны через эскалацию, без молчаливой структурной перезаписи
- [ ] Лимит итераций Implementer ↔ Reviewer не превышен (или оформлена эскалация после 3-й итерации)
- [ ] `dev-process-plan` обновлён: режим, статус фазы, итоги, отклонения, блокеры
- [ ] Режим 2: нет предложения коммита до прохождения всего процесса
- [ ] Режимы 1/3: предложение коммита сделано только после всех гейтов и финального ревью
