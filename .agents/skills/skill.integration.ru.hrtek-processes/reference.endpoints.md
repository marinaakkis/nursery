# Reference: эндпоинты базового процесса VK HR Tek

Полное описание эндпоинтов, участвующих в задокументированных процессах интеграции с VK HR Tek (запуск подписания, контроль статуса, получение файла, отмена). Формат — по `skill.integration.ru.api-endpoint-doc`. Прочие эндпоинты — кратко в [reference.endpoints-extra.md](reference.endpoints-extra.md); полный контракт — официальный `public-api.openapi.yaml`.

## Базовые URL

| Слой | Базовый URL |
|---|---|
| Прямой вызов VK HR Tek | `https://public-api.vkdoc.mail.ru/api/v1/...` |
| Через корпоративный шлюз | `<esb-krakend-host>/bcd-to-hrtek/api/v1.0/...` |

> Шлюз `bcd-to-hrtek` работает в режиме pass-through (без трансформации/маскирования), поэтому контракт совпадает с официальным API VK HR Tek 1:1. Шлюз добавляет собственный сегмент версии `api/v1.0`; официальный API использует `api/v1`.

## Общие заголовки (на уровне интеграции)

Документируются один раз; в таблицах параметров эндпоинтов не дублируются.

| Заголовок | Тип | Значения | Назначение |
|---|---|---|---|
| `Authorization` | string | `Bearer <access-token>` | Токен Service-Guard (к шлюзу). Детали — [reference.auth.md](reference.auth.md) |
| `X-User-Id` | string (uuid) | `<user-id>` | Идентификатор пользователя; получается из `/user/by_snils` или `/user/by_personnel_number` |
| `X-Side` | string (enum) | `employee` \| `company` | Сторона, действующая в процессе |
| `Accept` | string | `application/json` \| `application/pdf` | Ожидаемый тип ответа |

**Security scheme (официальный контракт):** `ApiKeyAuth` — заголовок `Authorization` (на всех эндпоинтах). На стороне потребителя в `Authorization` кладётся токен Service-Guard; подстановку токена VK HR Tek выполняет шлюз.

Модели запросов/ответов — в [reference.data-models.md](reference.data-models.md). Подписание — в [reference.signing-unep.md](reference.signing-unep.md) / [reference.signing-ukep.md](reference.signing-ukep.md) / [reference.signing-pep.md](reference.signing-pep.md).

## Получение идентификатора пользователя по СНИЛС

Возвращает внутренний идентификатор пользователя VK HR Tek по СНИЛС сотрудника. Полученный `id` используется как `X-User-Id` в последующих вызовах.

### Запрос
1. **HTTP-метод:** `GET`
2. **Путь:** `/user/by_snils`
3. **Параметры:**

| N | Параметр | Тип параметра | Название | Тип данных | Формат | Комментарий |
|---|---|---|---|---|---|---|
| 1 | `snils` | `query` | СНИЛС сотрудника | `string` | — | PII; в примерах — фиктивный |

### Ответ
1. **Content-Type:** `application/json`
2. **Тело ответа:** `UserBySnilsResponse` (`{ id }`)
3. **Статусы:**

| N | Статус | Условие | Тело ответа | Комментарий |
|---|---|---|---|---|
| 1 | `200` | Пользователь найден | `UserBySnilsResponse` | `id` → `X-User-Id` |
| 2 | `400` | Невалидные данные | `Error` | |
| 3 | `401` | Ошибка авторизации | `Error` | |
| 4 | `403` | Запрещено | `Error` | |
| 5 | `404` | Не найдено | `Error` | |
| 6 | `500` | Серверная ошибка | `Error` | |

## Получение идентификатора пользователя по табельному номеру

Возвращает идентификатор пользователя по табельному номеру (внешний id из 1С) и идентификатору компании. Альтернатива `by_snils`.

### Запрос
1. **HTTP-метод:** `GET`
2. **Путь:** `/user/by_personnel_number`
3. **Параметры:**

| N | Параметр | Тип параметра | Название | Тип данных | Формат | Комментарий |
|---|---|---|---|---|---|---|
| 1 | `personnel_number` | `query` | Табельный номер | `string` | — | Внешний id сотрудника |
| 2 | `company_id` | `query` | Идентификатор компании | `string` | — | Внешний id организации (1С) |

### Ответ
1. **Content-Type:** `application/json`
2. **Тело ответа:** `UserByPersonnelNumberResponse` (`{ id }`)
3. **Статусы:** `200` (найден, `id` → `X-User-Id`), `400`, `401`, `403`, `404`, `500` → `Error`.

## Получение доступных типов Заявок

Возвращает типы Заявок (`options[]`), которые пользователь может создать. `options[].event_type_id` используется при создании Заявки.

### Запрос
1. **HTTP-метод:** `GET`
2. **Путь:** `/event/create_options`
3. **Параметры:**

| N | Параметр | Тип параметра | Название | Тип данных | Формат | Комментарий |
|---|---|---|---|---|---|---|
| 1 | `event_type_group?` | `query` | Группа типов событий | `string` | GUID | Необязателен |
| 2 | `employee_id?` | `query` | Сотрудник | `string` | GUID | Необязателен |
| 3 | `personnel_number?` | `query` | Табельный номер | `string` | — | Необязателен |
| 4 | `legal_id?` | `query` | Идентификатор организации | `string` | — | Необязателен |

### Ответ
1. **Content-Type:** `application/json`
2. **Тело ответа:** `CreateEventOptionsList` (`{ options[] }`)
3. **Статусы:** `200`, `400`, `401`, `403`, `404`, `500` → `Error`.

**Пример ответа** (значения фиктивные):
```json
{
  "options": [
    {
      "option_name": "Командировка",
      "employee_id": "0a1b2c3d-0000-4000-8000-000000000001",
      "event_type_id": "0a1b2c3d-0000-4000-8000-0000000000aa",
      "event_type_name": "Заявление на командировку",
      "employee_name": "Иван Иванов"
    }
  ]
}
```
> Как получить `event_type_id`: вызвать `create_options`, найти нужный тип по `event_type_name`/`option_name` и взять его `event_type_id` (и `employee_id`) для `POST /event`.

## Создание Заявки

Создаёт Заявку (`Event`) на подписание для сотрудника. Возвращает `event_id` — корреляционный идентификатор всего процесса.

### Запрос
1. **HTTP-метод:** `POST`
2. **Путь:** `/event`
3. **Параметры:** — (заголовки `X-Side`, `X-User-Id`)
4. **Content-Type:** `application/json`
5. **Тело запроса:** `CreateEventRequest` (`event_type_id`, `employee_id?`, `participants?`, `deadlines?`)

**Пример (минимальный):**
```json
{ "event_type_id": "0a1b2c3d-0000-4000-8000-0000000000aa", "employee_id": "0a1b2c3d-0000-4000-8000-000000000001" }
```

**Пример (полный, с участниками и дедлайнами):**
```json
{
  "event_type_id": "0a1b2c3d-0000-4000-8000-0000000000aa",
  "employee_id": "0a1b2c3d-0000-4000-8000-000000000001",
  "participants": [
    { "role_id": "0a1b2c3d-0000-4000-8000-0000000000r1", "group_id": "0a1b2c3d-0000-4000-8000-0000000000g1" }
  ],
  "deadlines": [
    { "node_id": "0a1b2c3d-0000-4000-8000-0000000000n1", "deadline": "2026-07-01T12:00:00Z" }
  ]
}
```
> **`participants`** (опционально) — назначение исполнителей на роли для типов Заявок с настраиваемыми участниками: `role_id` — роль в типе Заявки, `group_id` — назначаемая на роль группа/подразделение. Допустимые `role_id`/`group_id` — из `GET /event/create_options/event_type/participant_options`. Если тип Заявки не требует настройки участников — поле опускается.

### Ответ
1. **Content-Type:** `application/json`
2. **Тело ответа:** `CreateEventResponse` (`{ event_id }`)
3. **Статусы:**

| N | Статус | Условие | Тело ответа | Комментарий |
|---|---|---|---|---|
| 1 | `200` | Заявка создана | `CreateEventResponse` | `event_id` → последующие вызовы |
| 2 | `400` | Невалидные данные | `Error` | |
| 3 | `401` | Ошибка авторизации | `Error` | |
| 4 | `403` | Запрещено | `Error` | |
| 5 | `404` | Не найдено | `Error` | |
| 6 | `500` | Серверная ошибка | `Error` | |

## Получение Заявки (статус, этапы, документы)

Возвращает текущее состояние Заявки: активные этапы (`active_nodes[].action.type`, `node_id`), документы (`documents[].id`, ссылки на файлы), `permissions` (включая `cancel`), детали отмены. Основной эндпоинт контроля статуса (поллинг).

### Запрос
1. **HTTP-метод:** `GET`
2. **Путь:** `/event/{event_id}`
3. **Параметры:**

| N | Параметр | Тип параметра | Название | Тип данных | Формат | Комментарий |
|---|---|---|---|---|---|---|
| 1 | `event_id` | `path` | Идентификатор Заявки | `string` | GUID | |

### Ответ
1. **Content-Type:** `application/json`
2. **Тело ответа:** `Event`
3. **Статусы:** `200` (состояние Заявки), `400`, `401`, `403`, `404`, `500` → `Error`.

> Используется в поллинге до `active_nodes[].action.type == completed` (см. [reference.flows.md](reference.flows.md)).

## Загрузка документа в этап

Загружает файл документа в активный этап Заявки (`node_id`). Тело — `multipart/form-data`; атрибуты передаются полями `attributes[<attribute-uuid>]`.

### Запрос
1. **HTTP-метод:** `POST`
2. **Путь:** `/event/{event_id}/{node_id}/upload`
3. **Параметры:**

| N | Параметр | Тип параметра | Название | Тип данных | Формат | Комментарий |
|---|---|---|---|---|---|---|
| 1 | `event_id` | `path` | Идентификатор Заявки | `string` | GUID | |
| 2 | `node_id` | `path` | Идентификатор этапа | `string` | GUID | Из `active_nodes[]`/`nodes[]` |
4. **Content-Type:** `multipart/form-data`
5. **Тело запроса:** `UploadRequest` (`document` binary, `attributes`, `document_date?`, `document_number?`)

> **Атрибуты** передаются отдельными multipart-полями `attributes[<id>]` (не единым JSON-объектом). Полный механизм (ключ = `id` из `form_attributes`, типы `text`/`file`/`[]file`, когда обязательны) — канонический раздел «[Передача атрибутов](reference.data-models.md)» в `reference.data-models.md`.

### Ответ
1. **Content-Type:** — (тело отсутствует)
2. **Тело ответа:** —
3. **Статусы:** `200` (загружено, без тела), `400`, `401`, `403`, `404`, `500` → `Error`.

## Отмена Заявки

Отменяет (отклоняет) Заявку целиком. Для **незавершённой** Заявки переводит её в состояние `canceled`. Для **уже завершённой** Заявки операция запрещена (`403`, `error_code = forbidden`). Предпроверка допустимости — `permissions.cancel` в `GET /event/{event_id}`.

### Запрос
1. **HTTP-метод:** `POST`
2. **Путь:** `/event/{event_id}/cancel`
3. **Параметры:**

| N | Параметр | Тип параметра | Название | Тип данных | Формат | Комментарий |
|---|---|---|---|---|---|---|
| 1 | `event_id` | `path` | Идентификатор Заявки | `string` | GUID | |
4. **Content-Type:** `application/json`
5. **Тело запроса:** `CancelEventRequest` (`reason_id`, `comment?`)

### Ответ
1. **Content-Type:** `application/json`
2. **Тело ответа:** `CancelEventResponse` (`{ event_id }`)
3. **Статусы:**

| N | Статус | Условие | Тело ответа | Комментарий |
|---|---|---|---|---|
| 1 | `200` | Заявка отменена | `CancelEventResponse` | Состояние → `canceled` |
| 2 | `400` | Невалидные данные | `Error` | |
| 3 | `401` | Ошибка авторизации | `Error` | |
| 4 | `403` | Запрещено / Заявка уже завершена | `Error` | `error_code = forbidden` для завершённой Заявки |
| 5 | `404` | Заявка не найдена | `Error` | |
| 6 | `500` | Серверная ошибка | `Error` | |

## Расхождения источников (важно при реализации)

- В официальном PDF упоминаются эндпоинты, отсутствующие в OpenAPI YAML (`POST /event/batch/accept`, `…/unep_sign_batch/confirm`), а `…/unep_sign_batch/code` помечен Deprecated. **Источник истины — OpenAPI** `public-api.openapi.yaml`.
- Стандартные `4xx/5xx` для части action-эндпоинтов в YAML не перечислены явно — применяется общий error-handling сервиса (`Error`).
