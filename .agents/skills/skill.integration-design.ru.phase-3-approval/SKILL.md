# SKILL: integration-design phase-3-approval — Фаза 3: Согласование

> **Скоуп:** Согласование спроектированной интеграции с отделами. «Согласование архитектуры межсервисной интеграции».
> **Семейство:** `integration-design`. Предыдущая фаза — `skill.integration-design.ru.phase-2-architecture`.
> **Приоритет:** явные инструкции пользователя → security/DLP → этот скилл → общая эвристика.
> **Companion-файлы:** [`template.sd-request.md`](template.sd-request.md), [`reference.approval-process.md`](reference.approval-process.md), [`reference.sd-links.md`](reference.sd-links.md).
>
> **Отделы-согласующие (полные названия, без аббревиатур):** Отдел архитектуры, Отдел информационной безопасности, Отдел инфраструктурного развития. Названия отделов универсальны; в конкретной организации сопоставь их с фактическими подразделениями/ролями.

## Ключевой принцип: согласование ведёт пользователь

Заявки в Service Desk создаёт и ведёт **пользователь вручную**. Роль агента:
- подготовить **лёгкую** заявку по шаблону (обзор/цель/процесс/ссылки на основную документацию);
- зафиксировать статусы в `integration-request-plan` (раздел «Процесс согласования») и журнале связанных заявок;
- по просьбе пользователя — обновить статус заявки в накопителе.

Агент **не** создаёт тикеты в Service Desk за пользователя и не меняет их статус там.

## Когда применять

- После завершения фазы «Проектирование», когда документация готова к согласованию.
- Для подготовки заявок на согласование с Отделом архитектуры, Отделом информационной безопасности, Отделом инфраструктурного развития.
- Для консультации по порядку и составу согласования.

## Порядок согласования

| Шаг | Отдел | Когда | Зависимость |
|---|---|---|---|
| 1 | **Отдел архитектуры** | Первым — заявка на согласование архитектуры интеграции | — |
| 2 | **Отдел информационной безопасности** | Обязательно; запускается параллельно с Отделом архитектуры (не дожидаясь его завершения) | можно параллельно с шагом 1 |
| 3 | **Отдел инфраструктурного развития** | По требованию Отдела архитектуры и/или Отдела информационной безопасности (создание УЗ/доступов/инфраструктуры) | по необходимости |

Детали и расширяемость — в [`reference.approval-process.md`](reference.approval-process.md). Ссылки на создание заявок — в [`reference.sd-links.md`](reference.sd-links.md).

## Алгоритм фазы «Согласование»

1. Убедись, что артефакты фазы 2 готовы (карточка проекта, тех-документация).
2. Подготовь лёгкую заявку для Отдела архитектуры по [`template.sd-request.md`](template.sd-request.md): обзор, цель, процесс, ссылки на основную документацию (детали — по ссылкам, не в теле заявки).
3. Передай заявку пользователю; он создаёт тикет в Service Desk (ссылки — `reference.sd-links`).
4. Зафиксируй заявку в журнале связанных заявок и в разделе «Процесс согласования» накопителя.
5. Параллельно подготовь заявку для Отдела информационной безопасности (она обязательна); при необходимости — для Отдела инфраструктурного развития.
6. Отражай статусы по мере подтверждения пользователем (`Создана`/`На рассмотрении`/`Согласовано`/`Отклонено`).
7. Когда все необходимые заявки согласованы — процесс проектирования и согласования **завершён**. Зафиксируй итог; после этого пользователь может инициировать разработку интеграции как отдельный этап.

## Принципы

- **Лёгкая заявка:** в теле заявки — только обзор/цель/процесс и опц. изображения; детали (карточка, C2, окружения, API, модель данных) — по ссылкам. Не дублируй документацию в заявке.
- **DLP:** в заявке и reference — плейсхолдеры для внутренних URL/имён; реальные ссылки подставляет пользователь.
- **Расширяемость:** этапы согласования ведутся таблицей — отделы можно добавлять/убирать.

## Чеклист (завершение процесса)

- [ ] Заявка для Отдела архитектуры подготовлена (лёгкая, со ссылками на документацию)
- [ ] Заявка для Отдела информационной безопасности подготовлена (обязательна; запускается параллельно с Отделом архитектуры)
- [ ] Заявка для Отдела инфраструктурного развития подготовлена (если требуется по итогам Отдела архитектуры / информационной безопасности)
- [ ] Статусы заявок отражены в `integration-request-plan` и журнале связанных заявок
- [ ] Все необходимые согласования получены (пользователь подтвердил)
- [ ] Итог зафиксирован; отмечена готовность к разработке
- [ ] DLP: внутренние ссылки/имена — плейсхолдеры в шаблонах
