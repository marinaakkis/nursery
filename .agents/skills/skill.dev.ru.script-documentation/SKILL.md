# Документация скриптов и утилит

Применяй этот скилл при создании или актуализации документации для любых скриптов:
CLI-утилит, PowerShell-командлетов, bash-скриптов, Node.js-скриптов автоматизации.

Приоритет правил этого скилла над общими инструкциями по документации.

---

## 1. Обязательная структура README

Каждый скрипт (или логическая группа скриптов) должен иметь раздел с фиксированной структурой:

```
## <Название скрипта / группы>

### 1. Общая информация
### 2. Установка          ← только если требуется предварительная установка
### 3. Запуск скрипта
```

Дополнительные разделы добавляй **после** раздела 3, если они обоснованы:

| Раздел | Когда добавлять |
|---|---|
| **Тесты** | Есть отдельный тест-файл |
| **Управление** | Скрипт имеет несколько режимов (включить/отключить/удалить) |
| **Типовые сценарии** | Документируется несколько взаимосвязанных скриптов |
| **Надёжность** | Скрипт использует retry, circuit-breaker, timeout |
| **Безопасность** | Скрипт работает с секретами, токенами, сетью |

### 1.1 Общая информация

Должна содержать:
- **Одно-два предложения** о назначении скрипта (что делает, зачем).
- Перечень того, **что именно происходит** при запуске (нумерованный список если шагов > 2).
- Указание на автозапуск если применимо (например: «Запускается автоматически при `git merge`»).

**Не включать:** историю изменений, ссылки на рабочие задачи (r-XXX, t-XXX), ссылки на содержимое `docs/dev-requests/**`.

### 1.2 Установка

Включай раздел только если скрипт требует предварительной установки зависимостей или системных компонентов.

Если установка не нужна — раздел **опускай целиком** (не пиши «Установка не требуется»).

### 1.3 Запуск скрипта

- Показывай команды для **всех поддерживаемых платформ** (Windows / Linux / macOS).
- Разделяй платформы заголовком (`**Windows:**`, `**Linux / macOS:**`) или кодовым блоком с комментарием.
- Включай **dry-run / preview** команду если она есть.
- Добавляй **таблицу опций** если флагов больше двух.

## 2. Языковое единообразие

### 2.1 Основной язык

Весь текст документации — **на русском языке**. Исключения:

| Оставить на английском | Пример |
|---|---|
| Имена собственные UI-элементов сторонних инструментов | `Settings → Community plugins` (Obsidian UI) |
| Термины-имена собственные, для которых нет устоявшегося RU-перевода | `vault` (Obsidian), `pipeline`, `circuit-breaker` |
| Команды, пути, имена файлов, переменные | `node scripts/publish.mjs --confirm` |
| Технические идентификаторы в коде | `docsStorage.apiToken`, `$VaultPath` |

Для сторонних UI-терминов, если продукт локализован, используй **терминологию продукта**.
Например: Obsidian называет папку с заметками «vault» — используй `vault`, не «хранилище».

### 2.2 Пользовательские сообщения в скриптах

Правила для `Write-Host`, `Write-Step`, `Write-Warn`, `step()`, `warn()`, `echo` в финальных блоках:

- **Единый язык** во всём блоке сообщений — полностью на русском или полностью на английском. Смешение запрещено.
- Если документация проекта на русском → сообщения на **русском**.
- Стрелки навигации: `→` (не `->`, не `>`).
- Нумерованные шаги: выравнивать пробелами для читаемости.

### 2.3 Идентичность сообщений между платформами

Если один и тот же скрипт существует для нескольких платформ (`.ps1` + `.sh`), финальные сообщения пользователю **должны быть идентичны** по содержанию и порядку шагов.

Допустимые различия только технические: имена переменных (`$VaultPath` vs `$VAULT_PATH`), синтаксис команд.

## 3. Хранение секретов в документации

Явно указывай где хранятся секреты. Никогда не пиши «только через env» если это неверно.

### 3.1 Принципы

| Тип данных | Где хранить | Как документировать |
|---|---|---|
| Токены и credentials сервисов | Gitignored локальный JSON-файл проекта | Указать точный файл и поле: `<файл> → <свойство>` |
| Пароли и переменные для docker-compose | `.env` (gitignored) | Указать точное имя переменной: `VAR_NAME` в `.env` |
| URLs, пути, project keys сервисов | Gitignored локальный JSON-файл проекта | Указать конкретное свойство-путь |

Всегда указывай **конкретное место** хранения, а не абстрактное «в конфигурации» или «в env».

### 3.2 Шаблоны примеров

Для каждого способа хранения предоставляй шаблон рядом со скриптом:
- `*.example.json` — шаблон для JSON-конфигурации (gitignored файлы).
- `.env.*.example` — шаблон для docker-compose переменных.

Шаблон должен содержать **все поля** соответствующей секции с заглушками-значениями (`null` или `<placeholder>`).

### 3.3 Пример применения (publish-dev-requests-docs)

В проекте `publish-dev-requests-docs` токены хранятся в секции `docsStorage` файла `.project-metadata.local.json`.
`docsStorage` — это одна из секций этого файла; со временем могут добавиться и другие секции под другие задачи.

```json
// .project-metadata.local.json (gitignored)
{
  "docsStorage": {
    "backend": "obsidian",
    "apiKey": "<вставить API-ключ из Local REST API>"   // токен сервиса — здесь, не в .env
  }
}
```

Шаблоны: `.project-metadata.docs-storage.<backend>.example.json` рядом с setup-скриптом.

## 4. Терминология

### 4.1 Использование терминов-омонимов

Если термин может означать разные вещи (пример: «хранилище» может быть git-репозиторием, S3-бакетом, Obsidian vault) — при первом упоминании уточняй контекст.

| Ситуация | Как писать |
|---|---|
| Термин продукта (Obsidian vault) | Использовать термин продукта: `vault` |
| Общее понятие хранилища документов | `хранилище` |
| Смешение контекстов в одном README | Добавить пояснение в первом упоминении: «хранилище (vault в терминах Obsidian)» |

### 4.2 Запрещённые упоминания в постоянных артефактах

Документация скриптов является **постоянным артефактом**.

| | Правило |
|---|---|
| ❌ | Ссылки на содержимое `docs/dev-requests/**` — запрещены (эфемерные рабочие артефакты) |
| ✅ | Ссылки на постоянную документацию `docs/*` вне `docs/dev-requests/` — разрешены |

## 5. Структура install-docs-storage (пример применения)

Для папок установки/конфигурации хранилищ используй шаблон:

```
install-docs-storage/
  <backend>/
    README.md                                    ← инструкция по установке
    setup-<backend>.win.ps1                      ← скрипт Windows
    setup-<backend>.lin-mac.sh                   ← скрипт Linux/macOS
    .project-metadata.docs-storage.<backend>.example.json  ← шаблон credentials
    .env.<backend>.example                       ← шаблон docker-compose vars (если нужен)
    <backend>.docker-compose.yml                 ← только если docker-based
```

README в папке backend должен содержать:
1. Общая информация (назначение хранилища, когда применять)
2. Установка (команды для Win/Linux/macOS)
3. Настройка (`.project-metadata.local.json`, поля `docsStorage`)
4. Публикация (команда запуска скрипта публикации)

## 6. Автоматизированные шаги в setup-скриптах

Setup-скрипты должны **добавлять, а не перезаписывать** конфигурацию. Паттерн:

```powershell
if (-not $meta.PSObject.Properties['docsStorage'] -or $null -eq $meta.docsStorage) {
    # добавить
} else {
    # пропустить — сообщить пользователю
}
```

Документировать в `.DESCRIPTION`:
- Что скрипт делает шаг за шагом (нумерованный список).
- Что **остаётся сделать вручную** после запуска.

## 7. Чеклист перед сдачей

- [ ] Каждый скрипт / группа имеет структуру с разделами 1–3 (и дополнительными если нужны).
- [ ] Весь текст на одном языке; UI-термины сторонних продуктов — на языке продукта.
- [ ] Платформенные скрипты (`.ps1` + `.sh`) имеют идентичные финальные шаги.
- [ ] Нет ссылок на r-XXX, t-XXX, ADR-XXX в постоянной документации.
- [ ] Место хранения секретов указано точно (`.project-metadata.local.json` или `.env`).
- [ ] Стрелки навигации `→`, не `->` и не `>`.
- [ ] Команды показаны для Windows и Linux/macOS где применимо.
- [ ] Раздел «Установка» опущен если установка не требуется.
- [ ] Нет упоминания DLP-gate, doc-sync или других удалённых стадий если pipeline изменился.
- [ ] Актуальные пути к тестам: `test/` подпапка если тесты вынесены.
