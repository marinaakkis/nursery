# Универсальные стандарты кодирования

Применяй эти правила как **минимальный baseline** для всех языков и стеков в репозитории.

> **Приоритет применения:**
> 1. **Явные соглашения проекта и инструменты форматирования/линтинга** (`.editorconfig`, `prettier`, `ruff`, `gofmt`, `rustfmt`, `pyproject.toml`, team agreement и т.д.) — всегда первые; они перекрывают этот документ и языковые скиллы.
> 2. **Языковый скилл** для конкретного стека — переопределяет baseline там, где это явно указано.
> 3. **Этот документ** — умолчание, когда ни проект, ни стек не задают иного.
>
> **Адаптация под стек:** регистр идентификаторов, синтаксис комментариев, стиль скобок и длина строки **существенно различаются между языками**. .NET, Python (PEP 8), Go, Rust, Java, Kotlin имеют устоявшиеся конвенции сообщества. Там, где стек явно задаёт иное — следуй стеку, а не этому документу. Для Go/Rust всегда приоритет у языкового скилла или конвенции проекта.
>
> **Дочерние стековые скиллы:** `skill.dev.ru.dotnet-csharp-standards`, `skill.dev.ru.frontend-ts-react-standards`.
>
> **Примеры и краевые случаи:** `reference.md`.

## Именование

### Общая таблица

| Элемент | Стиль | Пример |
|---|---|---|
| Класс, тип, компонент | PascalCase | `UserProfile`, `OrderService` |
| Интерфейс | `I` + PascalCase | `IRepository`, `IUserService` |
| Публичный метод / функция | PascalCase или camelCase — **зависит от стека** (см. языковый скилл) | .NET: `GetUser` / TS/JS: `getUser` |
| Параметр, локальная переменная | camelCase | `userId`, `orderItem` |
| Приватное поле | camelCase с префиксом `_` | `_repository`, `_maxRetry` |
| Публичная константа | PascalCase (или SCREAMING_SNAKE_CASE — см. языковый скилл) | `MaxRetryCount` / `MAX_RETRY_COUNT` |
| Приватная константа | как приватное поле: `_camelCase` (или стековый стиль — см. языковый скилл) | `_defaultTimeout` / `_DEFAULT_TIMEOUT` |
| Generic / template-параметр | префикс `T`, осмысленное имя | `TKey`, `TValue`, `TResult` |
| Значение enum | PascalCase, без повтора имени типа | `Color.Red`, не `ColorRed` |
| Обработчик события | `on`-префикс (frontend) / `On`-префикс или `Handler`-суффикс (backend) | `onClick`, `OnClose`, `SubmitHandler` |

### Python (PEP 8) — отклонения от baseline

| Элемент | Baseline | Python |
|---|---|---|
| Функция / метод | PascalCase | **snake_case**: `get_user`, `create_order` |
| Параметр, переменная | camelCase | **snake_case**: `user_id`, `order_item` |
| Приватное поле | `_camelCase` | **`_snake_case`**: `_repository`, `_max_retry` |
| Константа | PascalCase или SCREAMING\_SNAKE\_CASE | **SCREAMING\_SNAKE\_CASE**: `MAX_RETRY_COUNT` |
| Интерфейс (Protocol / ABC) | `I`-префикс | **без префикса**: `Repository`, `Iterable` |

«Сильная приватность» (name mangling): `__snake_case` — для членов, к которым не должны обращаться подклассы.

### Дополнительные правила

**Классы и типы:** существительное или прилагательное(ые) + существительное. Избегай лишних суффиксов «типа объекта» (`ManagerHelper`, `ServiceUtil`). Шаблоны проектирования — желательно отражать постфиксом: `Builder`, `Factory`, `Proxy`, `Decorator`, `Callback`.

**Интерфейс / эталонная реализация:** `IOrderService` / `OrderService`; не дублируй смысл в обоих именах.

**Enum:** простой тип — имя в единственном числе; флаги — множественное число. Значения в PascalCase без повтора имени enum.

**Boolean:** утвердительная форма; предпочтительные префиксы `Is`, `Can`, `Has`, или форма вроде `Enabled`, `Active`, `Allowed`.

**Счётчики:** суффикс `Count`.

**Generic-параметры:** порядок — сначала входные типы, затем результат: `TCommand, TResult`.

**Лямбды и колбэки:** осмысленные имена параметров (`orderItem`, `serviceProvider`), а не однобуквенные (`x`, `ch`, `sp`). Однобуквенные допустимы только для счётчиков в очевидных числовых преобразованиях.

**Методы:** имя отражает результат для методов с возвращаемым значением (`GetOrderState`, `LoadEntities`).

**Не кодируй тип в имени** (венгерская нотация): `strName` или `intCount` — антипаттерн.

## Запросные модели (постфиксы)

Неполный набор полей при создании/обновлении отражай в имени:

| Ситуация | Постфикс |
|---|---|
| Создание | `ToCreate` |
| Обновление (полное) | `ToUpdate` |
| Частичное обновление | `Patch` |
| Создание или обновление | `ToCreateOrUpdate` |
| Удаление | Постфикс **не используется**; передаётся идентификатор/контракт удаления по соглашению проекта (`ToDelete` не вводится как стандарт) |

## Структура типа

**Порядок членов по уровню доступа:** `public` → `protected internal` → `protected` → `private`.

**Порядок по виду:** поля → свойства → конструкторы → методы.

> **Python:** нет ключевых слов доступа — видимость только по соглашению (`_name` — protected-by-convention, `__name` — name mangling). Рекомендуемый порядок: атрибуты класса → `__init__` → dunder-методы (`__str__`, `__repr__` и т.д.) → публичные методы → приватные методы (`_`).

**Интерфейсы:** узкие (ISP — один концентрированный контракт); «бог-интерфейсы» — антипаттерн.

**Локальные переменные:** объявлять близко к месту использования; инициализировать сразу; одна переменная на оператор объявления.

## Методы и функции

- **≤5 параметров**; при большем числе — DTO, record или объект параметров.
  > **Python:** `self` и `cls` в счёт не входят.
- **Ориентир длины тела** — ~90 строк (языковый скилл может устанавливать другой лимит, например 50). Короче — лучше.
- **Именованные аргументы** — там, где повышают ясность вызова; API, непонятное без имён, лучше перепроектировать.
- **Предпочтительно** явный возврат над out/ref-мутациями; минимизируй побочные эффекты.
- **Необязательные параметры** — предпочтительно заменять перегрузками, если так читаемее.
  > **Python:** перегрузки через `@overload` (typing) или аргументы со значением по умолчанию — по читаемости.

## Документация и комментарии

**Язык:** русский, если проект не задаёт иное; для публичного API наружу организации — согласовать отдельно.

**Оформление:** предложения с заглавной буквы; в конце — точка (или `?` для boolean-свойств).

**Что документировать минимально:** классы, интерфейсы, публичные методы и свойства. Библиотеки и публичные пакеты — обязательно.

**Две политики проекта:**
- *Legacy / аутсорс:* полные XML/JSDoc-комментарии на все публичные сущности.
- *Новые проекты силами команды:* summary не обязателен везде; комментируй неочевидную логику, скрытые ограничения, workaround-ы.

**Синтаксис комментариев:** используй синтаксис конкретного языка. Для C-подобных языков — `//` для пояснений; блочные `/* */` не рекомендуются без необходимости.

> **Python:** для документирования модулей, классов и функций — docstring (`"""..."""`), а не `//`. Форматы: Google Style, NumPy или Sphinx — по договорённости проекта. Инлайн-комментарии — `#` (аналог `//`); блочные `#`-комментарии над кодом допустимы.

**Задачи и TODO:** `#warning` или задача в трекере вместо незакрытых `// TODO`. Формат с номером: `// TODO #1234`.

**`returns`:** уточняй краевые случаи («`-1`, если не найдено», «`null`, если пусто»).

**Наследование:** `<inheritdoc/>` / `@override` там, где описание уже есть в базовом классе/интерфейсе.

## Форматирование

| Параметр | Значение по умолчанию | Переопределения по стеку |
|---|---|---|
| Отступ | 4 пробела | Go: табы |
| Длина строки | ≤150 символов | TypeScript: 120 / Python PEP 8: 79 / Python Black: 88 / Go,Rust: по инструментам стека |
| Скобки | Allman (baseline) | TypeScript/JS: Egyptian (та же строка) / **Python: нет фигурных скобок — блоки через отступ** / Go,Rust: по языковым конвенциям |
| Одна инструкция на строку | да | — |

**Операторы:** пробелы вокруг бинарных операторов; после `,` и `;` — пробел.

**`if`/`else`/циклы:** тело всегда в фигурных скобках `{}`; при многострочном условии — обязательно.

> **Python:** фигурных скобок нет — блоки определяются отступом; правило об обязательных `{}` не применяется.

**Присваивание в условии `if`:** избегать.

**Инвертирование `if` (guard clause):** при возможности предпочитай ранний выход (`return` / `throw` / `continue` / `break`) вместо глубокой вложенности — обрабатывай граничный или невалидный случай первым и выходи, основной путь оставляй без вложенности:

```csharp
// ❌ вложенность растёт
if (isValid) {
    if (hasPermission) {
        // основная логика
    }
}

// ✓ guard clause — основной путь читается прямо
if (!isValid) return;
if (!hasPermission) throw new UnauthorizedException();
// основная логика
```

**Инициализаторы объектов:** одна строка, если коротко; иначе — одно свойство на строку.

**Fluent / цепочки:** переносы перед `.`; продолжение с отступом.

## Константы и литералы

- Магические числа/строки → именованные константы.
- Литералы `0` и `1` обычно допустимы без именования.
- Не разбрасывай одну и ту же строку по коду — используй константу или ресурс.
- Пустая строка — через стандартную константу языка/платформы.

## Видимость и изменяемость

- Минимальная видимость: начинай с наиболее ограничивающего модификатора.
- Публичные изменяемые поля — только при явной необходимости (interop, struct); по умолчанию наружу — только через свойства / геттеры.
- Типы без задуманного наследования — при возможности помечай как `sealed` / `final`.

> **Python:** ключевых слов `private`/`sealed`/`final` нет — видимость только по соглашению: `_name` (не использовать извне по договорённости), `__name` (name mangling). Для явной неизменяемости используй `Final` и `@final` из модуля `typing`.

## Валидация

- **Один исход** → ранние `return false`, финальный `return true`.
- **Несколько сообщений/условий** → накапливать результат (флаг или список ошибок), финальный `return`.

## Перед сдачей (чеклист)

1. Имена согласованы с таблицами; приватные поля/константы оформлены по стековому правилу.
2. Порядок членов и уровней доступа выдержан.
3. Параметров ≤5; длина метода — в пределах ориентира.
4. Форматирование сначала проверено по конфигам проекта (`.editorconfig`, formatter/linter), затем по языковому скиллу, и только потом по baseline этого документа.
5. Постфиксы запросных моделей (`ToCreate`, `ToUpdate`, `Patch`, `ToCreateOrUpdate`) применены по таблице; для удаления `ToDelete` не используется.
6. Магические числа и строки не размазаны без нужды.
7. Документация соответствует политике проекта (legacy / новый / библиотека).
8. Видимость — минимально необходимая; публичных изменяемых полей нет без причины.
9. Валидация — по выбранному паттерну (early return или accumulate).
