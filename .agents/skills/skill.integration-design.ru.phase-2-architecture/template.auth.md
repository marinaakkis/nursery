# Аутентификация и авторизация: <[Система A] ↔ [Система B]>

## Выбор схемы

| N | Связь (Источник→Приёмник) | Схема | Комментарий |
|---|---|---|---|
| 1 | [Система A] → [Шлюз] | OAuth2.0 client_credentials через OAuth2.0 Access Token Provider | предпочтительная межсервисная |
| 2 | [Шлюз] → [Система B] | Basic Auth | у целевой системы нет OAuth2.0/OIDC |

Допустимые схемы: `OAuth2.0 (через Access Token Provider)` / `Basic Auth (±роли)` / `mTLS` / `API key`.

> «OAuth2.0 Access Token Provider» — обобщённое название сервиса-провайдера токенов доступа (Identity Provider, выдающего OAuth2.0-токены). В рабочем экземпляре подставь название конкретного провайдера, используемого в организации. В основе схемы — протокол OAuth2.0 (grant `client_credentials`).

## Блок A. OAuth2.0 client_credentials (OAuth2.0 Access Token Provider или иной Identity Provider)

> Предпочтительная межсервисная схема. Получение токена: запрос к token-эндпоинту провайдера (узнаётся через OIDC discovery `<issuer>/.well-known/openid-configuration`, поле `token_endpoint`), `grant_type=client_credentials`, `client_id` + `client_secret`; использование: заголовок `Authorization: Bearer <access_token>`; валидация токена/ролей — на стороне получателя.

### Таблица доступов (Service Account → сервис → scope/роль)

| N | ClientId / Service Account | Целевой сервис | Scope / роль / ресурс | Статус | Примечание |
|---|---|---|---|---|---|
| 1 | `client-a-example` | `service-b-example` | `resource:read` | существует | |
| 2 | `client-gateway-example` | `service-b-example` | `resource:write` | требуется создать | заявка в Отдел архитектуры / Отдел инфраструктурного развития |

- **Статус** ∈ `существует` / `требуется создать`.
- `client_secret` **не указывается** в документации (выдаётся/хранится в защищённом хранилище).

> Некоторых клиентов (ClientId/Service Account) или доступов может не быть — их создание требует обращения в Отдел архитектуры и/или Отдел инфраструктурного развития.
