## Полный пример эндпоинта

### Создание пользователя

Создаёт нового пользователя и возвращает его карточку.

#### Запрос

1. **HTTP-метод:** `POST`
2. **Путь:** `/api/v1/users`
3. **Параметры:**

| N | Параметр | Тип параметра | Название | Тип данных | Формат | Комментарий |
|---|---|---|---|---|---|---|
| 1 | `X-Request-Id` | `header` | Идентификатор запроса | `string` | GUID | Нестандартный заголовок трассировки |
| 2 | `locale?` | `cookie` | Локаль пользователя | `string` | RFC 5646 | Опционально, влияет на локализацию сообщений |

4. **Content-Type:** `application/json`
5. **Тело запроса:**

| N | Поле | Название | Тип | Формат | Описание |
|---|---|---|---|---|---|
| 1 | `name` | Имя пользователя | `string` | 1-128 chars | Обязательное поле |
| 2 | `email` | Email пользователя | `string` | email | Обязательное поле |

#### Ответ

1. **Content-Type:** `application/json`
2. **Тело ответа:**

| N | Поле | Название | Тип | Формат | Описание |
|---|---|---|---|---|---|
| 1 | `id` | Идентификатор пользователя | `string` | GUID | Уникальный ID |
| 2 | `name` | Имя пользователя | `string` | 1-128 chars | |
| 3 | `email` | Email пользователя | `string` | email | |

3. **Статусы:**

| N | Статус | Условие | Тело ответа | Комментарий |
|---|---|---|---|---|
| 1 | `201` | Пользователь успешно создан | `UserDto` | |
| 2 | `400` | Ошибка валидации входных данных | `ValidationErrorDto` | |
| 3 | `401` | Отсутствует или невалиден токен доступа | `ErrorDto` | |
| 4 | `403` | Недостаточно прав для операции | `ErrorDto` | |
| 5 | `409` | Пользователь с таким email уже существует | `ErrorDto` | |

## Краевые случаи Content-Type

| Сценарий | Что указать в описании запроса | Что указать в описании ответа |
|---|---|---|
| `multipart/form-data` (загрузка файлов) | Укажи `Content-Type: multipart/form-data`, в теле запроса явно перечисли текстовые поля и файл(ы) | Обычно `application/json` с метаданными результата |
| Бинарный запрос (`application/octet-stream`) | Укажи бинарный `Content-Type`; в таблице тела используй `—`, если структура не JSON | Опиши ожидаемый код и модель ошибки |
| Бинарный ответ (файл) | Запрос описывается обычным образом | Укажи `Content-Type` бинарного файла (`application/pdf`, `image/png`, и т.д.), для тела ответа используй `—` |
| Streaming (`text/event-stream`) | Укажи формат подписки и ограничения | Отдельно зафиксируй, что ответ потоковый, а не конечный JSON-документ |
| Пагинация списка | Для `GET` укажи `query`-параметры (`page`, `size`, `sort`) и значения по умолчанию | Опиши метаданные пагинации (`total`, `page`, `size`) в теле ответа |

## Частые ошибки (good/bad)

### 1) Стандартные заголовки в таблице параметров

- **Bad:** добавлять `Authorization` в таблицу параметров как `header`.
- **Good:** документировать `Authorization` на уровне сервиса/контракта, а в таблице оставлять только endpoint-specific параметры.

### 2) Пропуск `?` для необязательных параметров

- **Bad:** `filter` (без суффикса) при фактической необязательности.
- **Good:** `filter?` в колонке «Параметр» + комментарий при необходимости.

### 3) Статус без условия

- **Bad:** указывать только `400` без условия.
- **Good:** писать конкретное условие, например: `Ошибка валидации входных данных`.

### 4) Пропуск явного `—` при отсутствии тела

- **Bad:** оставлять пустой блок «Тело запроса/ответа».
- **Good:** явно указывать `—`, если тело отсутствует.
