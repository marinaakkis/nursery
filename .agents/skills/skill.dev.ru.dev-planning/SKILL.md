# Dev-Planning: стандарт планирования разработки

Скилл задаёт **единый подход** к планированию реализации: от формирования dev-plan до детализации dev-задач. Применяется **до** начала кодирования, когда набор архитектурных артефактов (requirements, C4, ADR, DDS) уже сформирован.

Dev-plan всегда формируется в контексте конкретного dev-request: номер запроса (`r-<nnn>`) используется как корневой идентификатор и для dev-plan, и для dev-task.

**Терминология:** `dev-task` — конкретная задача разработки внутри dev-plan, полученная из бизнес-задачи (task). `task` намеренно зарезервирован для бизнес-уровня.

**Приоритет:** явные инструкции пользователя и правила репозитория → этот скилл → общая эвристика.

**Сопутствующие файлы:**

- Полные markdown-шаблоны всех артефактов — [reference.md](reference.md).
- Скрипт синхронизации dev-plan из dev-task-файлов — [scripts/sync-dev-plan.py](scripts/sync-dev-plan.py).

## Когда применять

- Пользователь просит создать план разработки по готовой документации.
- Пользователь создаёт или обновляет dev-plan или dev-task.
- Нужно понять структуру planning-артефактов, логику changelog, статус или версию.

**В ai-sdlc процессе:** применяется только после апрувленного дизайна (Phase 2 / `skill.ai-sdlc.ru.phase-3-planning`); входные артефакты берутся из `docs/dev-requests/dev-request.r-<nnn>.<system-request-name>/design/`, а не из глобальных `docs/`.

## Структура каталогов

```
docs/dev-requests/
└── dev-request.r-<nnn>.<system-request-name>/
    └── dev-planning/
        └── dev-plan.r-<nnn>.<system-dev-plan-name>/              # Директория одного dev-plan
            ├── dev-plan.r-<nnn>.<system-dev-plan-name>.md        # Главный файл плана разработки
            ├── dev-task.r-<nnn>.t-001.<system-dev-task-name>.md  # Dev-задачи на том же уровне
            ├── dev-task.r-<nnn>.t-002.<system-dev-task-name>.md
            └── ...
```

Где:

- `r-<nnn>` — трёхзначный номер dev-request (`r-001`, `r-002`, …); совпадает с номером родительского `dev-request.r-<nnn>`.
- `t-<nnn>` — трёхзначный порядковый номер dev-задачи (`t-001`, `t-002`, …), уникальный в рамках одного dev-plan.
- `<system-dev-plan-name>` — `kebab-case` системное имя плана (идентификатор в имени директории и файла).
- `<system-dev-task-name>` — `kebab-case` системное имя dev-задачи.

## Именование файлов

| Тип | Маска | Расположение |
|-----|-------|--------------|
| Dev-plan (директория) | `dev-plan.r-<nnn>.<system-dev-plan-name>/` | `docs/dev-requests/dev-request.r-<nnn>.<system-request-name>/dev-planning/` |
| Dev-plan (файл) | `dev-plan.r-<nnn>.<system-dev-plan-name>.md` | внутри директории dev-plan |
| Dev-task | `dev-task.r-<nnn>.t-<nnn>.<system-dev-task-name>.md` | внутри директории dev-plan |

Правила:

- Все части имён в lowercase `kebab-case` (`a-z`, `0-9`, `-`).
- Пробелы, подчёркивания, кириллица в именах файлов не допускаются.
- Номера `r-<NNN>` и `t-<NNN>` строго **трёхзначные** (`001`, `002`, …) с ведущими нулями, монотонные, без повторов в своей области.

## Строгий контракт именования создаваемых planning-документов (MUST)

При создании новых planning-артефактов агент обязан проверять имя на соответствие строгим regex:

- Dev-plan директория: `^dev-plan\.r-[0-9]{3}\.[a-z0-9]+(?:-[a-z0-9]+)*$`
- Dev-plan файл: `^dev-plan\.r-[0-9]{3}\.[a-z0-9]+(?:-[a-z0-9]+)*\.md$`
- Dev-task: `^dev-task\.r-[0-9]{3}\.t-[0-9]{3}\.[a-z0-9]+(?:-[a-z0-9]+)*\.md$`

Если имя не проходит regex:

- файл не создавать, пока имя не приведено к требуемому шаблону;
- не использовать альтернативные префиксы/суффиксы и свободные форматы имён;
- расширение для planning-документов строго `.md`.

## Структура `dev-plan.r-<nnn>.<system-dev-plan-name>.md`

Обязательные разделы:

| Раздел | Содержание |
|--------|-----------|
| **Статус** | Одно из: `Планирование` / `Разработка` / `Завершено`. |
| **Версия** | Версия плана в формате `<major>.<minor>` (начиная с `1.0`). |
| **Основные компоненты** | Таблица компонентов системы. |
| **Dev-задачи** | Таблица dev-задач со ссылками. |
| **Changelog** | Таблица изменений dev-plan. |

Контракт таблицы Основных компонентов:

`№ | Компонент | Ответственность | Ссылка на docs | Комментарий`

Контракт таблицы Dev-задач:

`№ | Код | Аннотация | Версия | Ссылка | Комментарий`

Контракт таблицы Changelog (dev-plan):

`№ | Дата | Версия | Описание изменения | Комментарий`

## Структура `dev-task.r-<nnn>.t-<nnn>.<system-dev-task-name>.md`

Обязательные поля:

| Поле | Описание |
|------|----------|
| **Системное название** | `kebab-case` имя dev-задачи (совпадает с `<system-dev-task-name>` в имени файла). |
| **Код dev-задачи** | `r-<nnn>.t-<nnn>` (тот же `r-<nnn>`, что у родительского dev-request). |
| **Название** | Человекочитаемое локализованное название. |
| **Версия** | `<major>.<minor>`, начиная с `1.0`. |
| **Аннотация** | Актуальное краткое описание. |
| **Описание** | Актуальное полное описание. |

Обязательные разделы:

| Раздел | Содержание |
|--------|-----------|
| **Цель** | Что реализуется в задаче. 1–2 предложения. |
| **Входные условия** | Что должно быть готово перед стартом: предыдущие задачи, данные, окружение. |
| **Описание** | Полное описание: что именно делается, какие компоненты затрагивает, ссылки на требования/ADR/DDS. |
| **Шаги реализации** | Конкретные действия с ожидаемым результатом каждого. Без неоднозначностей. |
| **Тест-кейсы** | Сценарии для проверки: позитивные и негативные. Таблица: Сценарий / Вход / Ожидаемый выход / Уровень. |
| **Acceptance Criteria** | Чеклист готовности; всегда включает build, тесты, линтеры, соответствие дизайну, security-review. |
| **Выходные артефакты** | Файлы, создаваемые / изменяемые / удаляемые в задаче. |
| **Changelog** | Таблица изменений dev-задачи. |

Полные шаблоны с примерами — [reference.md](reference.md).

Контракт таблицы Changelog (dev-task) — идентичен dev-plan.

## Универсальный контракт таблиц

Как и во всех скиллах проекта:

- Первый столбец всегда `№` (нумерация строк).
- Последний столбец всегда `Комментарий`.

## Логика Changelog

Единая для dev-plan и dev-task:

| Ситуация | Действие |
|----------|----------|
| Создание документа | Добавить первую строку Changelog с текущей датой, версией `1.0` и описанием создания. |
| Этап `Планирование` — правки | Редактировать содержимое без новой строки в Changelog, версия не меняется. |
| Этап `Разработка` — критическое изменение | Новая строка Changelog + инкремент Версии + обновление Аннотации в текущем документе. |
| Изменение dev-task | После обновления dev-task — запустить `sync-dev-plan.py` или вручную обновить строку этой dev-задачи в таблице Dev-задач dev-plan (Аннотация, Версия). |

Критическое изменение — любое, которое меняет смысл, объём или контракт описания (переработка требований, изменение scope, смена ответственного компонента и т.п.).

## Логика Статуса и Версии dev-plan

| Переход | Действие |
|---------|----------|
| Любой → Любой (кроме ниже) | Новая строка Changelog с описанием смены статуса. |
| `Завершено` → `Планирование` или `Разработка` | Инкремент `major` версии + новая строка Changelog. |

## Скрипт синхронизации

Расположение: `docs/dev-requests/dev-request.r-<nnn>.<system-request-name>/dev-planning/dev-plan.r-<nnn>.<name>/scripts/sync-dev-plan.py`  
(копируется из `.agents/skills/skill.dev.ru.dev-planning/scripts/sync-dev-plan.py` при старте проекта).

Запуск из директории dev-plan:

```bash
python scripts/sync-dev-plan.py <path-to-dev-plan.md>
```

Что делает:

1. Находит все файлы `dev-task.r-*.t-*.*.md` в той же директории, что и dev-plan.
2. Для каждого извлекает `Код dev-задачи`, `Аннотация`, `Версия` и относительный путь.
3. Находит соответствующую строку в таблице Dev-задач dev-plan по коду.
4. Если `Аннотация` или `Версия` изменились — обновляет ячейки и добавляет строку в Changelog dev-plan с датой и описанием изменения.
5. Выводит в консоль список изменённых dev-задач.

## Процесс создания planning-артефактов

1. Прочитать архитектурные артефакты. Путь зависит от контекста:
   - **ai-sdlc процесс** (совместно с `skill.ai-sdlc.ru.phase-3-planning`): читать из `docs/dev-requests/dev-request.r-<nnn>.<system-request-name>/design/` (C4, DFD, Sequence, ADR, api-requirements, test-strategy) и `docs/dev-requests/dev-request.r-<nnn>.<system-request-name>/research.r-<nnn>.<system-request-name>.md`.
   - **Standalone**: читать из `docs/requirements/`, `docs/api-requirements/`, `docs/c4-diagrams/`, `docs/adr-log/`, `docs/dds-log/`, `docs/architecture.md`.
2. Определить `r-<nnn>` — номер текущего dev-request (из `docs/dev-requests/dev-request.r-<nnn>.<system-request-name>/`).
3. Создать директорию `docs/dev-requests/dev-request.r-<nnn>.<system-request-name>/dev-planning/dev-plan.r-<nnn>.<system-dev-plan-name>/`.
4. Создать `dev-plan.r-<nnn>.<system-dev-plan-name>.md` со статусом `Планирование`, версией `1.0`.
5. Заполнить таблицу Основных компонентов из C2/C3 каталога компонентов.
6. Для каждого функционального требования или компонента создать dev-задачу `dev-task.r-<nnn>.t-<nnn>.<system-dev-task-name>.md` в той же директории.
7. Зарегистрировать все dev-задачи в таблице Dev-задач dev-plan.
8. Скопировать `sync-dev-plan.py` в директорию `scripts/` внутри dev-plan директории.

- [ ] Файл `dev-plan.r-<nnn>.<system-dev-plan-name>.md` существует внутри директории.

## Future-tasks — отложенные задачи

Future-task — задача на будущее, выявленная в ходе работы над dev-request: вне текущего scope, требует отдельного исследования, зависит от внешних условий или слишком велика для текущего цикла.

### Когда создавать

Future-task может быть создан **в любой фазе** (RESEARCH, DESIGN, PLANNING, IMPLEMENTATION, RELEASE GATE, POST-RELEASE):

- По явному запросу пользователя.
- По рекомендации ИИ-агента — обязательно с явным подтверждением пользователя перед созданием файла.
- При обнаружении техдолга вне scope текущего dev-task (техдолг не пишется в код — фиксируется как future-task).
- При выявлении улучшений, требующих отдельного дизайна, согласования или внешней зависимости.

### Папка и именование

| Артефакт | Путь | Маска имени |
|---|---|---|
| Future-task | `docs/dev-requests/future-tasks/` | `future-task.<domain>.<kebab-case-name>.md` |

Допустимые домены: `ai-sdlc`, `arch`, `dev`, `devops`, `integration`, `security`, `governance`.

Regex имени файла: `^future-task\.[a-z][a-z0-9]*\.[a-z][a-z0-9]+(?:-[a-z0-9]+)*\.md$`

### Обязательные разделы future-task

| Раздел | Содержание |
|---|---|
| **Статус** | `Отложено (backlog)` / `В анализе` / `Принято в работу` |
| **Приоритет** | Высокий / Средний / Низкий |
| **Создан** | `YYYY-MM-DD` |
| **Описание** | Что нужно сделать |
| **Мотивация** | Почему важно, какую проблему решает |
| **Ожидаемый результат** | Что изменится после выполнения |
| **Предшественники** | Что должно быть выполнено до начала (ссылки на dev-tasks или другие future-tasks) |

Опциональные разделы (добавлять при наличии данных): варианты стека, требования к окружению, init-скрипты, on-prem вариант.

### Связь с dev-process-plan

После создания future-task — добавить ссылку на него в текущий `dev-process-plan.r-<nnn>.*.md`:

- В раздел **«Итоги фазы»** соответствующей фазы (где была выявлена задача).
- Или в раздел **«Дополнительные исправления (Post-Release)»** со статусом `Отложена`.

### Чеклист future-task

- [ ] Файл создан в `docs/dev-requests/future-tasks/`
- [ ] Имя соответствует маске `future-task.<domain>.<kebab>.md`
- [ ] Заполнены обязательные разделы (Статус, Приоритет, Создан, Описание, Мотивация, Ожидаемый результат, Предшественники)
- [ ] Ссылка на future-task добавлена в dev-process-plan текущего dev-request

> Нормативный baseline: `rule.governance.ru.future-tasks` — применяется через `.cursor/rules/`.
