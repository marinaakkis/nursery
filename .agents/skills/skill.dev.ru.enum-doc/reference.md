# Reference: skill.dev.ru.enum-doc

Расширенные примеры и краевые случаи для документирования перечислений.

## Пример 1: .NET `enum (int)` — статус заявки

**Тип реализации:** `enum (int)`

| N | Системное название | Значение | Название | Комментарий |
|---|---|---|---|---|
| 1 | `Undefined` | `0` | Не определено | Резервное; не использовать явно |
| 2 | `Draft` | `1` | Черновик | Заявка создана, не отправлена |
| 3 | `Submitted` | `2` | Отправлена | Ожидает рассмотрения |
| 4 | `Approved` | `3` | Одобрена | Переход в исполнение |
| 5 | `Rejected` | `4` | Отклонена | Финальный статус; повторная подача невозможна |

## Пример для `[Flags]`-enum

Если используется битовая модель, нулевая семантика может быть `None = 0` вместо `Undefined = 0`.

| N | Системное название | Значение | Название | Комментарий |
|---|---|---|---|---|
| 1 | `None` | `0` | Нет прав | Допустимо для `[Flags]`; отражает пустое множество флагов |
| 2 | `Read` | `1` | Чтение | Бит `0001` |
| 3 | `Write` | `2` | Запись | Бит `0010` |
| 4 | `Delete` | `4` | Удаление | Бит `0100` |

## Правила версионирования enum

### Можно

- Добавлять новое значение в конец перечисления.
- Помечать значение как deprecated с сохранением прежней сериализации.
- Документировать миграционный путь до удаления deprecated-значения.

### Нельзя

- Менять сериализованное значение у уже опубликованного элемента.
- Переиспользовать старое значение для нового бизнес-смысла.
- Удалять публичное значение без миграционного плана и срока поддержки.

## Типичные ошибки (анти-паттерны)

1. Для `record (string)` указано числовое значение (`1`, `2`) вместо строковых литералов.
2. Для `enum (int)` отсутствует `0`-значение (`Undefined`) без явного обоснования.
3. Для `[Flags]` не описана нулевая семантика (`None = 0`) и это приводит к неоднозначной интерпретации.
4. В комментариях отсутствует бизнес-смысл, указано только «Статус 1/2/3».
5. После релиза изменено сериализованное значение (`"submitted"` -> `"sent"`), что ломает совместимость.
