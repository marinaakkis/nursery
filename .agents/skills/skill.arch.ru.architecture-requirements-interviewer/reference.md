# Интервьюер: справочник

## Черновик ответов раунда: `.input/proposals/<theme>-proposal.md`

Используется, пока пользователь **сам** вносит ответы в файл; после сигнала «готово» агент переносит содержимое в файл опроса и в `docs/`.

**Каталог:** **`.input/proposals/`** — отдельная папка для черновиков раундов интервью (не смешивать с ТЗ, `output-templates-proposal.md` и прочими файлами в корне `.input/`). Создай **`.input/proposals/`** при первом раунде, если его ещё нет.

**Имя файла:** `<theme>-proposal.md`, где `<theme>` — латиница **kebab-case**, отражает тему раунда (например `identifiers-mvp-boundaries`, `llm-provider-limits`). Полный путь: **`.input/proposals/<theme>-proposal.md`** (при стандартной раскладке `.input/` / `docs/`).

**Шаблон:**

```markdown
# Черновик ответов: [краткое название раунда]

Скоуп: [модуль / фича]
Раунд / дата: [по желанию]
Файл опроса (куда перенесут ответы): [имя, например interviewer-survey.md]

Инструкция: допишите ответы под каждым **В:** в блоке **О:**. Закончив, напишите в чат, что раунд завершён.

---

## Вопросы этого раунда

### 1

**В:** [формулировка вопроса]

**О:**


### 2

**В:** …

**О:**

```

Агент при старте раунда создаёт файл с заполненными **В:** и пустыми **О:** (или `(заполните)`). Не дублируй десятки вопросов в чате полностью — достаточно списка номеров и ссылки на файл.

## Шаблон файла опроса

Скопируй в **каталог скоупа** под **согласованным именем** (см. `SKILL.md`) и заполни. Заголовок `#` можно сделать специфичным для фичи.

```markdown
# Опрос уточнений требований

Скоуп: [кратко: название модуля / сервиса]
Спецификация: [относительная ссылка или имя файла]
Производная документация: [путь к индексу / папке, например ./docs/]
Активный черновик ответов (если есть): [например .input/proposals/round-name-proposal.md] — перенос в Q&A после сигнала пользователя

## Чеклист тем для уточнения

| Статус | Тема | Комментарий |
|--------|------|-------------|
| [ ] | … | … |

Или списком:

- [ ] …
- [x] …

## Вопросы и ответы

### [Тема / дата]

**В:** …

**О:** …

---

**В:** …

**О:** …
```

Статусы в таблице чеклиста:

| Статус | Значение |
|--------|----------|
| `[ ]`  | Открыт — ответ не получен |
| `[/]`  | В работе / частично — ответ дан, тема не закрыта окончательно |
| `[x]`  | Закрыт — ответ перенесён, тема закрыта |

**Ссылки в шаблоне:** поля «Спецификация» / «Производная документация» могут указывать пути относительно каталога опроса (в т.ч. на файлы в `.input/`). Это не нарушает правило «в `docs/` не ссылаться на `.input/`»: то правило относится только к markdown **внутри** каталога `docs/` модуля.

## Категории чеклиста (выборочно по релевантности)

Используй как **меню**, а не как обязательный полный перечень.

### Границы и ценность

- Включение/исключение из MVP; что явно «не делаем».
- Пользователи и роли; права на операции.
- Сценарии happy path и критичные альтернативы.

### Функциональность и правила

- Инварианты домена; идемпотентность; повторные попытки.
- Согласованность состояний (черновик → активен → архив и т.д.).
- Локализация, форматы дат/чисел, часовые пояса — если затрагивает UI/API.

### Данные

- Сущности, идентификаторы (UUID vs sequence), мягкое удаление.
- Объёмы, рост, сроки хранения, архивация, PII.
- Миграции и обратная совместимость чтения/записи.

### Интеграции и API

- Контракты (синхрон/асинхрон), версионирование, обратная несовместимость.
- Аутентификация, авторизация, делегирование, scopes.
- Rate limits, квоты, стоимость вызовов, таймауты, circuit breaker.
- Форматы ошибок и коды повторяемости.

### Нефункциональные требования

- Доступность, RTO/RPO, окна обслуживания.
- Производительность (latency, throughput), масштабирование.
- Наблюдаемость: логи, метрики, трассировки, алерты.
- Безопасность: угрозы, шифрование в покое и в транзите, секреты, аудит.

### Эксплуатация и жизненный цикл

- Конфигурация по средам; feature flags.
- Развёртывание, откат, миграции БД в релизе.
- Соответствие политикам (compliance) — если применимо.

### Согласованность артефактов

- Противоречия между спецификацией, архитектурными представлениями и описанием потоков.
- Термины: один глоссарий или явные синонимы.

## Перенос ответов в документы

**Порядок:** сначала чтение заполненного **`.input/proposals/<theme>-proposal.md`** → обновление **файла опроса** (чеклист + Q&A) → затем **спецификация** (если вне `docs/`) → затем файлы в **`docs/`** (требования, архитектура, потоки и т.д.) без ссылок из `docs/` на `.input/`, если так задано в репозитории.

Сопоставляй ответы с **реальными файлами** в репозитории; ниже — типичные роли документов, а не обязательные имена.

| Ответ касается | Куда писать (логическая роль) |
|----------------|-------------------------------|
| Бизнес-правила, объём MVP | Первичная спецификация + документ(ы) с требованиями / приоритизацией |
| Надёжность, производительность, сопровождение | Раздел или документ NFR / эксплуатации |
| Внешние системы, протоколы | Каталог интеграций / контрактов API + при необходимости спецификация |
| Потоки, шаги, сеть | Описание сценариев, последовательностей, сетевого взаимодействия |
| Границы системы, крупные части, компоненты | Архитектурные представления (структура, контекст, контейнеры — как принято) |
| Оглавление и ссылки | Индекс документации модуля (`README` и т.п.) |

После правок: пройдись по явным «открытым вопросам» в документах требований и закрой или перепиши их в зафиксированные требования.

## Пакетирование вопросов (пример логики)

1. Первый раунд: границы MVP + самые рискованные лакуны из разбора ТЗ.
2. Второй: данные и идентификаторы.
3. Третий: интеграции и ошибки/повторы.
4. Четвёртый: NFR и эксплуатация.

Если пользователь ограничен по времени — сортировать по **риску стоимости переделки** (контракты данных и внешних API выше косметики UI).
