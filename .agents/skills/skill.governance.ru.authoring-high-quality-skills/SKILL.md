# Авторство скиллов — планка качества

Скилл **не привязан к конкретному репозиторию**: пути вида `.agents/skills/...` ниже — это **конвенция размещения** в корне проекта; эталон для сравнения — **любой зрелый скилл**, который есть у команды, или критерии из раздела «Эталонная полнота» ниже.

Когда пользователь просит **новый скилл**, **доработать** существующий или **перенести** регламент/гайд в формат скилла, результат должен быть **сопоставим по полноте и удобству** с хорошим командным скиллом: тот же **класс структурирования** (агент находит ответы на типовые вопросы без догадок), а не обязательно тот же предметный домен.

## Что значит «настолько же детально»

1. **Охват по слоям темы** — не одна абзацная подсказка, а разделы по подзадачам домена (для стандартов кода типично: именование, структура, форматирование, стек-специфика, организация проекта, сдача; для других тем — своя естественная нарезка).
2. **Сканируемость** — таблицы для перечней правил, списки для процедур, **жирное** только для якорей, без «простыни» без структуры.
3. **Действия агента** — формулировки в повелительном/настоятельном наклонении к исполнителю («ориентируйся», «предпочитай», «проверь перед сдачей»), с оговоркой про конфликт с проектом, если нужно.
4. **Границы применения** — в начале: когда скилл активен, что делать при противоречии с локальными правилами репозитория.
5. **Связь с автоматизацией** — если тема допускает (линтеры, схемы, конфиги, CLI), **явно** указать артефакт (например `.editorconfig`, JSON Schema, скрипт) и кто главенствует при расхождении с текстом скилла.
6. **Чеклист перед сдачей** — короткий финальный список, по которому можно пройтись после генерации кода/артефакта.
7. **Прогрессивное раскрытие** — в `SKILL.md` только то, что нужно в большинстве обращений; длинные примеры, шаблоны и краевые случаи — в **`reference.md`** (или `examples.md`) с **одноуровневой** ссылкой из `SKILL.md`.

## Эталонная полнота (без соседнего файла в репозитории)

Если сравнивать не с чем, новый скилл должен по **структуре** закрывать:

| Измерение | Ожидание |
|-----------|----------|
| Вход | Скоуп, приоритет над конфликтами, куда смотреть дальше (`reference.md`, конфиги). |
| Правила | Перечни в таблицах или чётких списках; где уместно — разделение «должно» / «предпочтительно». |
| Процесс | Пошагово или чеклистом, если скилл описывает workflow. |
| Краевые случаи | В `reference.md`, не раздувая `SKILL.md`. |
| Завершение | 4–10 пунктов «перед сдачей» или definition of done. |

## Обязательные элементы `SKILL.md`

| Элемент | Требование |
|--------|------------|
| YAML frontmatter | Поля `name` (lowercase, дефисы, ≤64 символов) и `description` (непустой, ≤1024 символов). |
| `description` | **Третье лицо**, на **английском**: что делает скилл **и** при каких запросах/темах его включать (ключевые слова для поиска агентом). |
| Заголовок H1 | Понятное имя темы. |
| Вводный блок | Скоуп, приоритет над конфликтующими инструкциями, отсылка к сопутствующим файлам при наличии. |
| Основные разделы H2 | Логика темы, не одна куча; для стандартов — отдельно «именование / структура / формат / стек / проект» по смыслу. |
| Явные правила vs предпочтения | Где уместно — различать «должно» и «предпочтительно», чтобы не фиктивно жёсткие запреты. |
| Код и цитаты | Минимально достаточные примеры в `SKILL.md`; развернутые — в `reference.md`. |
| Финальный чеклист | 4–10 пунктов, проверяемых глазами или инструментом. |

## Ограничения формата Cursor

- **Длина:** тело `SKILL.md` **желательно** укладывать примерно в **500 строк**; избыток выносить в `reference.md`.
- **Расположение:** каталог скилла — под `<корень-репозитория>/.agents/skills/skill.<domain>.<ru|en>.<skill-name>/` (см. `rule.governance.ru.cursor-skill-command-rule-filenames.mdc`); внутри обязателен `SKILL.md`.
- Не создавать скиллы в `~/.cursor/skills-cursor/` (системная папка Cursor), если пользователь явно не просит пользовательский глобальный скилл.

## Процесс работы (когда пользователь заказал скилл)

1. **Зафиксировать цель и триггеры:** одна фраза «для чего» + список ситуаций, когда агент обязан открыть скилл (для блока `description` и вводного абзаца).
2. **Собрать иерархию правил** из источника (док, PDF, устно) — без потери важных исключений и «двух политик», если они есть.
3. **Проверить актуальность стека** (если источник содержит инструменты/технологии): для каждого инструмента убедиться, что он не устарел; задепрекейченные — пометить явно и указать современную альтернативу; разделить рекомендации на «новые проекты» и «legacy» там, где это различие существенно.
4. **Нарезать разделы** по подзадачам, добавить таблицы там, где сравниваются варианты именования/форматов/стеков.
5. **Добавить чеклист** и при необходимости **компаньон** (конфиг, схема, скрипт) с правилом приоритета.
6. **Вынести примеры** в `reference.md`, в `SKILL.md` оставить ссылку одного уровня.
7. **Сверка с источником по разделам:** пройтись по каждому смысловому блоку источника и убедиться, что он отражён в скилле; расхождения — устранить или явно отметить как намеренно опущенные. Объявлять скилл готовым только после этого шага.
8. **Проверить** `description`: третье лицо, английский, есть **WHAT** и **WHEN**.

## Актуальность стека и разделение new/legacy

Если скилл описывает инструменты, библиотеки или технологические подходы:

- **Не копировать стек из источника слепо** — источник мог быть написан 2–3 года назад; каждый инструмент проверять на актуальность.
- **Deprecated/unsupported инструмент** — отмечать явно (`create-react-app` → **не использовать**) и давать современную замену.
- **Разделять** рекомендации для новых проектов и legacy: `**Инструмент X** (новые проекты) / Инструмент Y (legacy)`.
- Если в источнике нет разделения new/legacy, а оно существенно — вводить его самостоятельно на основе текущего состояния экосистемы.

## Антипаттерны (не допускать)

- Один абзац вместо структуры; отсутствие триггеров в `description`.
- Смешение несвязанных тем в одном скилле без явного объединяющего workflow.
- Дублирование огромных листингов в `SKILL.md` вместо `reference.md`.
- Противоречия между скиллом и закреплённым конфигом без строки «что главнее».
- Описание на «я помогу вам…» в поле `description`.
- Рекомендовать задепрекейченный инструмент без пометки и современной альтернативы.
- Не разделять new/legacy там, где это меняет выбор инструмента.
- Объявлять скилл готовым без сверки с источником по разделам (шаг 7 процесса).

## Сверка с эталоном (обязательно)

Перед завершением авторства, **если в репозитории есть** другой содержательный скилл (стайлгайд, регламент процесса и т.д.), открой его и сравни **плотность и структуру**: число смысловых H2, таблицы, разделение обязательного и желательного, чеклист, наличие `reference.md`.

- Если пользователь **указал** путь к эталону — использовать его.
- Иначе можно взять **любой** наиболее развитый соседний каталог в `.agents/skills/` **этого** репозитория.
- Если соседей нет — опираться только на таблицу «Эталонная полнота» и обязательные элементы выше.

Шаблон-скелет нового скилла — [reference.md](reference.md).
