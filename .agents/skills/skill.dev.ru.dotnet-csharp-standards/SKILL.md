# C# / .NET 10 — стандарты кодирования

> Базовые принципы именования, структуры и форматирования — `skill.dev.ru.coding-standards-universal`. Ниже — только .NET/C#-специфика и переопределения.

Ориентируйся на эти правила для генерируемого и правимого C# кода под **.NET 8-10**, если в проекте нет явно противоречащих инструкций. Обязательные требования явно помечены как **MUST/MUST NOT**, рекомендации — как **SHOULD/MAY**.

Машинно проверяемое форматирование и часть стиля заданы в **`.editorconfig`** в корне репозитория; при расхождении текста скилла с `.editorconfig` для чисто синтаксических предпочтений (скобки, `var`, пространства имён) **можно** взять за основу `.editorconfig`.

## Нормативные уровни требований

- **MUST** — обязательное требование, нарушение считается дефектом стандарта.
- **MUST NOT** — запрещённый паттерн, требует переделки.
- **SHOULD** — рекомендуемая практика, отклонение допускается при обосновании.
- **MAY** — допустимая опция по контексту проекта.

## Переопределения относительно universal baseline

- Для C# используется **Allman style** для фигурных скобок.
- Для приватных констант применяется `_camelCase` (как для private fields).
- Префикс `I` для интерфейсов обязателен (`IOrderRepository`).
- Типы без планируемого наследования SHOULD помечаться `sealed`.
- Для библиотек MUST учитывать async-безопасность (`ConfigureAwait(false)`) и корректное пробрасывание исключений.

## Именование — C#-специфика

Базовые правила (PascalCase для типов/методов, camelCase для переменных/параметров, `_camelCase` для приватных полей, `I`-префикс для интерфейсов, `Is`/`Can`/`Has` для boolean, `T`-префикс для generic, enum без повтора имени типа, осмысленные имена лямбд) — в `skill.dev.ru.coding-standards-universal`.

| Элемент | Стиль | Пример |
|--------|--------|--------|
| Приватная константа | camelCase с префиксом `_` | `_maxRetryCount` |
| Приватное поле | camelCase с префиксом `_` | `_orderRepository` |
| Интерфейс | `I` + PascalCase | `IClock` |
| Обработчик события | `<EventName>Handler` | `OrderCreatedHandler` |
| Event args тип | суффикс `EventArgs` | `OrderCreatedEventArgs` |
| Исключение | суффикс `Exception` | `OrderNotFoundException` |
| EF-миграция | PascalCase | `AddCommentToTable1` |

**Сборки:** предпочтительно `<Product>.<Component>.dll` с точками в компоненте; для `.exe` **предпочтительно** не использовать точки как разделители в имени файла.

**Постфиксы типов:** `Attribute`, `Exception`, `EventArgs`, `Extension`, `Dictionary`, `Collection`, `Stream`, `Base` (абстрактный корень дерева). Делегаты, используемые как тип события, именуют с суффиксом **`EventHandler`**; прочие делегаты — по смыслу, часто **`Callback`**.

**Generic-параметры — порядок:** в обобщённых методах **предпочтительно** как у `Func<>`: сначала типы аргументов, затем возвращаемый тип: `Task<TResult> Post<TCommand, TResult>(TCommand command)`.

**Перечисления — C#:** простой enum — имя типа в единственном числе; флаги — множественное число + `[Flags]`. Явный базовый тип и числовые значения — **когда нужно** (флаги, комбинации, interop).

**Классы/структуры:** коллекции — `<Element>Collection`; элементы табличных/отчётных моделей — `<Name>Item`.

**Методы — события:** методы, поднимающие события, MUST использовать префикс `On` (`OnClose`). Обработчики MUST именоваться от имени события с суффиксом `Handler`, PascalCase без подчёркиваний.

**Свойства:** константы секций конфигурации — суффикс `Section`. Переиспользуемые значения — **`static readonly`** или свойство с expression body.

**Поля:** **предпочтительно** только `private`; наружу — свойства. Публичные изменяемые поля **лучше не использовать**; статические исключения (например `struct` interop) — по договорённости.

**Параметры методов — именование:** имена параметров должны быть полными и читаемыми без контекста; односимвольные (`r`, `e`) и сокращённые (`msg`, `dt`, `ext`) имена не допускаются — используй полные имена (`processingResult`, `message`, `displayType`, `additionalDetails`). Исключения: `sender`/`e` для BCL-событий (см. ниже), `i`/`j` для счётчиков вложенных циклов.

**Параметры BCL-событий:** `sender` и `e` (тип `EventArgs` или наследник). Мутации — минимизировать; предпочтительно `ref`/`out`, записи или явный возврат.

**Параметры-выходные буферы (без `out`/`ref`):** если параметр передаётся для заполнения/мутации внутри метода (семантика выходного параметра, но без ключевого слова `out`), называй с префиксом `out` в camelCase: `outResults`, `outAdditionalDetails`. Это сигнализирует вызывающему коду, что объект будет изменён внутри метода.

## Структура файла и класса — C#-специфика

- `using` до объявления `namespace`; **желательно** удалять неиспользуемые.
- Порядок членов по уровню доступа и по виду (поля→свойства→конструкторы→методы) — в `skill.dev.ru.coding-standards-universal`. Порядок ключевых слов **на одной строке** объявления (`static`, `abstract`, `virtual`, `override`, `sealed` и т.д.) — как в языке C# и в `.editorconfig`/стиле команды (см. [reference.md](reference.md)).
- **`partial`** — для отделения сгенерированного кода.
- **Extension-методы** — когда они читаются как методы типа; иначе статический helper.
- **Лямбды:** **предпочтительно** короткое тело (часто одна строка); если логики много — **лучше** локальная функция или именованный метод.

## Современный язык C# (ориентиры)

**Базовая политика фреймворков:** .NET 10 — **LTS**, `net8.0` - больше не поддерживается. Этот скилл применим к `net8.0`-`net10.0`; при LTS-требовании проекта MUST выбирать LTS-таргет и проверять совместимость фич языка.

**Все проекты** ориентируются на актуальный таргет проекта (`<TargetFramework>net8.0|net10.0</TargetFramework>` или стековый вариант, например `net10.0-windows`, если нужен). Язык C# — по умолчанию для выбранного SDK; понижать `LangVersion` SHOULD только при веской причине.

- **Файловые пространства имён** (`namespace X;`) — предпочтительны для новых файлов, если команда не держится за блочный `namespace`.
- **`using` declaration** (`using var x = …`) — предпочтительно для простых `IDisposable`, когда область видимости совпадает с блоком.
- **Pattern matching** (property/relational/list), **switch expression** (C# 8+) SHOULD применяться, если повышают читаемость и убирают каскады `if/else`.
- **Target-typed `new`** (`List<int> list = new();`) — допустимо рядом с явным типом слева, когда так яснее границы API.
- **Collection expressions** (`[1, 2, 3]`) — допустимы на подходящих таргетах, если стиль команды уже перешёл на них.
- **Primary constructors** — допустимы, когда не раздувают тип и согласуются с DI/тестируемостью; для сложной инициализации **предпочтительны** обычные конструкторы.
- **Nullable reference types** — в новых проектах **предпочтительно** `<Nullable>enable</Nullable>` и осмысленные аннотации (`?`, `required`, `null`-проверки).
- **События:** подписка методом/группой методов без `new EventHandler(...)`. Вызов снаружи типа объявления — через допустимый паттерн (копия делегата + `?.Invoke` или обёртка), избегая гонок и `NullReferenceException`.

## Async/Await и асинхронный код

- Async-методы MUST возвращать `Task`, `Task<T>` или `ValueTask`; `async void` допустим только для event handlers.
- В библиотечном коде SHOULD использоваться `ConfigureAwait(false)` (см. [reference.md](reference.md#asyncawait-examples)).
- `CancellationToken` SHOULD быть последним параметром публичных async-методов.
- В async-коде MUST NOT использовать `.Result`, `.Wait()`, `GetAwaiter().GetResult()` без изолированного boundary.
- `ValueTask` MAY использоваться только при подтверждённой оптимизации hot path и соблюдении ограничений повторного await.
- Потоки данных SHOULD использовать `await foreach` и `IAsyncEnumerable<T>` для стриминга.

## Обработка исключений

- `catch` MUST быть целевым: перехватывай ожидаемые типы исключений.
- Пустой `catch` и подавление ошибки без лога MUST NOT применяться.
- Для повторного выброса MUST использоваться `throw;` вместо `throw ex;`.
- Исключения MUST NOT использоваться как штатный control flow.
- Пользовательские исключения SHOULD наследоваться от `Exception` и отражать доменный контекст (`<Domain>ErrorException`).
- Исключения на boundary SHOULD логироваться структурированно без секретов и ПДн (см. [reference.md](reference.md#exception-handling-examples)).

## Record / Value Types

- `record` SHOULD использоваться для неизменяемых моделей и value-based equality.
- `class` SHOULD использоваться для сущностей с идентичностью и управляемым жизненным циклом.
- `record struct` MAY применяться для компактных value-типов без аллокаций, если это подтверждено измерениями.
- Для моделей запроса/ответа SHOULD использоваться `init`-only свойства и `required`, где это повышает корректность.
- Изменяемые `record` с settable-свойствами MUST NOT использоваться без явного обоснования.

## Dependency Injection

- Бизнес-код MUST получать зависимости через constructor injection.
- Service Locator (`IServiceProvider.GetService(...)` внутри доменной/прикладной логики) MUST NOT использоваться.
- Регистрация зависимостей SHOULD оформляться extension-методами `AddXxx`/`UseXxx`.
- Lifetime (`Singleton/Scoped/Transient`) MUST выбираться осознанно и документироваться для нестандартных случаев.

## IDisposable и IAsyncDisposable

- Типы, владеющие управляемыми/неуправляемыми ресурсами, MUST реализовывать `IDisposable` или `IAsyncDisposable`.
- Для асинхронного освобождения MUST использоваться `await using` (см. [reference.md](reference.md#idisposable-and-iasyncdisposable-examples)).
- В прикладном коде SHOULD предпочитаться `using` declaration для короткого и безопасного управления временем жизни.
- Dispose pattern с финализатором MAY использоваться только при прямом владении неуправляемыми ресурсами.

## Запреты (MUST NOT)

| Антипаттерн | Почему нельзя | Альтернатива |
|---|---|---|
| `async void` вне event handler | Нельзя отследить завершение/ошибки | `Task` / `Task<T>` |
| `catch (Exception) {}` без лога/ре-throw | Ошибки теряются | Лог + `throw;` или целевой `catch` |
| `Thread.Sleep` в async-коде | Блокировка потока | `await Task.Delay(...)` |
| `throw ex;` | Теряется исходный stack trace | `throw;` |
| `.Result` / `.Wait()` в async-потоке | Риск deadlock и блокировок | `await` |
| `dynamic` без обоснования | Потеря типобезопасности | Явные типы, generics, интерфейсы |

## Документация и комментарии — C#-специфика

Общая политика (язык, что документировать, `//` vs `/* */`, две политики проекта, TODO в трекер, краевые случаи `returns`) — в `skill.dev.ru.coding-standards-universal`.

- XML **предпочтительно** без пустых строк между тегами.
- Конструктор: кратко «Конструктор.», если не нужно больше.
- Обработчики событий обычно не документируют — логику **можно** вынести в именованный метод с XML.
- Для наследования — `<inheritdoc/>`, если описание в базовом классе/интерфейсе.
- Пометки о доработках — `#warning` или задачи трекера.
- Для библиотек: **желательно** `<GenerateDocumentationFile>true</GenerateDocumentationFile>` (XML-комментарии попадают в сборку для IntelliSense и потребителей пакета).

## Форматирование — C#-специфика

Базовые правила (4 пробела, ≤150 символов, одна инструкция на строку, пробелы вокруг операторов, `if`/`else` в `{}`, объект-инициализаторы) — в `skill.dev.ru.coding-standards-universal`.

**Стиль скобок (Allman — переопределение universal):** открывающая `{` на **новой строке** на уровне объявления; тело с отступом. Наследование: `class A : B` с пробелами вокруг `:`.

- **Fluent / LINQ:** переносы перед `.`; вложенность — **+4** пробела на уровень.
- Между именем метода и `(` пробела нет; модификатор доступа **предпочтительно** первым.
- **Свойства:** однострочно при простом accessor; иначе get/set на отдельных строках.
- **Лямбда:** один параметр — без скобок; одно выражение — без `return` и `{}`.
- **`switch`:** классический или **switch expression** — по читаемости (см. `.editorconfig`).
- **`try` / `catch` / `finally`** — в стиле проекта; фильтры `when` допустимы.
- **`this`:** **не** использовать для статических членов того же типа; `this` — при скрытии имён и при передаче текущего объекта.
- **`#region`:** **по возможности не добавлять**; если нужен — через ревью.

## Типы и стиль кода — C#-специфика

- **Предпочтительно** ключевые слова языка (`string`, `int`, `object`) вместо `String`, `Int32`, `Object`; nullable — `int?` и т.д.
- **`var`** — когда тип очевиден справа (`new TypeName(...)`, `new()`, анонимный тип, `for`/`foreach`, простые LINQ-цепочки). Если тип **неочевиден** без «мысленного вычисления» — **предпочтительно** писать явный тип слева.
- Тип по умолчанию часто **`internal`**; типы без задуманного наследования часто помечают **`sealed`**.
- Пустая строка — **`string.Empty`**; по возможности стандартные константы (`EventArgs.Empty`, …). Строковые литералы **предпочтительно** не дублировать — выносить в константы/ресурсы; исключения: имена для `INotifyPropertyChanged`, строки для reflection.
- События: `EventHandler` / `EventHandler<T>`; подписка без явного `new` конкретного типа делегата.

## Entity Framework Core

- Для read-only запросов SHOULD использоваться `AsNoTracking()`.
- MUST избегать N+1: использовать явные `Include`, projection, batch-подходы.
- Конфигурацию сущностей SHOULD выносить в `IEntityTypeConfiguration<T>`.
- Именование таблиц/схем MUST быть консистентным и централизованным в конфигурации модели.
- `EF.Functions`: **по возможности** не злоупотреблять; при использовании **желательно** комментарий про ограничения СУБД (например `EF.Functions.ILike` и PostgreSQL).
- Имена миграций — PascalCase; при коллизии — суффикс даты/времени.
- Вложенные JSON-сущности: суффикс **`JsonEntity`**, в XML/комментарии — что хранится как JSON/JSONB; конфигурация колонки и отдельно обычные связи через FK.
- Вложенные сущности — в **Entities** домена, без смешения с прочими моделями.

## Проект

- Целевой фреймворк выбирается по политике проекта: **LTS (`net8.0`)** или **STS (`net10.0`)**; в новых `csproj` SHOULD быть включён nullable-контекст (`<Nullable>enable</Nullable>`).
- Корпоративный NuGet: источник через `dotnet nuget add source` на **внутренний** registry; URL и токены — из документации организации, **не** хардкодить секреты.

## Перед сдачей (чеклист)

1. C#-постфиксы (`Attribute`, `Exception`, `EventArgs`, `EventHandler`, `JsonEntity`) согласованы; приватные поля/константы `_camelCase`; параметры методов — полные имена без сокращений.
2. `using` до `namespace`; неиспользуемые удалены; файловые namespace в новых файлах.
3. Allman-скобки; LINQ/fluent — переносы перед `.`; `var` только когда тип очевиден справа.
4. Async-код: нет `async void` (кроме событий), нет `.Result/.Wait()`, `CancellationToken` последним параметром (см. [reference.md](reference.md#asyncawait-examples)).
5. Исключения: нет пустых `catch`, используется `throw;`, исключения не применяются как control flow (см. [reference.md](reference.md#exception-handling-examples)).
6. Модели: корректный выбор `record`/`class`/`record struct`, `init`/`required` по месту (см. [reference.md](reference.md#record-and-record-struct-examples)).
7. DI: constructor injection, без Service Locator в бизнес-логике (см. [reference.md](reference.md#dependency-injection-examples)).
8. Ресурсы: корректный `using`/`await using`, `IDisposable`/`IAsyncDisposable` при владении ресурсом (см. [reference.md](reference.md#idisposable-and-iasyncdisposable-examples)).
9. EF / Mapster / модели — по разделам выше.
10. Базовые пункты (структура, константы, валидация, запросные модели) — сверить с `skill.dev.ru.coding-standards-universal`.

Подробные примеры — [reference.md](reference.md).
