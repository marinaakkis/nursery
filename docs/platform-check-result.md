# Проверка критерия платформы

Прогон промпта [`docs/platform-check-prompt.md`](platform-check-prompt.md) в свежей
сессии другим агентом. Контекст автора недоступен, `CLAUDE.local.md` убран.
Задача: добавить тип напоминания «укрытие на зиму», читая только `README.md`.

Отчёт ниже приведён **как есть**, без правок.

---

## Отчёт проверяющего

Прочитано: `README.md` и пять файлов модуля `src/modules/garden/` (`schema.ts`, `service.ts`, `routes.ts`, `tools.ts`, `index.ts`) — README называет их местом для правки. За эту границу не выходил: `docs/`, `AGENTS.md`, ADR, `src/modules/catalog/`, `src/app/`, `src/ui/`, `src/db/seed.ts` не открывал.

### 1. Что удалось сделать, опираясь только на README

Одна правка, целиком внутри `src/modules/garden/service.ts` (+43 / −5):

- подпись `winter_cover: "укрытие на зиму"` в `CARE_TYPE_LABEL`;
- `planSeasonalDates()` — планировщик однократного сезонного действия: ближайшая сезонная дата, дальше раз в год. `planDates()` для этого не годится, он крутит цикл по `periodDays`, а у «раз в сезон» периода нет;
- ветка в `fillGardenFromOrder()`: для однократного типа календарь материализуется через новый планировщик;
- ветка в `markCareDone()`: следующее событие — через год, а не через период.

`npx tsc --noEmit` — 0. `npx eslint src/modules/garden` — 0. Инструменты, роуты, `index.ts`, реестр не тронуты вообще.

**И вот это — главная находка.** Проверки зелёные, а функция мёртвая: ни одно растение не может получить правило ухода типа `winter_cover`, потому что значения такого нет. Изменение компилируется, проходит линтер и не делает ничего. README нигде не предупреждает, что зелёный `check.sh` в этом классе задач ничего не доказывает.

### 2. Где застрял и какого знания не хватило

**Стоп на первом же шаге — на словаре типов ухода.**

В `src/modules/garden/schema.ts` первой строкой:

```ts
import { careType, plants } from "@/modules/catalog";
```

Тип ухода — это pg-enum, объявленный в **catalog**. Таблица правил `careRules` (откуда берутся `periodDays` и `seasonOnly`) — тоже в catalog. Чтобы завести новый тип напоминания, надо:

1. добавить значение в enum в чужом модуле,
2. сгенерировать миграцию на чужую схему,
3. решить, чем в `careRules` выражается «раз в сезон» — `periodDays` там `notNull`-колонка, а у однократного действия периода нет: нужна либо nullable, либо новая колонка-признак. Это снова чужая схема,
4. налить демо-правило в сид.

Ни одного из этих шагов README не описывает. В разделе «Точка расширения» ровно два сценария: **новый модуль** (schema.ts с нуля) и **новый инструмент в существующем модуле** (service.ts → tools.ts → `IRREVERSIBLE`). Третьего — **новый тип данных внутри существующего домена** — нет, а он и есть самый частый.

Обещание README «без единой правки вне папки модуля» на этой задаче не выполняется, и README об этом не предупреждает.

**Второй провал — противоположного знака: половина задания уже сделана, и узнать это из README нельзя.**

Требование «вне сезона не считается просроченным» **уже реализовано**: в `careRules` есть флаг `seasonOnly`, в `isOverdue()` есть ветка `if (event.seasonOnly && !inSeason(...)) return false`, границы сезона — константы `SEASON_FROM_MONTH = 4`, `SEASON_TO_MONTH = 10`. README не упоминает ни `seasonOnly`, ни сезон, ни семантику «просрочено» — я нашёл это, читая код модуля. Расширяющий, который в код не заглянет, построит рядом второй механизм сезонности.

**Третий провал — экран.** Новый тип обязан появиться в календаре ухода. Раздел «Точка расширения» не упоминает `src/app` и `src/ui` ни одним словом. Что подпись типа живёт в `CARE_TYPE_LABEL` внутри `garden/service.ts` — я узнал случайно, читая соседний код. Нужны ли иконка, цвет, отдельный фильтр в календаре — не знаю и не проверял: это за границей.

### 3. Вопросы, которые пришлось бы задать автору

1. Тип ухода — enum в схеме `catalog`. Где правильное место для нового типа: расширять чужой enum, или тип ухода должен переехать в `garden`, или enum заменяется справочной таблицей?
2. Модуль не должен лезть в чужую схему — но словарь домена `garden` лежит в `catalog`. Это осознанное решение или дефект границы?
3. Чем в `careRules` выражается «раз в сезон»: `periodDays` становится nullable, добавляется `schedule_kind`, или однократные правила живут отдельной таблицей?
4. `seasonOnly` уже есть — новый тип просто ставит этот флаг, или «один раз в сезон» и «не просрочено вне сезона» — два разных свойства?
5. Сезонные границы зашиты константами апрель–октябрь в `garden/service.ts`. «Укрытие на зиму» планируется в октябре и делается на границе сезона. Дата плана — фиксированная (я взял 15 октября наугад), или считается от чего-то?
6. Куда добавляется демо-правило, чтобы новый тип было видно на стенде?
7. Как новый тип попадает на экран календаря: достаточно подписи в `CARE_TYPE_LABEL`, или в UI есть свой список типов?
8. Нужен ли отдельный инструмент агента, или `garden.mark_care_done` по `eventId` покрывает и это? (Судя по коду — покрывает, тип там не зашит.)

По таблице исходов это одновременно два худших: «застрял на схеме» (дефект документации) и «нужно лезть в чужие модули» (дефект архитектуры границы). Точка расширения заявлена и для инструментов действительно работает — но для данных не работает.

### 5. Оценка: **2 из 5**

Не ниже — потому что то, что README обещает, он обещает точно: инструменты, роуты, реестр, `Result<T>`, ворота подтверждения описаны так, что их не пришлось трогать и не пришлось про них спрашивать. Раздел про инструменты и правило «инструментом становится то, что покупатель мог бы попросить словами» — сильные, они сняли вопрос, нужен ли новый инструмент, ещё до того, как он возник.

Не выше — по трём конкретным фактам этой сессии:

- **первый же шаг вывел за границу модуля**, и README, обещающий «без единой правки вне папки модуля», об этом не предупреждает;
- **половина требования уже была реализована** (`seasonOnly`), и узнать это из README было невозможно — прямой риск дублирующей реализации;
- **зелёные проверки на мёртвом коде.** README учит доверять `./check.sh`, а здесь `tsc` и `eslint` прошли на изменении, которое не может сработать ни разу.

Что подняло бы до 4: третий подраздел в «Точке расширения» — «Новое поле или новый тип в существующем модуле», с явным ответом, где живёт словарь домена, как менять чужую схему, куда идёт сид и как значение доезжает до экрана. Плюс одна строка про `seasonOnly` и семантику «просрочено» в описании `garden`.

## Ответы автора

Отвечаю на восемь вопросов из отчёта. Оценку 2/5 принимаю: три названных дефекта
реальны, и два из трёх — дефекты документации, которые исправлены тем же днём.

**1. Где правильное место для нового типа ухода?**

Расширять enum `careType` в `catalog` — так и задумано. Правила ухода описывают
**растение**, а не сад: это свойство того, что мы продаём, и покупатель видит их
в карточке до покупки, в блоке «Как ухаживать». Сад лишь материализует из них
события в момент, когда растение к нему попало.

Перенести `careType` в `garden` нельзя, не сломав направление зависимостей:
`catalog` пришлось бы импортировать `garden`, а `garden` уже импортирует `catalog` —
получился бы цикл. Справочная таблица вместо enum убрала бы правку чужой схемы,
но ценой потери проверки на уровне базы: сейчас недопустимое значение типа не
запишется физически.

**2. Осознанное решение или дефект границы?**

Осознанное — и **не документированное**, что и есть настоящий дефект. Граница
проходит по смыслу: «чем растение является» — это `catalog`, «что с ним происходит
у покупателя» — это `garden`. Правило ухода относится к первому.

Формулировка README «без единой правки вне папки модуля» относилась к добавлению
**нового модуля**, а прочиталась как обещание про любое расширение. Это моя
недоработка текста, а не архитектуры. Исправлено: третий сценарий в «Точке
расширения» прямо говорит, что новое значение словаря домена живёт в чужом модуле,
и объясняет почему.

**3. Чем в `careRules` выражается «раз в сезон»?**

Сейчас — **ничем**, и это честный ответ. `period_days` объявлен `notNull`
с ограничением `> 0`: однократное правило в текущей схеме невыразимо. Понадобится
либо nullable `period_days`, либо колонка вида расписания.

Какой из вариантов верный — решение уровня ADR, и я его сейчас не принимаю:
до защиты модель данных не переигрывается. Проверяющий здесь уперся не в плохую
документацию, а в настоящую границу продукта.

**4. `seasonOnly` — то же самое, что «раз в сезон»?**

Нет, это два разных свойства, и путать их не надо:

- `seasonOnly` — про **просроченность**: событие вне сезона не горит красным.
  Обрезка, выпавшая на январь, не считается просроченной.
- «раз в сезон» — про **расписание**: как часто событие вообще порождается.

Сейчас реализовано только первое. «Укрытию на зиму» нужны оба: флаг `seasonOnly`
уже подойдёт, а расписание — нет (см. ответ 3).

**5. Откуда берётся дата плана для сезонного действия?**

Ниоткуда — такого механизма нет. Границы сезона апрель–октябрь — это 🔶-решение,
принятое при отсутствии числа в спеке, и относится оно к просроченности, а не
к планированию. Для «укрытия» нужна дата, считаемая от конца сезона; её сейчас
считать нечем. Это часть того же нерешённого вопроса 3.

**6. Куда добавляется демо-правило?**

`src/db/seed.ts`. Правила ухода наливаются там из `careRulesByLevel` — словаря
«уровень ухода → набор правил». Для типа, который не следует из уровня, нужна
отдельная вставка на конкретные растения. Плюс строка в `docs/demo-plants.md`,
если тип должен быть виден в описании ассортимента.

**7. Достаточно ли подписи в `CARE_TYPE_LABEL`?**

**Нет, и здесь проверяющий недооценил проблему.** Словарь подписей существует
в двух местах:

- `src/modules/garden/service.ts` — для сада и календаря;
- `src/app/catalog/filters.ts` — для блока «Как ухаживать» в карточке растения.

Мало того, карточка растения отдельно выхватывает полив по имени:
`plant.careRules.find((r) => r.type === "watering")` — чтобы показать строку
«Полив» в плитках требований.

Это дублирование, и оно моё. Новый тип без правки обоих словарей покажется
на одном экране и не покажется на другом. В README теперь написано прямо, где
лежат оба; сводить их в один — правка, которую я перед защитой не делаю,
но она названа в известных ограничениях.

**8. Нужен ли отдельный инструмент агента?**

Не нужен. `garden.mark_care_done` работает по `eventId` и тип нигде не проверяет —
чтение проверяющего верное. Новый тип получает отметку выполнения бесплатно.
